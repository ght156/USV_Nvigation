## 2. 结论

1. 五个归港节点迁移为 C++ 后，同为空闲状态、相同 5 秒采样方式下，合计 CPU 从 **120.50% 降至 21.40%**，绝对释放 **99.10 个百分点**，相对下降约 **82.2%**，约释放一个 8 核系统中的 **0.99 个 CPU 核**。
2. 合计 RSS 从 **348.9 MiB 降至 199.1 MiB**，下降约 **42.9%**；线程数从 **95 降至 67**，下降约 **29.5%**。
3. C++ 版本首次出港失败的直接原因不是 AprilTag 没有检出，而是 `/dock/in_dock` 的 `wait_vision=true` 服务等待期间，`dock_mission` 的订阅回调无法刷新缓存，最终误报“估计器不在线”。
4. 已确证根因为 **Executor 使用方式错误**：主循环逐个调用 `spin_once()`，阻塞服务回调占住唯一实际 spin 线程；虽然创建了 `MultiThreadedExecutor`，但没有通过 `executor.spin()` 启动线程池。
5. 修复后完整 `dock_mission` 测试为 **24 tests，0 errors，0 failures**；实船完成一次出港和一次一键归港，事件 ACK、AprilTag 通道收尾及夹爪检测均正常。

## 4. 出港失败现象与根因

### 4.1 现象

部署 C++ 版本后，出港前的 `/dock/in_dock {wait_vision: true}` 查询不能利用等待期间新到达的视觉位姿，日志出现：

```text
in_dock 查询: 检测节点异常/未就绪（apriltag 服务或估计器不在线），按失败处理，in_dock 不可信
```

同期 AprilTag 检测和位姿估计节点实际在工作。问题反复出现，重启后仍可按相同路径复现。

### 4.2 已确证的代码机制

旧主程序结构为：

```cpp
executor.add_node(node);
while (rclcpp::ok() && !stop_requested) {
  executor.spin_once(std::chrono::milliseconds(100));
}
```

`/dock/in_dock` 服务在 `wait_vision=true` 时需要等待视觉锚定。该服务回调由主循环的 `spin_once()` 执行后，主循环便停在服务内等待；而 `/docking/dock_pose`、`/docking/pose_source`、`/docking/anchor_status`、`/docking/measurement_age` 的订阅回调也只能等下一次 `spin_once()`，形成循环等待：

```text
服务回调等待新视觉缓存
        ↓
订阅回调需要 spin 才能刷新缓存
        ↓
唯一实际 spin 线程仍阻塞在服务回调中
        ↓
等待超时，误报估计器不在线
```

这不是“`MultiThreadedExecutor` 一定自动并发”：只有把节点交给 `executor.spin()` 持续调度后，线程池才能同时执行服务与订阅回调。

### 4.3 回归测试先行

新增 `src/dock_mission/test/test_in_dock_wait_vision.py`，启动真实 `dock_mission_node`：

1. 先发布 `INVALID` 位姿；
2. 异步调用 `/dock/in_dock {wait_vision: true}`；
3. 在服务等待期间持续发布 `VISION`、有效锚点和零量测年龄；
4. 要求服务及时返回 `pose_valid=true`、`in_dock=true`、`pose_source=VISION`；
5. SIGINT 退出并检查进程收尾。

测试先在旧实现上复现失败，修复后通过，避免了仅凭一次实船成功就认定问题闭环。

## 5. 修复、构建与部署

修改 `src/dock_mission/src/dock_mission_node_main.cpp`：

- 独立线程运行 `executor.spin()`，主线程仅周期检查退出信号；
- 退出时先执行节点 `shutdown()`，再 `executor.cancel()`、join 线程、销毁节点并关闭 ROS context；
- 保持原节点接口、参数、状态机和安全行为不变，继续统一使用 `m_common::mlogger`；
- 未新增第三方依赖。
