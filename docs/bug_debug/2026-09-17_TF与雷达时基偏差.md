# 2026-09-17 里程计 / TF 打戳比雷达快 0.85 s（时基不同源）

| 影响面 | Nav2 点云避障落图、bag 事后对齐、按时间戳做的多源融合 |

## 二、实测数据（age = now − 消息时间戳；负值 = 消息时间戳超前于系统钟）

| 数据流 | 时间戳来源 | 实测 age | 判定 |
|---|---|---|---|
| `/livox/lidar` 逐点 timestamp | 雷达自己的钟（PPS+GPRMC 授时） | −0.012 s | 与 UTC 一致 |
| `/livox/lidar` header | 同上 | −0.008 s | ✓ |
| `$GNGGA` 解析出的 stamp | 接收机 GNSS UTC | −0.085 s | ✓（报文晚到 ~85 ms） |
| `$INSPVAA` 自带时间 | 惯导解算的 UTC | **−0.850 s** | ✗ 快了 0.85 s |
| `/mavros/gps_input/local` | 抄 INSPVAA | −0.844 s | ✗ |
| `odom→base_link` TF | 抄 INSPVAA | **−0.842 s**（主机）/ −0.827 s（NX） | ✗ |
| `map→odom` TF | 同 INSPVAA 时基 | −0.77 s | ✗ |

三路对得上、一路单飞 → 偏的是 INSPVAA 这一路。**不是 TF 数值错，是 TF 挂的时间标签和激光不在一个时基上。**

## 三、机制

- tf2 的查询是**按时间标签**做的：给定查询时刻 `t`，在缓存里找"标签 ≤ t 的最新一帧"和"标签 ≥ t 的最早一帧"做插值；找不到就抛 `extrapolation`，**不会退而取最近一帧**。
- 点云用自己的 `header.stamp` 当查询键（`nav2_costmap_2d/src/observation_buffer.cpp` 的 `tf2_buffer_.transform(cloud, out, global_frame_, tf_tolerance_)`）。
- 因为 TF 标签**快** 0.85 s，云的时刻永远落在缓存区间内部（缓存默认 10 s），所以插值总是成功、**不报错、不丢帧**——只是取到的是"真实 0.85 s 前"那一帧姿态。
- 反过来若 TF 标签**慢** 0.85 s，云的时刻会晚于缓存最新样本，tf2 会等满 `transform_tolerance` 后抛 `into the future`，表现为整帧丢云 + 日志刷屏。**偏差方向决定了是静默错位还是响亮报错**，这次遇到的是更难查的那种。

同一个 TF 树上 Nav2 有两类查询：

| 用途 | 查询方式 | 结果 |
|---|---|---|
| 点云落图 | 按 `cloud.header.stamp` | 用 0.85 s 前的姿态 |
| 船位（滚动窗口中心、RPP、碰撞检查） | `getCurrentPose` 默认 stamp=0 → tf2 `TimePointZero` = 取最新 | 用最新标签那一帧 |

两者差 0.85 s 的船体运动，点云因此在代价地图上整体错位；RViz 与 `ghost_diag.py` 用的是同一套 TF，所以**自洽、看不出来**，只有拿真实位置对照才会暴露。

## 四、量级

按当前配置（`desired_linear_vel: 0.5`、可达角速度 ~0.15 rad/s）：

- 直航：0.5 × 0.85 ≈ **0.42 m** 纵向错位（障碍被标在更近的位置）；
- 转向：0.15 × 0.85 ≈ **7.3°** 指向误差，`obstacle_max_range: 20` 处横向偏 **约 2.2 m**。

## 五、修法（未实施）

1. 首选在 GI320 驱动或喂 MAVROS 的那一段，把 stamp 改到与雷达同源的时基（用接收时刻，或减掉实测常数偏置）；
2. 短期可加一个 stamp-repair 重发节点（参考 `gnss_odom_map_tf.py`），同时确认 MAVROS 侧 `tf.send:=false`，避免两套 TF；
3. **不要**反过来给雷达加 +0.85 s 去迁就 TF —— 雷达那路被两个独立源印证过，改它会把 bag 分析、SLAM 对接一起带偏；
4. 验证标准：四路 age 收敛到 ±30 ms 以内。
