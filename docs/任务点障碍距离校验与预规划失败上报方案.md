# 任务点障碍距离校验与预规划失败上报方案

> 目的：避免平台下发的任务点距离岸边或障碍物过近，船仍执行并长期反复尝试；
> 同时为平台提供“哪个点不合法、是否需要修改”的明确结果。
>
> 本文是后续开发方案，不代表所述校验和新增上报字段已经全部实现。

## 1. 问题与目标

当前 RPP 控制器依据局部代价图和实际 padded footprint 做碰撞检查，全局规划器依据
全局代价图规划路径。任务点过近时，如果只在航行过程中依赖 RPP 碰撞检查，船会先到
障碍附近，再出现碰撞急停、受困和任务失败，效率与安全性都不好。

需要形成两级防护：

1. **静态障碍/岸线：执行前拦截。** 点位本身不安全时，不进入执行状态，并明确告诉
   平台哪个点需要修改。
2. **动态障碍：执行时安全拦截。** 后来发现障碍时，先暂停、等待或重规划；障碍持续
   存在且无法绕开时再上报。动态障碍不能直接等同于“任务点需要修改”。

## 2. 全局静态障碍扩张与预规划

### 2.1 推荐做法

对全局静态地图中的岸边和实际障碍做适度的**硬障碍扩张**，让全局规划器把扩张区域
视为不可通行。其作用包括：

- 任务点落入扩张区时，执行前预规划失败；
- 航线需要穿越过窄区域时，预规划失败或选择更安全的绕行路径；
- 不直接修改 RPP 使用的局部代价图，局部碰撞保护仍独立存在。

### 2.2 与全局膨胀层的区别

`inflation_radius` 产生的是由近到远的代价值梯度，**不是所有膨胀区域都是硬禁区**。
如果只增加全局膨胀半径，规划器在缺少其他路径时仍可能选择高代价路径，不能保证
拒绝过近点位。

因此：

- 需要“明确不可通行”的区域，应使用静态致命格扩张或 keepout 掩码；
- 需要“尽量远离但允许通过”的区域，才使用非致命的膨胀代价；
- 两种效果会叠加，窄航道必须做规划可行性和实船 A/B 验证。

全局静态扩张会影响 RPP 实际跟踪的全局路径，但不应直接改变局部代价图中的障碍
数据。它是全局安全约束，不能替代局部实时碰撞检查。

### 2.3 直接点位距离检查可替代硬扩张

如果导航侧或平台已经能够检查“任务点是否位于障碍上”以及“任务点到障碍/岸线的距离”，
那么为了拒绝过近点位，**不必再对全局静态障碍做硬扩张**。直接校验更简单，也不会改变
全局规划器原有的代价分布。

可在静态地图或全局代价图上预先计算障碍距离场，逐点查询最近障碍距离。距离阈值暂定
**2 m**，但必须做成可配置参数，未来根据船体、定位误差、航道和实船结果调整。
检查时应考虑船体尺寸、朝向和定位误差，不能只凭一个像素点判断。

点位校验必须区分以下级别，并使用不同告警/拒绝原因：

| 条件 | 错误码 | 默认处置 | 平台上报语义 |
|---|---|---|---|
| 点位位于障碍/岸线占用区 | `WAYPOINT_IN_OBSTACLE` | 拒绝执行 | 点位落在障碍内，必须修改 |
| 点位不在占用区，但最近障碍距离 ≤ 2 m | `WAYPOINT_OBSTACLE_TOO_CLOSE` | 拒绝执行；未来可配置为仅警告 | 点位离障碍过近，建议修改 |
| 距离 > 2 m 且其他检查通过 | 无 | 允许进入后续预规划 | 静态点位检查通过 |
| 地图/定位/距离数据不可用 | `WAYPOINT_VALIDITY_UNKNOWN` | 不得放行 | 当前无法确认点位安全性 |

近障事件除点位身份外，还应携带 `distance_to_obstacle_m` 和
`obstacle_distance_threshold_m`，便于平台显示实际距离并支持未来调整阈值。
“仅警告”只能是近障级别的可选策略；点位已经在障碍内时不能降级为仅警告。
点位不满足要求时应拒绝或明确标记跳过并上报 `index + seq`，不能静默跳过后仍把整条
任务报告为完整完成。

硬边界扩张仍可用于另一个目的：约束整条全局航线与岸线的距离。若只解决点位过近问题，
它不是必需步骤。

## 3. 状态机必须检查预规划结果

上层 Decision/任务状态机在启动 `NavigateTask` 前，应先调用：

- `mission_bridge/plan_mission`
- 类型：`m_common/srv/PlanMission`

该接口对全量航点调用 Nav2 `ComputePathThroughPoses`，预规划成功不会启动或修改当前
任务。状态机应采用以下规则：

1. `IDLE/待执行` 收到新任务后，先进入 `VALIDATING/PREPLANNING`。
2. 调用预规划并检查 `success`，不能只看 service 是否调用成功。
3. 预规划成功且路径非空，才允许进入 `RUNNING` 并发送 `NavigateTask`。
4. 预规划失败时保持在任务接收/拒绝分支，**不得启动 FollowWaypoints，不得自动重试
   同一任务点，也不得把它包装成航行过程中的普通控制失败**。
5. 向平台上报预规划失败和点位信息，等待修改后的新任务；新任务应带新的
   `command_id`，避免与上一次失败事件混淆。

仅收到 `ComputePathThroughPoses` 失败，通常无法知道具体哪个点不合法。状态机不能
猜测点位。需要在上报前增加逐点合法性检查，或让导航侧返回明确的失败点索引。

## 4. 上报“哪个任务点需要修改”

### 4.1 必须保留的点位身份

航点数组索引与原始 `MissionWaypoint.seq` 都要保留：

- `waypoint_index`：从 0 开始的数组索引，便于程序定位；
- `waypoint_seq`：平台下发的原始序号，导航不得重新编号；
- `latitude` / `longitude`：便于平台界面定位和人工核对；
- `task_id` / `command_id`：标识本次任务和指令。

### 4.2 建议的事件内容

现有 `NavigateTask.Result` 可用 `RESULT_PLANNING_FAILED` 表示规划失败，并用
`final_current_seq` 指向失败点、`final_reached_seq` 指向前一已到达点；但当前 Result
没有完整点位数组。建议由 Decision 终态处理链路上报平台，同时在 `/task_event` 的
JSON 详情中为 GCS 增加兼容性字段。新增 JSON 字段不影响旧字段消费者。

示例：

```json
{
  "event": "TASK_FAILED",
  "task_id": "task-20261119-01",
  "command_id": "command-new-02",
  "detail": {
    "failure_stage": "PREPLAN",
    "error_code": "WAYPOINT_OBSTACLE_TOO_CLOSE",
    "failed_waypoint_index": 9,
    "failed_waypoint_seq": 10,
    "latitude": 31.000000,
    "longitude": 120.000000,
    "distance_to_obstacle_m": 1.35,
    "obstacle_distance_threshold_m": 2.0,
    "reason": "waypoint is too close to an obstacle or shoreline",
    "needs_waypoint_update": true
  }
}
```

要求：

- 预规划阶段失败时，`failed_waypoint_index` 和 `failed_waypoint_seq` 必须指向同一点；
- 不知道具体点位时，应返回 `unknown`，不能把 0 或当前执行点冒充失败点；
- 平台收到 `needs_waypoint_update=true` 后，应提示修改该点并重新下发；
- 若一次发现多个非法点，可扩展 `invalid_waypoints` 数组，逐项包含上述身份字段；
- 不建议只把点位写在自由文本 `message` 中，因为平台难以稳定解析。

## 5. 局部代价图中的过近校验是否合理

**合理，而且适合作为全局静态校验之外的第二道防线，但它解决的是动态安全问题，
不是永久点位合法性问题。**

### 5.1 适用场景

- 地图生成后出现新的障碍；
- 静态地图或岸线存在误差；
- 当前目标点附近有水草、漂浮物、其他船或临时施工区域；
- 全局地图尚未包含这些实时障碍。

在逐点发送 `FollowWaypoints` 前，可检查当前目标在局部代价图中的占用和距离；必要时
也检查上一航点到目标的近场路径段，而不是只检查目标中心一个栅格。

### 5.2 必须处理的边界条件

1. **局部地图覆盖范围有限。** 超出局部窗口的航点返回 `NOT_EVALUATED`，不能判合法，
   也不能判非法；等船接近后再校验。
2. **使用船体而非点。** 应按当前 padded footprint 或可配置安全余量检查目标占用区域；
   只看 base_link 中心点会漏掉船头、船身和旋转扫碰。
3. **局部数据必须新鲜。** TF 不可用、代价图过旧、定位丢失时返回 `UNKNOWN`，不能因
   缺数据而直接放行。
4. **避免单帧误判。** 水雾、尾流、自回波和鬼影都可能产生瞬时障碍，应使用连续多帧、
   障碍持续时间或多次确认；清图后也必须等待新的有效观测。
5. **动态障碍具有时效性。** 障碍消失后点位应恢复可执行，不应永久写入泊位库或要求
   平台修改坐标。

### 5.3 推荐的状态机行为

局部校验失败时返回独立原因，例如：

```json
{
  "error_code": "WAYPOINT_TEMPORARILY_BLOCKED",
  "failure_stage": "LOCAL_PRECHECK",
  "failed_waypoint_seq": 10,
  "needs_waypoint_update": false,
  "retry_policy": "wait_or_replan"
}
```

建议先暂停/等待或请求局部重规划；只有持续超时且确认无法绕开时，才终止任务并上报。
不要把它与 `WAYPOINT_OBSTACLE_TOO_CLOSE` 混用，否则平台会误以为动态障碍出现后必须
修改任务点。

## 6. 推荐实施顺序

1. 实现全局静态障碍/岸线的逐点距离检查（阈值可配置），并确认 `plan_mission` 对非法任务失败；
   只有在还需要约束整条航线时，才额外评估静态硬扩张。
2. 增加逐点合法性检查，使预规划失败能准确携带 `index + seq + lat/lon`。
3. Decision 状态机强制检查预规划 `success`，失败不上船执行，并向平台上报修改要求。
4. 在逐点下发前增加局部动态校验，使用独立临时阻塞原因和恢复策略。
5. 完成静态、动态和未知区域测试后再实船启用。

## 7. 验收用例

至少覆盖：

- 点位在障碍内：返回 `WAYPOINT_IN_OBSTACLE`，不得降级为仅警告；
- 点位不在障碍内且距离分别为 1.99 m、2.00 m、2.01 m：验证近障阈值边界和独立错误码；
- 近障事件包含实际距离、阈值和正确 `index + seq`，默认不启动任务；
- 点位合法性数据不可用：返回 `WAYPOINT_VALIDITY_UNKNOWN`，不得放行；
- 静态障碍扩张后，目标点在硬禁区内：预规划失败，报告正确 `seq`，不启动任务；
- 点位合法但路径被完全阻断：报告航线不可达，不伪造某个点为非法；
- 多个非法点：逐一报告，不遗漏原始序号；
- 动态障碍进入局部地图：暂停或重规划，报告临时阻塞，`needs_waypoint_update=false`；
- 动态障碍消失：允许继续，无需修改任务点；
- 航点超出局部窗口：返回 `NOT_EVALUATED`，不误判；
- 局部地图过期、TF 失效、定位丢失：不得放行；
- 水雾/单帧噪点：不得立即拒绝；
- 静态扩张不影响局部 RPP 的独立碰撞保护。

## 8. 综合防护结论

“障碍内检查 + 2 m 近障检查 + 执行前预规划 + 局部实时障碍检测”可以拦截大多数明显
不合理的任务点，并减少船到障碍附近后才碰撞/受困的概率，但不能承诺覆盖所有情况。
地图与岸线误差、定位误差、传感器盲区、未知区域和动态障碍仍需由实时检测与状态机兜底。

2 m 只是初始阈值，不等于所有船体朝向下都安全。后续应根据实船碰撞恢复、可通行率和
平台误报情况调整，并保留按船型配置的能力。
