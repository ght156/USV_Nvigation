# 2026-10-12 服务类调用全部超时：客户端 RMW 与船端节点不一致（FastDDS ↔ CycloneDDS）

> 一句话：船端节点跑 `rmw_cyclonedds_cpp`（限 eth1），而 `ssh hkzl 'cmd'` 这类**非交互会话不读 `~/.bashrc`**，
> `ros2` / rclpy 落到默认 `rmw_fastrtps_cpp` → **话题能收、服务全部超时**（`ros2 param set` 表现为挂住、无任何输出）。
> 显式 `export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` 后立刻恢复。

## 2. 现象

1. `ros2 param set /local_costmap/local_costmap voxel_layer.enabled false` → **无输出、命令挂住**（只能 Ctrl-C 才回来）；
2. 换成 rclpy 直接调 `/local_costmap/local_costmap/set_parameters` → `NO_RESULT (timeout)`；
3. `get_parameters` 同样超时，而且**读一个不存在的参数也超时**（本该立刻回"未设置"）→ 排除"参数名写错"；
4. 同一会话、同一时刻 `ros2 topic echo --once /map`、`/kvmsbms_state`、`/livox/lidar` **全部正常**。

## 3. 证据

`ros2` CLI（非交互会话，无 RMW 环境）——挂住：

```text
$ ros2 param set /local_costmap/local_costmap voxel_layer.enabled false
（无输出，Ctrl-C 才返回）
```

rclpy 客户端（无 RMW 环境）——服务全部超时：

```text
get /local_costmap voxel_layer.enabled                  -> TIMEOUT (6s)
get /local_costmap __no_such_param__                    -> TIMEOUT (6s)     ← 读不存在的参数也超时 = 服务通路不通
get /controller_server FollowPath.*                     -> TIMEOUT (6s)
set /controller_server FollowPath.use_collision_detection=false -> TIMEOUT (6s)
```

补上 RMW=cyclonedds 后，同一个脚本立刻通：

```text
$ export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
get /local_costmap voxel_layer.enabled  -> value=ParameterValue(type=1, bool_value=True)
set /local_costmap/local_costmap voxel_layer.enabled=false -> successful=True
```

代价图读数印证"① 那刀其实没生效"（前后一字不差 = 静默失败）：

```text
改动前：W=240 H=240 cells>0=23460 lethal=1394 max=100
"改"完：W=240 H=240 cells>0=23460 lethal=1394 max=100
```

环境对照（船端 `~/.bashrc` 里有，但只有交互式 shell 会读）：

```bash
$ grep -nE "RMW_IMPLEMENTATION|ROS_DOMAIN_ID" ~/.bashrc
122:export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
123:export ROS_DOMAIN_ID=5
```

## 4. 根因（已确证）

- 船端节点由 `~/start_xingfei_stack.sh` 拉起，脚本里显式 `export ROS_DOMAIN_ID=5 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp`
  + `source .cyclone_env`（CycloneDDS 限 `eth1`）；
- `RMW_IMPLEMENTATION` 只写在 `~/.bashrc`（第 122 行）→ **只有交互式 shell 读得到**；
  `ssh hkzl 'cmd'`、脚本、cron 这些非交互会话拿到的是默认 `rmw_fastrtps_cpp`；
- 跨 RMW vendor 时 **pub/sub 走 DDS 线协议能互通**（所以 `ros2 topic echo` 正常），
  但 **ROS 2 service（含 `/get_parameters`、`/set_parameters`、`ros2 service call`、action 底层服务）请求/应答配不上对**，
  客户端一直等 → 超时；`ros2` CLI 连错误都不打印，看起来像"服务坏了 / 参数不支持在线改"。
- 顺带解释两处历史现象：调试文档 §2 记的"`ros2 CLI` 偶发卡死"、§7 记的
  "`ros2 service call` 清图偶发静默失败"——**都是这一个根因**，不是服务本身的问题。

## 5. 已做修改

- 无代码 / 配置改动（**没动** `~/.bashrc`，避免影响交互终端）。
- 固化规范：非交互会话里做服务类操作（`param set/get`、`service call`、action）前必须显式：

```bash
source ~/logs/xingfei_stack/.cyclone_env
export ROS_DOMAIN_ID=5 RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
source /opt/ros/humble/setup.bash && source ~/usv-main/install/arm/setup.bash
```
