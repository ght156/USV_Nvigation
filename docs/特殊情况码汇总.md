# 特殊情况码汇总

更新时间：2026-08-20

本文原名"故障码汇总"，后来发现里面越来越多条目本身不是故障（任务被新任务顶替、被遥控器接管、MQTT 断链缓存补传……），继续叫"故障码"名不副实，改名为**特殊情况码**：只要是"任务/链路没有按最简单的成功路径走完，需要一个稳定码让云平台/日志能识别具体发生了什么"，不管是不是真故障，都归在这里，用"是否故障"这一列区分。

本文统一记录 MQTT 控制指令、导航 Action、返坞 Action、无任务安全事件、设备健康状态和 MQTT 链路状态使用的结果码。相同情况在不同层只能按本表映射，不能直接把导航内部枚举值当作云平台故障码。

## 1. 编码分层

| 编码范围/形式 | 使用位置 | 表达的含义 |
|---|---|---|
| `0` | `services_reply.result`、任务终态码 | 命令已受理，或者任务最终成功；必须结合所在报文判断 |
| `1xxx` | `services_reply.data.common.result` | 云端控制命令是否被船端立即受理 |
| `2xxx` | `mission_state.failure_code`（项目扩展） | 已接受的普通导航任务为什么结束（含故障和非故障原因） |
| `21xx` | `mission_state.failure_code`（项目扩展） | 已接受的返回船坞任务为什么结束 |
| `22xx` | `mission_state.failure_code`（项目扩展） | 沿边清扫任务为什么结束（预留，算法未实现） |
| 字符串 `event_code` | `NavSafetyEvent` | 没有活动 Action 时发生的异步安全事件 |
| `3xxx/4xxx/5xxx` | `sensor_event.fault_code`、`sensor_state.fault_code` | RTK、水质、BMS 等设备健康故障 |
| `6xxx` | `sensor_event.fault_code` 或新增字段（待定） | MQTT 链路特殊情况：断链缓存、恢复补传、断链超时自动暂停 |

必须遵守：

- `services_reply.result=0` 对异步任务只表示"Goal 已受理"，不表示已经到点或返坞完成。
- 导航任务是否最终成功，只看 Action Result；Decision 再转换成 `mission_state`。
- Goal 在请求阶段被拒绝时，任务根本没有开始，使用 `1xxx` 即时受理码，不伪造 `mission_state=FAILED`。
- Goal 已经接受后发生故障，使用 Action Result，并映射为 `2xxx/21xx/22xx` 任务终态码。
- Action 内部 `RESULT_*` 的数值只在 ROS 接口内部使用，不直接上报云平台。
- `NavSafetyEvent.event_code` 是无任务异步事件，不填入 `sensor_event.fault_code`。
- `2xxx/21xx/22xx` 段里不是所有码都代表故障，必须看"是否故障"列；云端展示逻辑不能看到 `failure_code` 非 0 就一律显示成"设备故障"。

## 2. 控制指令即时返回码（`1xxx`）

| 码值 | 名称 | 含义 | 典型触发条件 |
|---:|---|---|---|
| `0` | `SUCCESS` | 命令成功或异步任务已受理 | Action Goal 被接受；暂停、恢复、取消请求被接受 |
| `1001` | `ERROR_INVALID_PARAM` | 参数错误 | 空航点数组、非法经纬度、缺少或非法预泊点、非法围栏数据 |
| `1002` | `ERROR_INVALID_URL` | URL 无效 | 推流、升级等 URL 校验失败，与导航任务无关 |
| `1003` | `ERROR_CONNECT_FAILED` | 连接失败 | 外部连接建立失败 |
| `1004` | `ERROR_DEVICE_BUSY` | 导航或设备忙 | 已有活动 Goal，新 Goal 被拒绝 |
| `1005` | `ERROR_DEVICE_OFFLINE` | 设备或下游节点离线 | 导航 Action Server、Service 或其他 ROS 下游不可用 |
| `1006` | `ERROR_UNSUPPORTED_METHOD` | 方法不支持 | 下发了船端未实现的方法 |
| `1007` | `ERROR_STATE_NOT_ALLOWED` | 当前状态不允许 | 导航未就绪、无可暂停任务、返坞安全阶段禁止暂停、Cancel 被拒绝 |
| `1008` | `ERROR_EXECUTION_TIMEOUT` | 即时调用超时 | 等待 Goal 接受、Service Response 或 Cancel 接受超时 |
| `1009` | `ERROR_ILLEGAL_MODE` | 发送了非法模式 | `set_mode` 不是 `HOLD` 或 `GUIDED` |
| `1999` | `ERROR_UNKNOWN` | 未知错误 | 无法归类的异常 |

### 2.1 导航 Goal 请求阶段映射

| 场景 | Action 是否开始 | 云端即时返回码 | 后续任务状态 |
|---|---:|---:|---|
| 航点数组为空 | 否 | `1001` | 不创建任务终态 |
| 航点经纬度、yaw 或 seq 非法 | 否 | `1001` | 不创建任务终态 |
| 返坞前没有有效预泊点 | 否 | `1001` | 不创建任务终态 |
| 围栏快照结构非法，导航无法开始 | 否 | `1001` | 不创建任务终态 |
| 已有活动导航或返坞 Goal | 否 | `1004` | 旧 Goal 保持不变 |
| Action Server 不存在或节点离线 | 否 | `1005` | 不创建任务终态 |
| 导航定位、规划器或控制器未就绪 | 否 | `1007` | 不创建任务终态 |
| 等待 Goal 接受超时 | 未确认 | `1008` | Decision 继续确认或尝试 Cancel，避免孤儿 Goal |
| Goal 被接受 | 是 | `0` | 最终结果等待 Action Result |

### 2.2 暂停、恢复和取消映射

| 操作结果 | 即时返回码 | 说明 |
|---|---:|---|
| 暂停成功 | `0` | Goal 保持活动，进入暂停状态 |
| 已经暂停，再次暂停 | `0` | 幂等成功 |
| 恢复成功 | `0` | 从原 Goal 上下文继续 |
| 已经运行，再次恢复 | `0` | 幂等成功 |
| 没有活动任务却请求暂停/恢复 | `1007` | 当前状态不允许 |
| 返坞安全阶段不允许暂停 | `1007` | 不改变当前返坞状态 |
| Cancel 请求被接受 | `0` | 最终等待 Action 返回 `CANCELED` |
| 当前无 Goal，再次 Cancel | `0` | 幂等成功 |
| Cancel 被导航拒绝 | `1007` | Decision 保持原任务上下文 |
| 暂停、恢复或 Cancel 接口不可用 | `1005` | 下游离线 |
| 等待响应超时 | `1008` | 不得擅自当作已暂停、已恢复或已取消 |

### 2.3 `1009 ERROR_ILLEGAL_MODE`

- 适用命令：`method="set_mode"`。
- 允许值：`mode=5`（`HOLD`）、`mode=15`（`GUIDED`）。
- 其他整数模式返回 `result=1009`、`message="发送了非法的模式"`。
- MQTT 桥不得向 `/decision/set_mode` 转发非法模式。

## 3. 导航任务终态码（`2xxx`）

以下码值用于已经接受的 `NavigateTask` 或 `ReturnDock`。云端任务阶段由 Decision 同时上报：成功为 `COMPLETED`，取消为 `CANCELLED`，其余执行故障为 `FAILED`。

### 3.1 通用导航任务码

| 码值 | 名称 | 是否故障 | 适用任务 | 触发条件 |
|---:|---|:---:|---|---|
| `0` | `TASK_SUCCESS` | 否 | 单点、无动作航线、返坞 | Action 最终成功；单点已到达并停车、航线全部完成或船坞已锁定 |
| `2001` | `MISSION_GEOFENCE_VIOLATION` | 是 | 单点、航线、返坞 | 活动 Action 执行中发生电子围栏越界，导航安全处置后以 `ABORTED` 结束 |
| `2002` | `MISSION_INVALID_GOAL` | 是 | 单点、航线 | Goal 已接受后才发现航点或任务数据非法；通常应在 Goal 请求阶段用 `1001` 拒绝 |
| `2003` | `MISSION_NAV_BUSY` | 是 | 单点、航线、返坞 | Goal 已接受后发现资源被其他任务占用；通常应在 Goal 请求阶段用 `1004` 拒绝 |
| `2004` | `MISSION_NAV_NOT_READY` | 是 | 单点、航线、返坞 | Goal 接受后导航运行条件失效，尚未开始有效运动 |
| `2005` | `MISSION_CANCELED` | 否 | 单点、航线、返坞 | Decision Cancel，导航安全停止后 Action 进入 `CANCELED` |
| `2006` | `MISSION_PLANNING_FAILED` | 是 | 单点、航线 | 无法生成到目标点的有效路径 |
| `2007` | `MISSION_CONTROLLER_FAILED` | 是 | 单点、航线 | 控制器故障、控制输出失败或持续无法跟踪轨迹 |
| `2008` | `MISSION_STUCK` | 是 | 单点、航线 | 恢复策略执行后仍无法脱困 |
| `2009` | `MISSION_LOCALIZATION_LOST` | 是 | 单点、航线、返坞 | 执行期间定位丢失，无法安全继续 |
| `2010` | `MISSION_EMERGENCY_STOP` | 是 | 单点、航线、返坞 | 执行期间触发急停，导航安全停止后终止任务 |
| `2011` | `MISSION_EXECUTION_TIMEOUT` | 是 | 单点、航线、返坞 | 超过约定任务超时或 Decision 判定 Action 长期无响应并完成取消/终止处理 |
| `2012` | `MISSION_SUPERSEDED` | 否 | 单点、航线、返坞 | 任务执行到一半，云平台下发了新的 `mission_execute`；Decision 判定新任务合法后对旧任务发起 Cancel，旧任务以此码结束，不算故障 |
| `2013` | `MISSION_RC_OVERRIDE` | 否 | 单点、航线、返坞 | 任务执行到一半，物理遥控器突然接管（判据见 `MavrosData::rcOverride()`，读 `/mavros/rc/in`）；Decision 对当前任务发起 Cancel，以此码结束 |
| `2099` | `MISSION_INTERNAL_ERROR` | 是 | 单点、航线、返坞 | 导航内部异常且无法归入其他稳定类别 |

`2005 MISSION_CANCELED`、`2012 MISSION_SUPERSEDED`、`2013 MISSION_RC_OVERRIDE` 都是任务终止原因，不属于故障。云端应上报 `phase=CANCELLED`，不应显示成设备故障。三者的区别只在"谁/什么原因让 Decision 发起了这次 Cancel"：

- `2005`：云平台或人工显式下发取消指令。
- `2012`：旧任务还在跑，被云平台下发的新任务顶替。
- `2013`：物理遥控器接管，人工优先于自动任务。

导航 Action 层只返回统一的 `RESULT_CANCELED`，分不清这三种原因；Decision 必须在发起 Cancel 前记下触发原因，Action 结束后按记下的原因选择 `2005`/`2012`/`2013` 中的一个上报，不能一律映射成 `2005`。

`2013 MISSION_RC_OVERRIDE` 除了终止当前任务，还需要单独向云平台上报一次"遥控器突然接管"事件（不只是任务终态码），当前上报哪个字段/哪个 method 还没定，对应 `decision和mqtt修改.md` §3.7.2 里"当前有无实体遥控器是否作为独立字段，等待云平台确认"这个待确认项；确认前 Decision 至少要先把 Action 正确取消并上报 `2013`，事件上报后续接上。

以上两个码目前只是预留：`MavrosData::rcOverride()` 已经实现但还没有被状态机调用，`mission_active_` 时收到新 `mission_execute` 目前是直接拒绝（`1007`），还没有"取消旧任务、接受新任务"的抢占逻辑；这两点都需要单独排期实现，不属于本次文档改动范围。

### 3.2 返回船坞专用码（`21xx`）

| 码值 | 名称 | 触发条件 |
|---:|---|---|
| `2101` | `DOCK_NOT_FOUND` | 已到达搜索/感知区域，但无法识别目标船坞 |
| `2102` | `DOCK_APPROACH_FAILED` | 船坞已识别，但对准、接近或最终进入过程失败 |
| `2103` | `DOCK_LOCK_FAILED` | 已进入锁定阶段，但卡扣未能锁定或未收到锁定成功确认 |

以下情况不新增返坞专用码，复用通用码：

- 围栏越界：`2001`。
- 导航未就绪：`2004`。
- 取消：`2005`。
- 定位丢失：`2009`。
- 急停：`2010`。
- 超时：`2011`。
- 内部异常：`2099`。

预泊点缺失或坐标非法应在发送 `ReturnDock` Goal 前发现，使用即时返回码 `1001`，不应先接受 Goal 再上报 `21xx`。

### 3.3 沿边清扫专用码（`22xx`，预留）

沿边清扫是沿河岸边缘巡线清理垃圾的任务模式，跟点到点航线的区别在于：全程依赖一个"贴着岸边走"的实时参照（岸线/边缘检测），而且执行期间要驱动清洁机构工作，两者任何一个失效都会让任务失去意义，即使定位、路径规划本身完全正常。据此预留以下码：

| 码值 | 名称 | 是否故障 | 触发条件 |
|---:|---|:---:|---|
| `2201` | `EDGE_TRACKING_LOST` | 是 | 持续跟丢岸线/边缘参照（植被遮挡、桥洞/涵洞遮挡、水位变化导致边界特征消失等），无法继续沿边 |
| `2202` | `EDGE_DISTANCE_VIOLATION` | 是 | 贴边距离超出预设安全范围（过近有搁浅/碰撞风险，过远清扫失效），且未能自动纠正 |
| `2203` | `CLEANING_MECHANISM_FAULT` | 是 | 清洁机构（毛刷/打捞装置）卡滞、堵转或长时间未收到工作状态确认 |
| `2204` | `EDGE_OBSTACLE_BLOCKED` | 是 | 贴边路径被障碍物阻挡（桥墩、系泊船只、密集水生植物、临时施工物等），无法绕行继续 |

以下情况不新增沿边专用码，复用通用码：

- 围栏越界：`2001`。
- 导航未就绪：`2004`。
- 取消：`2005`。
- 被新任务顶替：`2012`。
- 被遥控器抢占：`2013`。
- 定位丢失：`2009`。
- 急停：`2010`。
- 超时：`2011`。
- 内部异常：`2099`。

**这四个码目前是推演出来的预留项，不是已经实现的东西**：沿边清扫本身还没有算法（见 0813 会议"智能清扫：等算法做出来"），贴边参照用什么传感器、安全距离带具体多宽、"过近"和"过远"要不要拆成两个码、障碍物判定和普通导航的 `MISSION_STUCK(2008)` 怎么区分，这些都要等算法方案定下来后再核实调整，不是这次凭空定死的最终版本。

## 4. Action Result 到任务码的映射

### 4.1 `NavigateTask` 映射

| Action 状态 | Action Result | Decision 任务码 | 云端阶段 |
|---|---|---:|---|
| `SUCCEEDED` | `RESULT_SUCCESS` | `0` | `COMPLETED` |
| `ABORTED` | `RESULT_INVALID_GOAL` | `2002` | `FAILED` |
| `ABORTED` | `RESULT_BUSY` | `2003` | `FAILED` |
| `ABORTED` | `RESULT_NOT_READY` | `2004` | `FAILED` |
| `CANCELED` | `RESULT_CANCELED` | `2005`/`2012`/`2013` | `CANCELLED` |
| `ABORTED` | `RESULT_PLANNING_FAILED` | `2006` | `FAILED` |
| `ABORTED` | `RESULT_CONTROLLER_FAILED` | `2007` | `FAILED` |
| `ABORTED` | `RESULT_STUCK` | `2008` | `FAILED` |
| `ABORTED` | `RESULT_LOCALIZATION_LOST` | `2009` | `FAILED` |
| `ABORTED` | `RESULT_GEOFENCE_VIOLATION` | `2001` | `FAILED` |
| `ABORTED` | `RESULT_EMERGENCY_STOP` | `2010` | `FAILED` |
| `ABORTED` | `RESULT_INTERNAL_ERROR` | `2099` | `FAILED` |

`2011 MISSION_EXECUTION_TIMEOUT` 通常由 Decision 的任务监控产生：Decision 先尝试 Cancel，并在确认任务无法正常完成后上报超时，不能仅因某一帧 Feedback 缺失就立即判超时。

`RESULT_CANCELED` 对应 `2005`/`2012`/`2013` 中的哪一个，取决于 Decision 发起这次 Cancel 的原因（见 §3.1 后的说明），不是 Action Result 本身能区分的，Decision 必须在调用 Cancel 之前就记下原因。

### 4.2 `ReturnDock` 映射

| Action 状态 | Action Result | Decision 任务码 | 云端阶段 |
|---|---|---:|---|
| `SUCCEEDED` | `RESULT_SUCCESS` | `0` | `COMPLETED` |
| `ABORTED` | `RESULT_BUSY` | `2003` | `FAILED` |
| `ABORTED` | `RESULT_NOT_READY` | `2004` | `FAILED` |
| `CANCELED` | `RESULT_CANCELED` | `2005` | `CANCELLED` |
| `ABORTED` | `RESULT_DOCK_NOT_FOUND` | `2101` | `FAILED` |
| `ABORTED` | `RESULT_APPROACH_FAILED` | `2102` | `FAILED` |
| `ABORTED` | `RESULT_LOCK_FAILED` | `2103` | `FAILED` |
| `ABORTED` | `RESULT_GEOFENCE_VIOLATION` | `2001` | `FAILED` |
| `ABORTED` | `RESULT_EMERGENCY_STOP` | `2010` | `FAILED` |
| `ABORTED` | `RESULT_INTERNAL_ERROR` | `2099` | `FAILED` |

返坞 Action 不要求进度百分比。Goal 接受立即响应，最终 Result 可以在较长时间后返回；没有 Feedback 进度不能单独判定为失败。

## 5. 无活动任务时的突发安全事件

没有活动 Action 时无法返回 Action Result，导航通过 `/mission_bridge/safety_event` 发布 `m_common/msg/NavSafetyEvent`。

### 5.1 已确认事件码

| `event_code` | 触发条件 | Decision 行为 | 是否上报任务故障码 |
|---|---|---|:---:|
| `GEOFENCE_VIOLATION` | 没有活动 Action 时进入禁航区或驶出作业区 | 转换为云平台 `geo_fence_alert(enabled=true)` | 否 |
| `GEOFENCE_VIOLATION` 且 `enabled=false` | 船回到允许区域 | 转换为云平台 `geo_fence_alert(enabled=false)` | 否 |

规则：

- 无活动任务时不能伪造 `mission_state=FAILED`，也不使用 `2001`。
- 有活动任务时围栏越界通过当前 Action Result 上报，不要求导航再重复发布同一 `NavSafetyEvent`。
- Topic 事件不能结束一个活动 Action。
- 相同围栏状态持续期间不得高频重复发布，触发和解除应做边沿去重。

### 5.2 其他突发事件的处理原则

急停、定位丢失、控制器故障等事件：

- 有活动 Action：必须结束当前 Action，并分别使用 `2010`、`2009`、`2007` 等任务故障码。
- 没有活动 Action：通过 `/nav_status` 反映持续状态；如果还需要事件式告警，再为 `NavSafetyEvent` 增加稳定的字符串 `event_code`，经导航与 Decision 联调确认后登记到本表。
- 未登记的 `event_code` 不得直接上云，避免云平台无法区分事件含义。

## 6. 云平台任务状态上报规则

当前 V0.6 `mission_state` 已有 `phase` 和 `failure_message`，尚未正式定义数值型 `failure_code`。需要云平台确认并增加项目扩展字段：

```text
int32 failure_code
```

建议规则：

| `mission_state.phase` | `failure_code` | `failure_message` |
|---|---:|---|
| `RUNNING` / `PAUSED` | `0` | `null` |
| `COMPLETED` | `0` | `null` |
| `CANCELLED` | `0` | 可写取消原因；内部终止原因仍记录为 `2005` |
| `FAILED` | 对应 `2xxx/21xx` | 必须填写可读的失败说明 |

云平台未确认 `failure_code` 字段前，Decision 仍应在内部保存稳定任务码并通过 `failure_message` 上报文字原因，但不能声称云平台已经识别该数值码。

## 7. 设备健康故障码

设备健康故障码与导航任务码相互独立。

| 码值 | 代码常量 | 故障 | 上报位置 |
|---:|---|---|---|
| `3001` | `kFaultRtkOffline` | RTK 离线 | `sensor_event` / `sensor_state` |
| `4001` | `kFaultWaterQualityOffline` | 水质传感器离线 | `sensor_event` / `sensor_state` |
| `5001` | `kFaultBatteryOffline` | BMS 离线 | `sensor_event` / `sensor_state` |
| `5002` | `kFaultBatteryProtection` | BMS 保护位非零 | `sensor_event` / `sensor_state` |

设备故障采用状态翻转上报：同一 `(type, fault_code)` 故障持续期间只产生一次故障事件，恢复时复用对应的 `alarm_id`。

例如 RTK 离线导致活动导航任务定位丢失时，应同时表达两个不同事实：

- 设备健康：`sensor_event.fault_code=3001`。
- 当前导航任务失败：Action Result 为 `RESULT_LOCALIZATION_LOST`，Decision 映射任务故障码 `2009`。

两者不能互相替代。

## 8. MQTT 链路特殊情况码（`6xxx`）

MQTT 跟云平台断链、期间缓存数据、重连后补传，这套行为本身（见 `decision和mqtt修改.md` §3.4：`MqttBridgeV2Node::caching_active_`/`pending_uplink_queue_`/`drain_pending_uplinks`/`check_disconnect_stop_timeout`）不是设备故障，也不是任务故障，是独立于两者之外的第三种情况——链路层面的特殊情况，所以单开一段编码。

| 码值 | 名称 | 是否故障 | 触发条件 |
|---:|---|:---:|---|
| `6001` | `MQTT_LINK_LOST` | 否 | Paho `connection_lost` 触发，进入本地缓存模式（`caching_active_=true`），船上任务继续正常执行 |
| `6002` | `MQTT_LINK_RESTORED` | 否 | Paho 重连成功，缓存队列已按时间顺序补传完毕，退出缓存模式（`caching_active_=false`） |
| `6003` | `MQTT_DISCONNECT_AUTO_PAUSE` | 是 | 断链持续超过 `mqtt_disconnect_stop_timeout_sec_`（默认 600s）仍未恢复，已对当前航线任务发起 `mission_control(pause)` |

`6001`/`6002` 本身不是故障（断线重连是正常的容错行为），但 `6003` 意味着有一个任务被迫卡在 `PAUSED`、需要人工关注，所以标成"是"，跟前两个区分开。

**当前实现状态（跟前面 2012/2013 一样是预留）**：`on_mqtt_disconnected()`/`on_mqtt_connected()`/`check_disconnect_stop_timeout()` 现在只有 `MLOGGER_INFO/WARN/ERROR` 本地日志，并没有把这三个情况实际发一条 `sensor_event` 或其它报文上报云平台——只是把断链期间产生的业务数据（`mission_state`/`alarm_state`/`sensor_event`/水质）缓存补传了，链路状态变化这件事本身目前云平台看不到。要把 `6001/6002/6003` 真正用起来，还需要：

1. 复用 `publish_sensor_event_transition()` 同样的边沿上报机制（`type="MQTT_LINK"`），在 `on_mqtt_disconnected`/`on_mqtt_connected` 里各加一次调用；但断链期间报文本身发不出去，只能在重连后补报"曾经断过"，这条不受"暂停原因"网络本身影响；
2. `6003` 触发时受影响任务的 `mission_state.phase=PAUSED`，但 §6 的 `failure_message` 目前文档上只覆盖 `FAILED` 阶段；要不要在 `PAUSED` 时也复用 `failure_message` 说明"因 MQTT 断链自动暂停"，还是云平台要单独的暂停原因字段，需要云平台确认，属于跟 §6 一样的待定项。

## 9. 实现时需要集中定义的常量

建议在公共协议头文件或 Decision 的任务结果映射模块中集中定义以下任务码，禁止各回调直接写裸数字：

```text
TASK_SUCCESS                     = 0
MISSION_GEOFENCE_VIOLATION       = 2001
MISSION_INVALID_GOAL             = 2002
MISSION_NAV_BUSY                 = 2003
MISSION_NAV_NOT_READY            = 2004
MISSION_CANCELED                 = 2005
MISSION_PLANNING_FAILED          = 2006
MISSION_CONTROLLER_FAILED        = 2007
MISSION_STUCK                    = 2008
MISSION_LOCALIZATION_LOST        = 2009
MISSION_EMERGENCY_STOP           = 2010
MISSION_EXECUTION_TIMEOUT        = 2011
MISSION_SUPERSEDED               = 2012
MISSION_RC_OVERRIDE              = 2013
MISSION_INTERNAL_ERROR           = 2099
DOCK_NOT_FOUND                   = 2101
DOCK_APPROACH_FAILED             = 2102
DOCK_LOCK_FAILED                 = 2103
EDGE_TRACKING_LOST               = 2201
EDGE_DISTANCE_VIOLATION          = 2202
CLEANING_MECHANISM_FAULT         = 2203

```

Action Server 只返回自己的 `RESULT_*`；Decision 负责在一个统一映射函数中转换成上述任务码，MQTT 桥只负责按云协议发布，不应重新猜测导航错误原因。

MQTT 链路特殊情况码（`sensor_event.fault_code` 复用同一常量风格）：

```text

MQTT_DISCONNECT_AUTO_PAUSE       = 6003
```
