## 3. RS485 驱动包（夹爪 / 背光板）

包路径：`~/usv-main/src/usv_rs485_driver`

统一管理 RS485 总线上的设备：水质传感器、BMS、IO 控制器、无线充电器等。
夹爪和背光板都挂在 **IO 控制器**（Modbus RTU，从站地址 64）的 DO 输出上。

当前通信方式（`config/usv_rs485_config.yaml`）：TCP → `192.168.2.111:18223`（串口服务器），非直连串口。

注意：整船启动时该节点可能由 `usv_app/launch/cleaning_boat.launch.py` 拉起；
`mqtt_bridgev2.launch.py` 若带 `start_rs485_driver:=true` 会在 `/mqtt` 命名空间下再起一份
（服务/话题带 `/mqtt` 前缀），两处同时起会抢总线，调试时确认只有一份在跑。

### DO 通道映射（2026-09-30 实物验证）

| 位（掩码） | 硬件 | 控制逻辑 |
| --- | --- | --- |
| bit0（`0x0001`） | 夹爪电机线圈 | ControlDO 闭合，电机动作 ~3s |
| bit1（`0x0002`） | 背光板 | ControlDO 随夹爪同开；WaitIO 期间保持；WaitIO 结束/取消/失败随夹爪同关（驱动日志里叫 "DO2"，1 基命名） |
| bit2（`0x0004`） | 无线充电启停 | WaitIO 成功后 BMS RSOC 自动控制（日志里叫 "DO3"）；ControlDO 后停止自动控制但不断电 |

注意：`set_do` 写的是 **16 位全掩码**，不是单 bit 操作——`{digital_output: 2}` 会把
bit1 置位、其余全部清零。想保留其他通道状态时，先读当前 DO 再按位或：

```bash
ros2 topic echo /io_state    # digital_output 字段即当前 DO 掩码，按位或后再写回
```

2026-09-30 起驱动行为（船端已打补丁，见
`bug_debug/2026-09-30_RS485驱动DO定时关闭误伤背光与无线充电.md`）：
归港途中夹爪+背光保持不断电；WaitIO 结束（抓住/取消/失败）才一并断电；
10 分钟兜底仅断 DO0/DO1，无线充电全程不被定时器误关。

## 4. 打开命令

### 4.1 打开夹爪（ControlDO Action）

```bash
ros2 action send_goal /control_do \
    usv_rs485_driver/action/ControlDO \
    "{start: true}"
```

- 闭合 DO0+DO1，电机动作约 3 秒后返回成功
- 60 秒后驱动自动断开 DO（`kDOAutoCloseDelayMs`），属正常行为
- 归港 FSM（usv_docking）中 `dock_claw_enabled=true` 时，WAIT_DOCK_OPEN / WAIT_DOCK_RELEASE 状态就是调这个 Action

### 4.2 打开背光板（SetDO Service）

```bash
ros2 service call /set_do \
    usv_rs485_driver/srv/SetDO \
    "{digital_output: 2}"
```

关闭背光板：

```bash
ros2 service call /set_do \
    usv_rs485_driver/srv/SetDO \
    "{digital_output: 0}"
```

注意：`set_do` 写的是 **16 位全掩码**，不是单 bit 操作——`digital_output: 2` 会把
DO2 置位、其余全部清零。想保留其他通道状态时，先读当前 DO 再按位或：

```bash
ros2 topic echo /io_state    # digital_output 字段即当前 DO 掩码，按位或后再写回
```

### 4.3 其他常用接口

```bash
ros2 topic echo /io_state           # DI/DO 实时状态（16 位位掩码）
ros2 topic echo /water_quality      # 水质数据
ros2 topic echo /ttbms_state        # 铁塔 BMS
ros2 topic echo /wireless_charger_state  # 无线充电器（需先开监测）

# 等待停泊到位检测（WaitIO Action，期间会自动打开 DO2 背光板）
ros2 action send_goal /wait_io \
    usv_rs485_driver/action/WaitIO \
    "{max_queries: 0}"              # 0 = 用 yaml 默认 3000 次

# 无线充电器状态监测开关
ros2 service call /wireless_charger_monitor \
    usv_rs485_driver/srv/WirelessChargerMonitor "{enable: true}"
```

### 4.4 触发 / 取消归港（dock_mission 契约）

```bash
# 仅归港（dock_only：不做 Nav2 预泊导航，直接 /dock/start，现场调试用这个）
ros2 topic pub --once /gcs_dock/command std_msgs/msg/String \
    '{data: "{\"action\": \"dock_only\"}"}'

# 一键归港（one_click：先 Nav2 巡航到预泊点再归港；
# 需要 mission_bridge/Nav2 在跑，否则报 send_waypoints service unavailable）
ros2 service call /dock/mission/start std_srvs/srv/Trigger

# 取消（任务卡住/busy 时先取消再重发）
ros2 service call /dock/mission/cancel std_srvs/srv/Trigger

# 出泊
ros2 topic pub --once /gcs_dock/command std_msgs/msg/String \
    '{data: "{\"action\": \"undock\"}"}'
```

观察：

```bash
ros2 topic echo /docking/state        # FSM 状态（仅跳变时新值；夹爪模式先 WAIT_DOCK_OPEN 再 ACQUIRE_TAG）
ros2 topic echo --once /dock/status   # dock_mission 状态 JSON
ros2 topic echo --once /docking/tag_visible   # 二维码是否可见（触发前提）
ros2 topic echo --once /docking/pose_source   # VISION/ODOM_PREDICTION/INVALID
```

注意：

- `/dock/mission/start`（one_click）失败后 dock_mission 可能卡在
  `NAV_TO_STAGING`（日志 `busy in NAV_TO_STAGING`），先 `/dock/mission/cancel` 再重发。
- 夹爪打开（ControlDO）首次失败会自动重试（总线偶发超时），重试成功才进 ACQUIRE_TAG；
  持续失败查 rs485 日志 `~/logs/xingfei_stack/rs485.log`。
- ACQUIRE_TAG 搜索超时 `acquire_timeout_sec: 60s`，搜不到 tag 任务结束回 IDLE。

### 4.5 相机曝光（夜间/逆光检测 tag；2026-10-07 更新）

**现象**：夜间开背光板后，后视相机自动曝光把整个面板拉成均匀白块，二维码图案被洗掉，
`objects: []` 检测不到（白天同位置双 tag 稳定）。**位置/角度没问题，是过曝**。

**✅ 当前推荐方法：`~/bridge_calib/cam_backlight_mode.sh`**（仓库 `scripts/bridge_calib/`）

```bash
~/bridge_calib/cam_backlight_mode.sh          # 无参：显示当前曝光/gain（会打印找到的设备）
~/bridge_calib/cam_backlight_mode.sh on 50    # 切手动 + 短曝光（背光板点亮时用；值可省，默认 50）
~/bridge_calib/cam_backlight_mode.sh on 100   # 白天/弱背光：留环境光余量
~/bridge_calib/cam_backlight_mode.sh off      # 恢复自动曝光（默认安全态）
```

**为什么不用旧方法**（本节曾写 `python3 ~/v4l2_ctrl.py set exposure_auto 1` 那套）：

| 旧方法的问题 | 说明 |
|---|---|
| **设备号写死** | `~/v4l2_ctrl.py` 内 `DEV = "/dev/video0"`，而后视相机现在已漂到 **/dev/video8**（Orbbec 深度相机占 video0~7）。写死 = 改到**别的相机**上或直接失败，后视相机根本没人管 |
| 必须先切手动 | `exposure_auto=3(自动)` 时直接写 `exposure_absolute` 报 EACCES —— 这点新旧脚本都一样 |

`cam_backlight_mode.sh` 按 `/sys/class/video4linux/video*/name` 里的 **"USB Camera"** 自动找设备
（2026-10-06 起），重启后设备号漂移也不怕。

**按光照选值**（2026-10-07 实测补充）：

| 场景 | 设置 | 说明 |
|---|---|---|
| 白天、背光关 | `off`（自动）或 `on 80`~`on 100` | 自动足够；要稳可手动留余量 |
| 逆光 / 傍晚 / **夜间且背光板点亮** | **`on 50`** | 黑底亮 tag、抗过曝，实测检出 100% |
| **夜间、背光没开** | ⚠️ **手动短曝光 = 全黑** | 2026-10-07 18:19 实测：夜里不开背光时 `on 50` / `on 100` 抓帧只剩几个灯点（36 KB 帧），`off`（自动）才有 122 KB 的环境轮廓。**夜间要检测 tag 必须先点亮船坞背光板**，单靠调曝光救不回来 |

**验证**：`python3 ~/grab_frame.py` 抓一帧肉眼确认；或 `ros2 topic echo --once /docking/tag_visible`。

**背光亮度**：RS485 驱动侧 DO 只有开关（Modbus 线圈，无 PWM/调光接口），
亮度调节只能看硬件侧（灯箱驱动是否有调光旋钮），软件无法调。

注意：

- v4l2 设置是**临时的**：相机/节点重启或重新插拔后恢复自动曝光，夜间测试前需重设。
- 白天用手动曝光 50 会全黑，**白天务必 `off` 恢复自动**。
- 长期方案：给 video_camera 节点加曝光参数支持，或在 perception launch 里固化
  v4l2 设置（最好按白天/夜间分两档）。

## 5. 与归港算法（usv_docking）的接口对应

已核对（2026-09-30）：本地与船端 `docking_fsm.py`、`docking.yaml` 完全一致，接口匹配，无需改代码。

| 归港 FSM 侧 | 驱动侧 | 说明 |
| --- | --- | --- |
| `control_do_action: "control_do"` | `/control_do` Action | WAIT_DOCK_OPEN / WAIT_DOCK_RELEASE 发 `{start: true}` → DO0+DO1 开夹爪 |
| `wait_io_action: "wait_io"` | `/wait_io` Action | BACK_IN/FINAL_DOCK 发 `{max_queries: 0}` 等夹爪抓住；期间驱动自动开 DO2 背光板 |
| `dock_claw_enabled: true` | — | 兴飞船坞带夹爪，保持 true |

两侧节点都在根命名空间，相对名解析到 `/control_do`、`/wait_io`，对得上。
驱动侧 WaitIO 成功判定掩码 `io_wait_input_mask` 默认 `0x0003`（DI0+DI1 同时置位），
需现场确认夹爪"已抓住"两个检测开关接的就是 DI0/DI1。

## 6. 远程可视化（4G + Foxglove，无网线/图传时用）

国庆远程调试方案：船端跑 foxglove_bridge（单 websocket、按需订阅），
笔记本 Foxglove Studio 经 4G 隧道连接，替代 RViz。
**带宽只取决于订阅了什么**——只订 Path/Marker/TF 约 30~80 KB/s；点云、
costmap、相机话题一订就卡死，不要加。

### 6.1 船端一次性准备（连上船后执行）

```bash
# 1) 确认已安装（澄丰船用过，兴飞这台还没装过，先查）
ros2 pkg prefix foxglove_bridge || sudo apt install ros-humble-foxglove-bridge

# 2) 4G 是 CGNAT 无公网 IP，端口映射无效。船和笔记本都装 Tailscale/ZeroTier
#    组虚拟网（ssh 也靠它），或用 frp 透传 8765/22 到公网服务器
```

### 6.2 船端启动（白名单限流）

```bash
source /opt/ros/humble/setup.bash
ros2 launch foxglove_bridge foxglove_bridge_launch.xml port:=8765 \
  topic_whitelist:="['/tf','/tf_static','/local_plan','/transformed_global_plan','/received_global_plan','/plan','/lookahead_point','/lookahead_collision_arc','/cmd_vel_nav','/docking/*','/collision_points_marker']"
```

参数名已在主机同版本包（/opt/ros/humble/share/foxglove_bridge/launch）核实。

### 6.3 笔记本侧

1. `foxglove-studio` → Open connection → `ws://<船虚拟IP>:8765`
2. 导入布局：`scripts/foxglove_rpp_4g_layout.json`（主机侧已备好，含
   /local_plan、/transformed_global_plan、/plan、/lookahead_point + /cmd_vel_nav）
3. 3D 面板固定坐标系选 `odom`（4G 抖动时比 map 稳）

RPP 观察要点：`/lookahead_collision_arc`（红）是 RPP 每个控制周期按当前速度
前推到前瞻点、逐点做 footprint 碰撞检查的那段弧（use_collision_detection 输出），
碰撞前会压速到 0；`/local_plan`（绿）是裁剪后正在跟踪的全局路径段，两者直线段
看着像但不是一回事；前瞻点看 `/lookahead_point`。arc 末端若顶到局部 costmap
窗口边缘会越界误判碰撞（见 bug_debug/2026-09-21）。
偶尔要看 costmap 就在船端
`ros2 run topic_tools throttle messages /local_costmap/costmap 0.2 /local_costmap_slow`
再订这个 0.2 Hz 的。

## 8. 注意事项

- 所有 RS485 设备共享同一条半双工总线，由 `RS485Manager` 串行化访问，不要绕过节点直接操作串口。
- WaitIO / ControlDO 运行期间会覆盖手动设置的 DO2 / DO0+DO1 状态，手动调试时先确认没有归港任务在跑。
- 完整协议与消息定义见船端 `~/usv-main/src/usv_rs485_driver/README.md`。
