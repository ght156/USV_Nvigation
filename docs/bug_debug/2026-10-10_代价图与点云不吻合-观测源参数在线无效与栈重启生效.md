# 2026-10-10 代价图与点云不吻合：观测源参数在线修改无效（phantom 参数）+ 重启生效全记录

承接 2026-10-09 "mark_threshold 主闸门"结论（§6.7⑥）。昨天在线改 `obstacle_max_range 15→18`
后"效果有限"，今天（10-10）上船实测定因，结论如下。

## 根因：观测源级参数在 Nav2 humble 里不支持在线修改

船上为 `ros-humble-nav2-costmap-2d 1.1.20`（apt 二进制）。源码核对（humble 分支）：

- `ObstacleLayer::onInitialize()` 用**启动时的参数值**构造 `ObservationBuffer`
  （`obstacle_max_range` / `obstacle_min_range` / `raytrace_max_range` / `min|max_obstacle_height`（源级）
  都是构造函数参数），之后**没有任何动态参数回调更新它们**；
- `marking` / `clearing` 只在 `onInitialize()` 决定该 buffer 是否进
  `marking_buffers_` / `clearing_buffers_` 列表，之后在线改无效；
- `ObstacleLayer::dynamicParametersCallback` 只处理 `enabled` /
  `footprint_clearing_enabled` / `min|max_obstacle_height`（层级）/ `combination_method`；
- `VoxelLayer::dynamicParametersCallback` 处理 `mark_threshold` / `max_obstacle_height`（层级）/
  `origin_z` / `z_resolution` / `z_voxels` / `unknown_threshold` / `combination_method` / `enabled` 等；
- **关键坑**：`ros2 param set` 对观测源参数照样返回 `Set parameter successful`，
  `ros2 param get` 也能读到新值——参数服务器变了，但缓冲区行为没变（**phantom 参数**）。

**时间线实锤**：栈 2026-10-09 **16:48:18** 启动，yaml 当天 **18:38** 才改 15→18
→ 运行中的缓冲区一直是 **15.0/16.0**，`param get` 显示的 18.0 是昨天在线 set 留下的假值。

**实测吻合**：重启前 `compare 5` 中"点云有、代价图没标"的格子最远只有 **14.07 m**
（15~30 m 的岸每帧 ~900 点全被丢），证明生效值确实是 15 而非 18。

| 参数 | 在线改是否生效 |
|---|---|
| `voxel_layer.mark_threshold` | ✅ 生效（昨天 281→1230 全是它的功劳） |
| `voxel_layer.max_obstacle_height`（层级） | ✅ 生效 |
| `voxel_layer.footprint_clearing_enabled` | ✅ 生效 |
| `voxel_layer.livox_cloud.obstacle_max_range` / `raytrace_max_range` | ❌ **phantom**，需重启 |
| `voxel_layer.livox_cloud.marking` / `clearing` | ❌ **phantom**，需重启 |
| `voxel_layer.livox_cloud.min|max_obstacle_height`（源级） | ❌ **phantom**，需重启 |

### 时钟三轨补充更正（代码+逐包龄期实测）

- livox：雷达硬件 GPS 钟原样透传（livox_ros_driver2 `pub_handler.cpp` GPS 类型包直接 `return time.stamp`），
  超前系统钟 +0.48s，逐包精确；
- GI320 驱动：代码用报文 UTC 字段 `utcToUnix` 回填 stamp（GPS 钟，方向正确），**但**戳是"解算时刻"
  （INS 1~2Hz 更新、0.1s 量化、50Hz 重发同一戳）→ 实测龄期 0~0.5s 抖动，并非精确逐包时间；
- 系统钟：chrony 的 PPS/SHM(GPS) refclock 从未收到数据，实际走 4G NTP，慢 GPS 0.46s；
- mavros/LIO/TF：全部系统钟（mavros gps_input 转发时即丢失 GPS 戳）。

### 时钟问题二次更正（2026-10-10 晚，读代码后）

前文"mavros/LIO/TF 全部系统钟"**有误**。代码核实：mavros gps_input 是项目定制插件，
`odom.header.stamp = inspvaa_msg->stamp`（接力 GI320 戳），usv_map_odom_tf 也有 stamp_topic 接力
——**定位链全程用 GI320 的 GPS 解算时刻戳，不是主机钟**。实测它们数值≈系统钟纯属巧合
（GI320 解算滞后 ~0.45s ≈ 主机 NTP 偏差 ~0.46s）。
真正的时间差是 **livox（GPS 真时）比 TF（GI320 解算时刻）快 ~0.5s**：TF 滤波器需排队 ~0.5s
对齐，缓存重置/队列溢出时丢帧（STVL 被饿死的机制）。主机钟只影响日志/相机等主机打戳数据。
治理方向修正为：① 减小 GI320 解算戳滞后对 TF 对齐的影响（transform_tolerance、或 TF 改到码戳）；
② 主机 GPS 授时仍值得做（相机/日志/跨机对齐），但不再是为 TF 链。

### 时钟问题最终结论（2026-10-10 晚，第三方基准裁决 + 点级原始时间戳）

**前文"主机钟慢 0.46s"和"GI320 解算滞后 0.45s"均被推翻**，最终实测：

| 时钟 | 相对真时 | 证据 |
|---|---|---|
| 主机系统钟 | **准（±30ms）** | NTP 双源互证：aliyun −2~+16ms、pool.ntp.org −4~−34ms（自写 NTP 客户端四时间戳法） |
| GI320 报文时间 | 准（滞后 ~70ms） | GNGGA 龄期实测 +0.070s 稳定（12 条） |
| **livox 雷达钟** | **快 0.47~0.57s** ❗ | 点级原始时间戳实测：首点龄期 −0.475s、末点 −0.575s（帧内 100ms 跨度），帧头戳=首点戳 |

要点：
- 雷达把"物理上还没发生的时刻"写进了已发出的包（末点戳在收到时刻之后 0.575s）→ **雷达钟本身快，不是驱动打戳约定问题**（驱动 `pkg.base_time` 原样透传，代码已核）；
- Livox Viewer 的 `Time Offset: -6μs` 只表示雷达紧跟它的同步**输入源**，不代表等于 UTC 真时——
  要查雷达 GPS 同步的输入：GPRMC/PPS 从哪来（GI320 转出？）、时间标签和 PPS 沿的配对是否错了半秒；
- 现场快速验证：Livox Viewer 的 Local Time 与手机真时同屏对比拍照，快 ~0.5s 即实锤；
- 处置：① 查/修雷达同步输入（治本，需上船查线）；② 或 livox 不走 GPS 同步、驱动回退主机钟打戳
  （`GetEthPacketTimestamp` 对非 GPS/PTP 包有 fallback，待验证）——主机钟现在准，此路可统一全船时间；
  ③ 或在 costmap 侧把 `transform_tolerance` 提到 0.8s 容忍（治标）。

**另：livox 驱动多实例坑**——反复手动重启只按节点二进制名 pkill，launch 壳进程会残留累积
（最多时 3 个实例并存抢雷达，数据流直接断）。正确清理：`pkill -9 -f livox_ros_driver2` 后
确认 `pgrep -c -f livox_ros_driver2` 为 0 再重启。

### 给同事的测量方法说明（可截图）

原理：ROS 消息 `header.stamp` 是发布方写入的"出生时刻"，在船上订阅话题逐条算
`龄期 = 收到那一刻的主机系统时间 − stamp`；龄期为负 = 发布方的钟比主机快。雷达点级时间戳
（每个点自带的硬件时间）同理直接读 PointCloud2 的 `timestamp` 字段。NTP 校验用自写 UDP
客户端按协议四时间戳公式 offset=((t2−t1)+(t3−t4))/2 计算。
