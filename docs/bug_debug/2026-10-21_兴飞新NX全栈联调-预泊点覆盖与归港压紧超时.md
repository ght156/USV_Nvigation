### 2.7 mission_bridge 在任务失败后崩溃，导致后续归港 service unavailable

一次导航任务因旧预泊点落在障碍层失败：

```text
Starting point in lethal space
Planning algorithm GridBased failed to generate a valid path to (245.28, 155.71)
MISSION FAILED
```

失败收尾后 `mission_bridge` 崩溃：

```text
rclpy._rclpy_pybind11.InvalidHandle:
cannot use Destroyable because destruction was requested
```

随后一键归港连续重试，`dock_mission` 均报：

```text
send_waypoints service unavailable
```

最终 `DOCK_FAILED`，船没有开始预泊导航。

代码证据：`_on_nav_fatal()` 在 ROS 回调内直接执行
`self.destroy_subscription(self._odom_sub)`，随后多线程执行器再次访问已销毁实体。
该路径与异常高度吻合，但尚需最小复现确认；当前属于**未完成修复项**。

### 2.8 新预泊点生效后进入精靠泊，压紧段超时

重启全栈并加载新归港代码后，`dock_mission` 日志确认使用船端新点：

```text
Nav2 staging goal sent gnss=(31.4873086, 120.3691938)
yaw_deg=26.40
```

精靠泊阶段正常经过：

```text
ACQUIRE_TAG -> APPROACH_ENTRY -> ALIGN_ENTRY -> BACK_IN -> FINAL_DOCK
```

进入 `FINAL_DOCK` 后，FSM 按设计继续低速倒车压紧，等待 WaitIO 夹爪成功信号。

日志先收到：

```text
WaitIO feedback：夹爪 DI 置位 0x0002
```

但 WaitIO 最终成功条件要求两个夹爪检测位同时置位：

```text
0x0003 = bit0 + bit1
```

本次始终只看到 `bit1`，未收到完整的 `0x0003`。达到
`final_push_time_sec=15.0` 后报：

```text
FINAL_PUSH_TIMEOUT
FAILED: FINAL_PUSH_TIMEOUT
```

FSM 在夹爪已有部分置位后禁止驶出重试，就地停车，随后任务取消并回 `IDLE`。

## 3. 根因归纳

已确证：

1. 地图工具 datum 失败是本地工具默认 CycloneDDS，NX 使用 FastDDS。
2. 状态机旧 `nav_dock_*` 参数可以覆盖船端 bay2 预泊点。
3. `mission_type=3` 的云端唯一航点也会作为预泊点覆盖。
4. `mission_bridge` 崩溃后，后续一键归港必然因
   `/mission_bridge/send_waypoints` 不在线而失败。
5. 本次精靠泊进坞后继续倒退是 `FINAL_DOCK` 压紧段设计，不是停车逻辑失效。
6. 本次压紧失败是没有收到 `0x0003` 完整夹爪成功信号。

待验证：

1. `mission_bridge` 的 `InvalidHandle` 是否由失败回调内销毁 odom subscription
   单项触发。
2. 夹爪 DI0 是接线/机械未到位，还是压紧时间不足。

## 4. 当前安全策略

- 归港默认只使用船端 bay2 预泊点，不再接受状态机/平台预泊点覆盖。
- 状态机或平台要恢复外部预泊点覆盖，必须显式设置：

```yaml
accept_gcs_staging_override: true
```

- 精靠泊成功不能只看 `0x0002`；完整成功信号仍要求 `0x0003`。
