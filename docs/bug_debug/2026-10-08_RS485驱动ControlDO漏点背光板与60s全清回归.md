# 2026-10-08 RS485 驱动回归：ControlDO 不点亮背光板 + 60s 全通道清零

> 提单对象：**嵌软**（`~/usv-main/src/usv_rs485_driver` 由嵌软维护）
> 结论一句话：归港侧只负责发 `/control_do`，**已经发了而且返回成功**；背光板没亮是因为
> 驱动 `kDOOnMask` 只写了 bit0（夹爪），漏了 bit1（背光板）；另外 `2026-09-30` 修过的
> "60s 全通道清零误伤背光" 也一并回归了。**不是归港 FSM 的问题。**

- 硬件：IO 控制器（Modbus RTU 从站地址 64），DO 通道映射见 `docs/兴飞船调试文档.md` §3

## 2. 现象

1. 归港（`/dock/start`，`dock_only`）下发后**船坞背光板不亮**，直到进坞段的
   `WaitIO` 才亮几秒；`ACQUIRE_TAG` / `APPROACH` 全程是灭的。
2. 每次 `ControlDO` 之后 60 秒，DO 会整体掉一次。
3. 现场影响：今天傍晚 17:54~18:05 连续多次 `ACQUIRE_TAG -> IDLE` 超时重试，
   tag 找不到（`/docking/tag_visible: false`、`target_mode: SEARCH`）。
   与调试手册 §4.5/§9 的结论一致：**夜间/傍晚 tag 检出依赖船坞背光板**。

### 3.2 但写下去的值只有 bit0（夹爪），不含 bit1（背光板）

`~/logs/xingfei_stack/rs485.log`：

```text
18:04:02.479 ControlDO action accepted, trying to close DO0 and DO1
18:04:03.000 IOController: failed to write DO, slave_id=64, value=0x0001, timeout=500ms
18:04:03.521 IOController: failed to write DO, slave_id=64, value=0x0001, timeout=500ms
18:04:03.680 DO0 and DO1 closed successfully on attempt 3/3
18:04:03.680 DO auto-close scheduled after 60000 ms
```

日志文案写的是 "DO0 and DO1"，但**实际写入值 `0x0001` 只有 bit0**。

驱动实现（`src/usv_rs485_node.cpp:1368` 调 `io_->writeDO(kDOOnMask)`）：

```cpp
// include/usv_rs485_node.hpp:288
static constexpr uint16_t kDOOnMask = 0x0001;   // DO0        ← 现在是这个
```

而 `IOController::writeDO()` 用的是 **Modbus 0x0F「写全部线圈」**，不是单 bit 操作：

```cpp
// src/io_controller.cpp:180
bool IOController::writeDO(uint16_t digital_output)
{
    ...
    const auto states = maskToCoils(digital_output, do_count_);
    // 使用 0x0F 写全部 DO
    modbus_.writeMultipleCoils(slave_id_, 0x0000, states, timeout_ms_)
```

所以 `ControlDO` 传 `0x0001` 这一下，**会把 bit1 明确写 0**——背光不仅不会被点亮，
而且还会被顺手熄灭。（只有 `setDOBit()` 才是"读-改-写"，见 `src/io_controller.cpp:245`。）

### 3.3 唯一会点亮背光板的地方是 WaitIO，且只覆盖进坞段

`src/usv_rs485_node.cpp:1097-1131`：WaitIO 轮询时 `setDOBit(1, true)` 点亮，退出时
`setDOBit(1, false)` 熄灭。今天日志：

```text

17:59:39.271 WaitIO canceled: DO2 OFF
```

`WaitIO` 只在 `BACK_IN` / `FINAL_DOCK` 才起（`docking_fsm.py`），
**`ACQUIRE_TAG` / `APPROACH` 没有任何环节管背光**。

## 4. 根因（已确证）

1. **归港侧没有"打开背光板"的动作可用**：全船 RS485 只有 `/control_do`（夹爪）和
   `/wait_io`（等停泊到位）两个 action（`action/` 目录 + 板上 `ros2 action list` 均确认）。
   按设计，背光板（bit1，掩码 `0x0002`）应由 `ControlDO` 与夹爪同帧点亮。
2. **驱动这一版 `kDOOnMask = 0x0001`**，`ControlDO` 只驱动夹爪；并且因为 `writeDO` 是
   写全部线圈，`0x0001` 还会把 bit1 清零。→ **归港一开始背光就是灭的**，
   不是"亮了 60 秒再灭"。
3. **60s 定时器仍是 `writeDO(0x0000)` 全清**，`kDOAutoCloseDelayMs=60000`：
   每次 `ControlDO` 后 60 秒会把 bit0/bit1 一起断一次；由于 `ACQUIRE_TIMEOUT` 也在
   60s 量级，现场表现为"反复重试、背光一直没亮"。
4. 只有 `WaitIO` 活跃期间背光会被 `setDOBit(1,true)` 临时点亮，覆盖不到
   `ACQUIRE_TAG` / `APPROACH`。

## 5. 期望行为（现场要求）

| 阶段 | bit0 夹爪 | bit1 背光板 |
| --- | --- | --- |
| ControlDO 打开（归港/出港开始） | 开 | **开** |
| 归港途中（ACQUIRE / APPROACH / BACK_IN） | 保持 | **保持** |
| WaitIO 抓住（归港成功） | 关 | 关 |
| WaitIO 取消 / 失败 | 关 | 关 |
| 兜底超时（应远大于单次归港时长） | 关 | 关 |

## 6. 建议修改（给嵌软，`~/usv-main/src/usv_rs485_driver`）

1. `include/usv_rs485_node.hpp:288`
   `kDOOnMask` 从 `0x0001` 改回 **`0x0003`**（DO0 夹爪 + DO1 背光板）。
2. `include/usv_rs485_node.hpp:294`
   `kDOAutoCloseDelayMs` 从 `60000` 改回 **`600000`**（10 分钟兜底，仅作线圈保护）。
3. `src/usv_rs485_node.cpp:1531`（`doCloseTimerCallback()`）
   把 `io_->writeDO(kDOOffMask)` 改回 **`io_->setDOBit(0,false) + io_->setDOBit(1,false)`**，
   只断夹爪线圈和背光，避免整通道清零。
4. 建议顺手补两处可观测性（现场这次就是因为看不到 DO 状态才绕了弯路）：
   - `writeDO()` 成功时按 INFO 打印**实际写入掩码**（如 `writeDO ok value=0x{:04X}`），
     现场可直接用 `value=` 判断背光位有没有被带上；
   - 恢复 DO 状态的可读接口（老的 `/io_state` 话题在本版已不存在，
     `ReadDI` 只返回 DI，现在没有任何途径读回 DO）。
5. **待确认的语义歧义（遗留）**：`ControlDO` 同时被"归港打开"（`WAIT_DOCK_OPEN`）和
   "出港松开"（`WAIT_DOCK_RELEASE`）复用，驱动无法区分，出港也会点亮背光。
   若需要出港后立即灭灯，建议给 `ControlDO.Goal` 加语义字段（如 `mode: dock|undock`），
   而不是继续用一个掩码表达两种意图。

## 7. 现场临时规避（不改驱动，仅应急）

手工点背光（`3` = 夹爪+背光，`2` = 只背光）：

```bash
ros2 service call /set_do usv_rs485_driver/srv/SetDO "{digital_output: 3}"
```

两个坑：60 秒后驱动会 `writeDO(0x0000)` 全清；下一次 `ControlDO` 也会把 bit1 抹掉。
所以 `ACQUIRE` / `APPROACH` 期间需要**每 60 秒内重发一次**才能维持。

## 8. 验收方法

1. 修完重编、重起 `~/start_xingfei_stack.sh`。
2. 发一次 `/dock/start` → `WAIT_DOCK_OPEN`，看 `rs485.log`：
   - 应出现写入掩码 **`0x0003`**（不是 `0x0001`）；
   - 60 秒后不应再出现把 bit1 关掉的记录。
3. 目视：进入 `ACQUIRE_TAG` / `APPROACH` 后背光板**始终亮**；`WaitIO` 抓住后按预期熄灭。
4. 夜间完整归港一次，确认 `ACQUIRE_TAG` 不再超时（对照调试手册 §4.5/§9）。

## 9. 结论边界（明确不背锅的部分）

- 归港侧（`usv_docking` / `dock_mission`）**只负责发 `/control_do`**，本次日志证明已发且成功；
  归港侧不存在也没有义务实现"打开背光板"的接口。
- `ControlDO` 的写入掩码、DO 定时关闭策略、DO 状态的可读接口，**全部在 RS485 驱动内**。
- 本记录**未改动任何代码**（驱动是嵌软维护的包，现场只做只读排查）。

## 10. 更新（2026-10-08 晚：现场澄清硬件语义后，归港侧已自行绕开）

现场确认了硬件事实，改变了上面 §5/§6 的结论基线：

> **归港时夹爪不用电机打开**——船体会通过机械结构自己把爪子撞开；
> **只有出港必须主动抬爪**（爪子被船体扣住）。

因此归港侧（`usv_docking`，本仓维护）已做如下改动，**归港不再依赖驱动的
`ControlDO` 来点背光**，本单对 §6.1 的紧急程度随之下降：

1. `dock_claw_enabled` 拆成 `dock_claw_open_on_start`（兴飞 `false`）+
   `dock_claw_release_on_undock`（兴飞 `true`）：归港跳过 `WAIT_DOCK_OPEN`，
   出港仍走 `WAIT_DOCK_RELEASE`。
   副作用（正向）：10-06/10-07 的 11 次 `DOCK_OPEN_FAILED/TIMEOUT`
   归港失败从此消失。
2. 背光改由 FSM 经 `/set_do` 管：`/dock/start` 点亮 `bit1`，**整个会话保持**并按
   `backlight_keepalive_sec=20s` 保活；**失败/重试不关灯**（重试期间相机还要看
   Tag），只有 `DOCKED` / `/dock/cancel` / `/dock/undock` 关闭；
   `WAIT_DOCK_OPEN/RELEASE` 与 `BACK_IN/FINAL_DOCK` 不干预（交给驱动）。
   参数见 `usv_docking/config/docking.yaml`，语义见 `docs/兴飞船调试文档.md` §3.1/§3.2。

**仍然需要嵌软处理的部分（§6 剩余项，优先级重排）**：

- **§6.3 / §6.2（60s 全通道清零）仍需修**：归港虽然不再触发该定时器，
  **出港的 `ControlDO` 仍会挂上 60s 定时器并 `writeDO(0x0000)`**。出港后 60s 内
  若又开始下一次归港，这一刀会把刚点亮的背光抹掉（靠 FSM 20s 保活兜住，
  最坏有 ≤20s 熄灭窗口）。建议仍按 §6.2/§6.3 改：兜底 600s +
  改为 `setDOBit(0,false)+setDOBit(1,false)`。
- **§6.4（`ControlDO` 语义歧义）**：出港与（其他船坞的）归港仍共用一个 goal，
  建议加 `mode: dock|undock` 字段。
- **§6.1（`kDOOnMask`）优先级下降**：兴飞归港已不走 ControlDO，此项不再影响
  兴飞现场；但**若哪台船仍用 `dock_claw_open_on_start=true`**，则必须改回 `0x0003`。
- **§6.4 可观测性**（`writeDO` 打印实际掩码 / 恢复 DO 读回）**仍需**，
  否则现场只能靠 `docking_fsm` 日志间接判断背光位状态。
