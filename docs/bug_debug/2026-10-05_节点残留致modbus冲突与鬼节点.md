# 2026-10-05 节点残留导致 modbus 冲突与"鬼节点"事故

> 现象：归港 DOCK_OPEN_FAILED 频发、坞侧 modbus 设备（IO 控制器 slave 64、无线充电器 slave 6)"时好时坏/陆续掉线"、充电监测开了却没数据。
> 根因：**同一角色 ROS 节点多份残留**（重启只杀了 launch 包装进程，子节点变孤儿），多份 rs485 节点同时向同一 modbus TCP 网关（192.168.2.111:18223）发帧，帧交错冲突。
> 状态：已修复（清理 + 栈脚本改 setsid + 进程组停止）。

## 经过

1. 当天多次手动重启（部署调试需要），每次 `kill <launch wrapper pid>` 或 `kill -INT` 只杀了 `ros2 launch` 包装进程，**launch 拉起的节点进程变孤儿继续运行**。
2. 高峰时船上同时跑着：速度桥 ×4、rs485 ×3、归港 FSM/控制器 ×2、gi320 ×2、定位 ×2。
3. 直接后果：
   - **rs485 ×3 争抢 modbus 网关**：17:34 起 slave 64（坞 IO 控制器）/slave 6（充电器）读写大面积失败，被误判为"坞硬件故障"，现场白做了一次坞断电重启；
   - **充电监测"鬼节点"**：`/wireless_charger_monitor` 服务调用随机落到某个残留节点上，开关开到了后来被 kill 的节点，存活节点一直没发 `/wireless_charger_state`，归港压紧段秒触发 `CHARGE_SIGNAL_LOST`；
   - **归港参数不生效**：旧 FSM/控制器残留顶名，`ros2 param get` 拿到旧值；新旧两套同时发 `/cmd_vel_nav`。
4. 巧合叠加增加了误判难度：同期无线充电上到 15A(800W)，一度怀疑 EMI 干扰。

## 判断依据

- `pgrep -af` 每个角色 >1 份；rs485 日志同一时刻两个 pid 都在做 IO query;
- 清理到单节点后，ReadDI 立即恢复（`digital_input=0x03`)、充电 15A 稳定、坞通信全绿——**坞硬件全程无辜**。

## 修复与根治

1. 全船进程审计，所有角色清理到恰好一份；
2. `start_xingfei_stack.sh` 两项根治改动：
   - 启动改 `setsid nohup`(pid 即进程组组长）;
   - `stop` 改按进程组杀：`kill -INT "-$(cat pid)"`——包装进程和全部子节点一起停。
3. **规矩：重启一律走栈脚本 `stop`/`start`，不手动 kill pid**；节点 `SIGINT` 可能卡在驱动 wait 上，杀不掉用 `SIGTERM`。
