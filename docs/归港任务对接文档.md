>
> **代码基线（2026-10-20）**：本文按 `src/dock_mission`、`src/usv_docking` 当前实现重写，包含
> 2026-10-13 的 SETTLE 实测停稳门/断流防线、2026-10-15 的 `/dock/in_dock`、2026-10-19 的
> 出泊盲开与「驶出未确认」处理。与旧版文档冲突时以本文为准。
>
> 实现包：`src/dock_mission`（任务编排 FSM）→ 交接 `src/usv_docking`（精靠泊四节点）。
> 相关文档：`docs/导航与归港异常告警.md`（告警清单）、`docs/特殊情况码汇总.md`（21xx，旧版；
> 船端仓 `docs/特殊情况码V0.2.md` 更新）、`src/usv_docking/docs/架构与上层接口.md`（精靠泊内部架构）。

## 0. 读前必看：对接结论速查

| 问题 | 结论 |
|---|---|
| 上层触发什么？ | 主入口 `/gcs_dock/command`（JSON，可带 `mission_id`/`command_id`/预泊点）；兼容 `/dock/home`、`/dock/mission/start` |
| 如何确认受理？ | 5 s 内收到 `DOCK_TASK_ACCEPTED` / `UNDOCK_TASK_ACCEPTED`（service 事件，上层回 ACK） |
| 如何确认成功？ | 只认 `DOCK_SUCCEEDED` / `UNDOCK_SUCCEEDED` 事件，且 `/dock_task/status` 回到 `dock_active=false && run_state=IDLE` |
| 失败怎么判？ | 只认 `DOCK_FAILED`（含出泊失败）；按 §5 把 `reason` 映射到 21xx |
| 船在不在坞？ | 调 `/dock/in_dock`（`m_common/srv/QueryInDock`，二维码判定），见 §2.4/§2.5 |
| 精靠泊丢 Tag 会不会盲倒？ | **有界**：只在 `ODOM_PREDICTION` 推算态、按 3 s / 5 s / 10 s 等窗口继续；`pose_source=INVALID` 时倒船运动立即停。详见 §4.5 |
| 夹爪已扣住船体还能不能退/重试？ | **不能**：WaitIO 任一夹爪 DI 置位即禁止一切驶出/重试，就地 FAILED + 人工接管。详见 §4.5.3 |
| 出泊失败有什么特殊？ | 统一回 `DOCK_FAILED`（不是 `UNDOCK_FAILED` 事件），上层按出泊会话映射 2106；默认不盲开，无 VISION 等待 10 s → `UNDOCK_NO_VISION`，没出去就失败（§4.5.2） |

## 1. 系统位置与职责划分

```text
上层状态机 / 嵌软（Decision）                      ← 本文的对接对象
   │  触发：/gcs_dock/command、/dock/home、/dock/mission/start|cancel
   │  查询：/dock/in_dock（船是否在坞内）
   ▼
dock_mission（编排 FSM）
   │  预泊：/mission_bridge/send_waypoints（WGS84）→ Nav2
   │  到点判定：订阅 /task_event（mission_bridge 生态）
   │  停稳门：SETTLE 实测速度/角速度（/mavros/gps_input/local）
   │  交接：/dock/start → usv_docking；/dock/cancel、/dock/undock
   │  上报：/dock_task/status（5 Hz）+ /dock_task/event（service，等 ACK）
   ▼
usv_docking（精靠泊，船内四节点；上层不直接对接）
   estimator → fsm → motion_controller → /cmd_vel_nav
   safety 独立监督（硬停/撤离请求）
```

- 上层**只**消费本文 §2（触发/在坞查询）、§3（上报）、§4（状态与无视觉边界）、§5（21xx 映射）。
- `/dock/status`、`/docking/*`、`/dock/mission_status`、`/dock/speed_authority` 是**船内联调接口**，
  不要作为对接依据（字段/状态名可能随内部重构变化）。
- `dock_mission` 与 `usv_docking` 都随整栈启动；上层调用时若 `/dock_task/status` 无心跳，
  视为归港栈离线，按 §6 兜底。

## 2. 触发接口（上层 → 船）

### 2.1 `/gcs_dock/command`（推荐主入口）

- 类型：`std_msgs/msg/String`，data 为 UTF-8 JSON；QoS：RELIABLE depth=10
- topic 名可由参数 `gcs_dock_command_topic` 改

```json
{
  "action": "one_click_dock",   // 必填：one_click_dock | dock_only | undock | cancel
  "mission_id": "m001",         // 可选：任务标识，原样回填到 status/event
  "command_id": "c1",           // 可选：指令标识，原样回填到 status/event
  "dock_lat": "30.123456",      // 可选：预泊点纬度（WGS84，度；字符串/数值均可）
  "dock_lon": "120.123456",     // 可选：预泊点经度（WGS84，度）
  "dock_yaw": "65536.0"         // 可选：预泊点处船艏航向（度，见下方 yaw 语义）
}
```

| action | 语义 | 流程 |
|--------|------|------|
| `one_click_dock` | 一键编排归港 | Nav2 预泊 → 停稳 → 交接精靠泊 → 监控至完成 |
| `dock_only` | 仅精靠泊（船已在预泊点附近） | 跳过 Nav2 预泊与 SETTLE，直接交接 |
| `undock` | 出泊 | 交接 usv_docking 前进离坞 → 监控至完成 |
| `cancel` | 取消当前归港会话 | 任何时刻可发；幂等 |

#### 2.1.1 预泊点覆盖规则（重要）

- **要用船端泊位库默认点**：省略 `dock_lat`/`dock_lon`、传 `null`，或把二者填
  **65536.0 哨兵**（与 `dock_yaw` 相同语义，2026-10-20 起兼容上层 Decision 的
  “三字段恒发 65536”写法）。当前解析规则：
  - 任一坐标为缺失/null/非数/65536.0 → 视为未指定，回退
    `dock_database.yaml: gnss_staging`；
  - 两个都齐全且合法（非 `(0,0)`、在 WGS84 范围内）→ 覆盖泊位库；
  - **两个都齐全但非法（`(0,0)`、真正越界，如 lat=91 / lon=181）→ 整条指令丢弃**
    （打 warning，无事件上报）。
- **`dock_yaw` 语义**：预泊点处**船艏航向**（ENU/map 系，度，逆时针为正，0°=东），
  船端原样透传给导航作为到点朝向，不做取反/旋转。归港要求船尾朝坞（后向相机看 Tag、
  倒船入坞），故该值应为**船艏朝坞外**的航向；若上层量的是“船尾→船坞”方向角，
  须 **+180°** 后再下发。
- `dock_yaw` 缺失、非数或超出 `[-360, 360]`（约定哨兵 65536.0）表示不指定朝向，
  导航按行进方向取到点朝向；经纬度合法但 yaw 非法**不算错误**。
- 仅 `one_click_dock` 会用到预泊点（`dock_only` 跳过导航、`undock`/`cancel` 忽略这些字段）。
- 预泊点覆盖在**同一会话的重试中保留**：预泊失败重试仍用上层下发的同一个点，不会退回泊位库。
- 上层（Decision）侧预泊点来源（供联调核对）：`mission_type=3` 用云端下发的唯一航点；
  `mission_type=1` 且结束动作=4、以及低电量返航，用 `usv_param_set` 存下的默认船坞
  （`dock_berths`）。两处都取不到时，上层把 lat/lon/yaw 三者都填 65536 哨兵——
  船端已按“未指定”处理并回退泊位库，不会再丢弃整条指令。
- 商用单坞：JSON 不含 `bay_id`（泊位由船端 `dock_mission.yaml: bay_id` +
  `config/dock_database.yaml` 选定）。
- 非法 JSON / 未知 action：丢弃并打 warning，**不上报事件**（上层靠 status/受理超时兜底）。
- 忙时（已有会话，或状态不在 IDLE/SUCCEEDED/FAILED/CANCELLED）静默拒绝，只打 warning；
  上层以下发后 5 s 内是否收到 `*_TASK_ACCEPTED` 判断受理与否。
- 从 `FAILED` 状态可以直接下发新命令（无需先 cancel）；`cancel` 也会把 `FAILED` 复位到 IDLE。
- **建议始终带 `mission_id` 和 `command_id`**：船端事件会原样回填这两个字段；
  若上层事件 server 要求二者非空（Decision 的 `DockActuator::onEvent` 要求），
  不带 `command_id` 的触发会被 ACK 为 `success=false`（船端 FSM 仍继续执行，但
  `event_ack_failures` 会增加）。

> 注：入口验收环节（ENTRY_VALIDATE / `dock_entry_validator`）已于 2026-09-15 移除；
> 停稳后直接交接精靠泊，交接前的到点把关由 Nav2 `docking_goal_checker` 承担。

### 2.2 `/dock/home`

- 类型：`std_msgs/msg/Bool`，`data: true` = 一键归港（等价 `one_click_dock`，无外部 mission_id/command_id）
- `data: false` 忽略。topic 名可由参数 `dock_home_topic` 改
- 船端会把 `mission_id` 回填为默认 `dock_mission_id`（默认 `dock_staging`），`command_id` 为空。
- **注意**：若上层事件服务要求 `mission_id`/`command_id` 都非空
  （Decision 的 `DockActuator::onEvent` 就是这样），用 `/dock/home` 触发会被回 `success=false`。
  正式对接请走 `/gcs_dock/command` 并带上 id。

### 2.3 Service（Trigger）

| 服务 | 类型 | 语义 |
|------|------|------|
| `/dock/mission/start` | `std_srvs/srv/Trigger` | 一键归港；`success=true` 表示受理，`message` 含模式 |
| `/dock/mission/cancel` | `std_srvs/srv/Trigger` | 取消；`success=true` 幂等 |

> 与 `/dock/home` 相同：Trigger 通道没有 `command_id`，正式对接优先用 `/gcs_dock/command`。

### 2.4 `/dock/in_dock`（船是否在坞内，2026-10-15）

出泊/派发航线**前**，上层调用本 service 确认船确实在坞内，避免船不在坞时误出泊，
或船还在坞内就派航线拖着船坞走。

- 类型：`m_common/srv/QueryInDock`（定义：`src/m_common/srv/QueryInDock.srv`，
  注释副本 `docs/srv/QueryInDock.srv`）；服务名可由参数 `in_dock_service` 改，置空 = 不注册。
- 服务端：`dock_mission_node`（不是 `usv_docking`）。
- 方向：上层（client）→ 船端（server）。

**判定依据**：二维码（AprilTag）定位链 `docking_pose_estimator` 发布的
`/docking/dock_pose` = `base_link` 在 `dock_est` 系的平面位姿
（坞中心/充电位为原点，**+x 朝坞内**，坞外 `x<0`），配合 `/docking/pose_source`
（`VISION` / `ODOM_PREDICTION` / `INVALID`）判有效性；位姿落在配置区域即“在坞内”。
**判定的是“船体 base_link 相对坞中心的位置”**，不是夹爪/IO 信号。

**Request**（上层 → 船）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `wait_vision` | `bool` | `true`=位姿无效时允许船端临时打开二维码检测通道、点亮船坞背光，等视觉锚定（最长 `in_dock_vision_timeout_sec`，默认 6 s）再作答；`false`=只用当前缓存立即作答 |

**Response**（船 → 上层）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `in_dock` | `bool` | `true`=判定在坞内；`pose_valid=false` 时**恒为 false** |
| `pose_valid` | `bool` | 判定所用坞系位姿是否有效；**false 时 `in_dock` 不可信** |
| `pose_source` | `string` | `VISION` / `ODOM_PREDICTION` / `INVALID` / `NONE`（无数据） |
| `dock_x` / `dock_y` | `float64` | 判定时 `base_link` 坞系坐标（米）；位姿无效为 0 |
| `message` | `string` | 判定依据说明 |

**`pose_source` 语义**：

| 值 | `pose_valid` | 含义 |
|---|---|---|
| `VISION` | true | 当前视觉有效，`in_dock` 可信 |
| `ODOM_PREDICTION` | true | 锚点仍在、里程计推算（≤3 s），可用但有漂移风险 |
| `INVALID` | false | 曾锚定后丢失/推算超时，不可信 |
| `NONE` | false | 无位姿数据（估计器未运行/断流），不可信 |

> **本服务不额外上报相机故障**。相机故障由上层状态机通过 `/sensor_health` 自己检测；
> 船端在相机故障时只会表现为 `INVALID`/`NONE`，不会把它误报成“坞外”。
> 上层结合自己的相机健康判断：相机正常且 `in_dock=false` → 按坞外处理；
> 相机故障 → 按故障处理；其余 → `Unknown`。

**在坞区域（`dock_mission.yaml`，dock 系，米）**：

| 参数 | 默认 | 说明 |
|------|------|------|
| `in_dock_x_min` | `-1.5` | x 下限；坞外为负，半入坞也算在坞内（可出泊） |
| `in_dock_x_max` | `1.0` | x 上限；停稳充电位 x≈0 |
| `in_dock_y_max` | `0.6` | \|y\| 上限（横向） |
| `in_dock_pose_max_age_sec` | `1.5` | 缓存位姿最大龄期；estimator 正常 20 Hz 恒发 |
| `in_dock_prediction_max_age_sec` | `3.0` | `ODOM_PREDICTION` 最大推算龄期；超此不用于在坞判定 |
| `in_dock_vision_timeout_sec` | `6.0` | `wait_vision=true` 且位姿无效时，等视觉锚定的上限 |
| `in_dock_restore_channel` | `true` | 查询结束后恢复关闭本查询打开的检测通道与背光 |
| `in_dock_backlight_mask` | `2` | 船坞背光 DO 掩码（bit1）；0=查询不控制背光 |
| `dock_measurement_age_topic` | `/docking/measurement_age` | 估计器“距最近视觉观测秒数” |

**行为细节**：

- `pose_valid=true` 的条件：收到过 `/docking/dock_pose`，`pose_source ∈ {VISION, ODOM_PREDICTION}`，
  且消息龄期 ≤ `in_dock_pose_max_age_sec`。`pose_source=ODOM_PREDICTION` 是**里程计推算**，
  会随推算时间漂移；关键决策建议优先采信 `VISION`。推算龄期超过
  `in_dock_prediction_max_age_sec`（默认 3 s）时不再用于在坞判定（返回
  `ODOM_PREDICTION` 但 `pose_valid=false`）。
- **无有效位姿时 `in_dock=false`**：船端不新增状态码，只通过 `message` 说明原因：
  - `wait_vision=true`、检测节点正常（apriltag 服务在线 + 估计器在发数据）、已开启
    检测但 `measurement_age=inf`（从未见到 Tag）→ message 明确“未检测到 Tag，
    判定不在坞内”；
  - 检测节点异常/服务不在线 → message 明确“按失败处理，in_dock 不可信”；
  - 曾锚定后丢失 / 未尝试开检测 → message “in_dock 不可信”。
  相机是否掉线由上层状态机用 `/sensor_health` 自己判；出泊任务本身
  （`usv_docking`）另有“无视觉不盲开”的硬保护，见 §4.5。
- `wait_vision=true` 且当前位姿无效：
  - 若**没有**归港/出泊会话在进行：船端先通过 **ControlDO `{start:true, mask:2}`**
    点船坞背光（只开灯、不驱动夹爪），再开二维码检测通道，
    等视觉锚定或 6 s 超时；查完按 `in_dock_restore_channel=true` 恢复关闭。
  - 若**有**会话在进行（`dock_active=true`）：不动背光/检测通道，只用当前缓存作答，
    因此可能立即返回 `pose_valid=false`。
  - 若 `usv_docking` 的背光会话活跃（`backlight_session_active=true`），查询不写 DO，
    避免把 FSM 为重试保持的灯误关。
- `wait_vision=false`：只读缓存，立即返回；适合高频监视，不适合做出泊门。
- 查询本身可能阻塞数秒（最长约 6 s + 传输）。服务端在独立回调组、用多线程 executor，
  不会饿死归港 FSM；但**上层客户端不要阻塞自己的 200 ms 主循环**，应异步调用。
- 若 estimator 没在跑（`usv_docking` 未启动），不会有 `/docking/dock_pose` →
  `pose_source=NONE`、`pose_valid=false`。

> **现场实测（2026-10-15，船坞位于 map 系约 (112, 124)）**：
> 出港后坞外 ~1.8 m → `wait_vision=true` 返回 `in_dock=false, pose_valid=true,
> VISION, dock_x=-1.780, dock_y=0.135`（区域外）；人工开回坞内居中后 →
> `in_dock=true, pose_valid=true, VISION, dock_x=-0.008, dock_y=-0.004`（坞中心/充电位）。
> 全程无需人工点灯：调用前 `pose_source=INVALID`，调用中即得 `VISION`，调用后自动回到
> `ODOM_PREDICTION` 且检测通道关闭。判定区域与排错细节见 `兴飞船调试文档.md` §4.4.1。

### 2.5 上层状态机如何接入“在坞检测”（重点）

当前船端已经提供二维码在坞判定；上层（Decision 的 `DockActuator`）旧的实现是向
`/wait_io` action 发抓夹探测（`max_queries=1000`，最坏要 200 s 才能得出“不在坞里”），
慢且依赖 RS485 夹爪。**建议把“在不在坞”的判定切换到 `/dock/in_dock`**；
WaitIO 只保留用于归港成功后的 2103 夹爪锁定确认（见 §5）。

#### 2.5.1 返回值 → 上层三态

| `/dock/in_dock` 返回 | 上层判定 | 说明 |
|---|---|---|
| `pose_valid=true` 且 `in_dock=true` | `InDock` | 船在坞内 |
| `pose_valid=true` 且 `in_dock=false` | `OutOfDock` | 船不在坞内 |
| `pose_valid=false` 且 `in_dock=false` | 结合上层自己的相机健康：<br>相机正常 → `OutOfDock`；<br>相机故障 → `CameraFault`（报错）；<br>其他 → `Unknown` | 船端只报“无有效坞系位姿”，不报相机故障 |
| 服务不可用 / 调用超时 | `Unknown` | 归港栈未起或网络异常 |

> **分工**：船端只回答“坞系位姿是否有效、`in_dock` 是否成立”；“相机是否掉线”
> 由上层状态机通过 `/sensor_health/active_faults`（`REAR_CAMERA` 3005）自己判。
> 因此 `pose_valid=false` 时，相机正常且 `in_dock=false` 可按坞外处理；相机故障
> 则按故障处理，不能把船开出坞/派航线。
>
> 对 `pose_source=ODOM_PREDICTION` 的更保守策略（推荐）：`in_dock=true` → `InDock`；
> `in_dock=false` 时只有 `pose_source=VISION` 才判 `OutOfDock`，否则判 `Unknown`——
> 推算位姿漂移时，“说不在坞”可能是假的，不能在船可能还在坞里时派航线。

#### 2.5.2 调用方式与超时

- **异步调用**，不要在状态机 tick 里同步等；或放到独立线程/executor。
- 客户端超时建议 **≥ 8 s**（`in_dock_vision_timeout_sec=6 s` + 服务发现/传输余量）。
  超时按 `Unknown` 处理。
- 位姿有效时服务**立即返回**（只读缓存），可以按需查询；位姿无效且 `wait_vision=true`
  才会阻塞等视觉，不要高频轮询。
- **不要在归港/出泊会话进行中**（`dock_active=true`）调用并等待视觉：船端不会开灯/开通道，
  只会返回缓存；需要等待时先等会话结束。
- 一次查询可能点亮船坞背光几秒，属正常现象；不要把它当作“出泊/归港已开始”的信号。

#### 2.5.3 两个典型接入点

**A. 派发航线/单点任务前（出泊门）**

```text
上层 ── /dock/in_dock {wait_vision: true} ──► dock_mission
     ◄── {pose_valid, in_dock, pose_source, dock_x, dock_y}

if InDock:
    /gcs_dock/command {action:"undock", mission_id, command_id}
    等 UNDOCK_TASK_ACCEPTED → UNDOCK_HANDOFF → UNDOCK_SUCCEEDED
    （失败：DOCK_FAILED，按出泊会话映射 2106；不要派航线）
    出泊成功且 status 回 IDLE 后再派航线
if OutOfDock:
    直接派航线
if 上层自己的相机健康显示后视相机故障（3005）:
    不出泊、不派航线；上报相机故障，转人工/等待相机恢复
if Unknown（pose_valid=false 且相机健康也判不出，或服务超时）:
    安全方向：不派航线、不出泊；转人工确认
    （Decision 当前语义：探不出在坞 → task_code=NAVIGATION_NOT_READY；
      出泊失败 → task_code=UNDOCK_FAILED/2106）
```

**B. 归港任务/低电量返航开始前（是否已经在坞内）**

```text
上层 ── /dock/in_dock {wait_vision: true} ──► dock_mission
if InDock:      已在坞内，归港任务可直接判完成（无需再跑一遍靠泊）
if OutOfDock:   发 one_click_dock
if 上层相机健康=后视故障: 拒绝归港任务，上报 3005（没有视觉无法精靠泊）
if Unknown:     照常发 one_click_dock（多跑一次靠泊只是浪费时间；
                与出泊门相反，这里不能因为判不出在坞而拒绝归港）
```

> 注意：`one_click_dock` 本身**不检查**船是否已经在坞内；如果上层不先查，会重新 Nav 到预泊点
> 再靠泊一遍。是否需要“已在坞内直接成功”由上层决定。

#### 2.5.4 与 WaitIO 的分工

| 检查 | 接口 | 用途 |
|------|------|------|
| 船是否在坞（presence） | `/dock/in_dock`（二维码） | 派航线前出泊门、归港前已在坞判断 |
| 夹爪是否锁定（lock） | `/wait_io` action（`usv_rs485_driver`） | 归港上报 `DOCK_SUCCEEDED` 后，上层再验一次；没合上/验不出 → 2103 |

两者不能互相替代：二维码只能说明船体位置，不能说明夹爪已扣住；WaitIO 只能说明夹爪状态，
在相机故障/无位姿时无法独立判“船在不在坞”。上层应分别使用。

## 3. 上报接口（船 → 上层）

### 3.1 `/dock_task/status`（周期状态，约 5 Hz）

`std_msgs/msg/String`，data 为 UTF-8 JSON；QoS：RELIABLE depth=10。
topic 名可由参数 `dock_task_status_topic` 改。

```json
{
  "schema_version": 1,
  "run_state": "RUNNING",            // IDLE | RUNNING | SUCCEEDED | FAILED | CANCELLED
  "phase": "STAGING",                // IDLE | STAGING | DOCKING | UNDOCKING
  "mode": "one_click",               // one_click | dock_only | undock | null
  "dock_active": true,               // 归港会话是否存活（成功/失败/取消后释放=false）
  "retry_count": 1,                  // 已发生的预泊/交接重试次数
  "retry_max": 5,                    // staging_retry_max（默认 5）
  "needs_manual_takeover": false,    // true = 请求人工接管（重试耗尽/夹爪半抓/驶出未确认）
  "needs_reapproach": false,         // true = 精靠泊失败需重 Nav 预泊（会话内粘滞）
  "camera_ready": true,              // 预留，当前恒 true，勿当作相机就绪门
  "error_code": 0,                   // 预留，当前恒 0（21xx 由上层按 §5 映射）
  "error_message": null,             // 失败原因（最近一次）；成功后可能为空
  "mission_id": "m001",
  "command_id": "c1",
  "elapsed_sec": 98.5,               // 会话开始至今；会话结束后请忽略
  "event_ack_ok": true,              // 最近一次关键事件是否已被上层 ACK
  "event_ack_failures": 0,           // 累计未确认事件数（>0 = 事件通道异常）
  "odom_speed": 0.03                 // 最近一帧实测线速度 m/s（SETTLE 停稳门用）；缺测为 null
}
```

**`run_state` 语义**：

| 值 | 含义 | 备注 |
|---|---|---|
| `IDLE` | 无活动会话 | `dock_active=false` |
| `RUNNING` | 会话进行中 | 含预泊、停稳、交接、精靠泊、出泊 |
| `SUCCEEDED` | 成功终态 | **瞬态**，同一 tick 内随后回 IDLE，通常只在事件里看到 |
| `FAILED` | 失败终态 | **会保持**，直到新命令或 `cancel`；`dock_active=false` |
| `CANCELLED` | 取消终态 | **瞬态**，随后回 IDLE |

**`phase` 语义**：

| phase | 覆盖的内部状态 | 说明 |
|---|---|---|
| `STAGING` | ARMED / NAV_TO_STAGING / SETTLE | Nav2 预泊、到点、实测停稳 |
| `DOCKING` | DOCK_HANDOFF / MONITOR_DOCK / COMPLETE_SETTLE | 已交接 usv_docking 精靠泊（含 2 s 收尾） |
| `UNDOCKING` | ARMED / UNDOCK_HANDOFF / MONITOR_UNDOCK / COMPLETE_SETTLE（mode=undock） | 出泊中 |
| `IDLE` | IDLE / SUCCEEDED / FAILED / CANCELLED | 无活动会话或终态 |

**`dock_mission` 内部状态 → status 映射**（排障用；上层只需 phase/run_state）：

| 内部状态 | run_state | phase | 说明 |
|---|---|---|---|
| `DOCK_MISSION_IDLE` | IDLE | IDLE | 无会话 |
| `DOCK_ARMED` | RUNNING | STAGING / UNDOCKING | 命令已受理，等待进入下一步 |
| `NAV_TO_STAGING` | RUNNING | STAGING | 已下发/重发 Nav2 预泊目标 |
| `SETTLE` | RUNNING | STAGING | 到预泊点后等实测停稳（见 §4.1） |
| `DOCK_HANDOFF` | RUNNING | DOCKING | 已发 `/dock/start`，等待下一 tick 进 MONITOR |
| `MONITOR_DOCK` | RUNNING | DOCKING | 等 usv_docking 成功/失败 |
| `UNDOCK_HANDOFF` | RUNNING | UNDOCKING | 已发 `/dock/undock` |
| `MONITOR_UNDOCK` | RUNNING | UNDOCKING | 等出泊成功/失败 |
| `COMPLETE_SETTLE` | RUNNING | DOCKING / UNDOCKING | 完成后的 2 s 收尾 |
| `DOCK_SUCCEEDED` | SUCCEEDED | IDLE | 瞬态；随后 IDLE |
| `DOCK_FAILED` | FAILED | IDLE | 保持到新命令/cancel |
| `DOCK_CANCELLED` | CANCELLED | IDLE | 瞬态；随后 IDLE |

**上层关键判据**：

| 判定 | 条件 |
|------|------|
| 执行中 | `dock_active==true && run_state=="RUNNING"` |
| 成功闭环 | 收到 `DOCK_SUCCEEDED`/`UNDOCK_SUCCEEDED`（并回 ACK），且 status 回到 `dock_active==false && run_state=="IDLE"` |
| 失败 | 收到 `DOCK_FAILED`（并回 ACK）；status 保持 `run_state=="FAILED"`
| 需人工接管 | `needs_manual_takeover==true`（或 `MANUAL_TAKEOVER_REQUESTED` 事件） |
| 可自动重试 | `needs_reapproach==true`；船端已自动重试，上层通常只需继续等 |
| 归港栈离线 | `/dock_task/status` 超过 3 s 无新帧（建议阈值；船端 5 Hz） |

补充：

- `retry_count`/`retry_max` 是**预泊/交接重试**计数；`dock_only` 模式失败也会计入并直接重交接。
- `needs_reapproach` 在会话内**粘滞**：一旦精靠泊报告需要重接近，后续 status 仍为 true，直到新会话。
- `error_message` 是最近一次失败原因；`FAILED` 后仍保留，新会话开始时清空。
- `elapsed_sec` 在会话结束后仍按上次会话起点增长（当前实现的已知小问题），**IDLE 时请忽略**。
- `odom_speed` 是最近一帧值，不保证新鲜；`null` 表示从未收到速度帧。

### 3.2 `/dock_task/event`（事件上报 service，上层为 server）

> 事件通道是 **service**：上层状态机实现 server，船端作 client，**确保上层收到关键事件后回 ACK**。
> 不是话题，不要用 topic echo 等它。

- 类型：`m_common/srv/DockTaskEvent`（定义：`src/m_common/srv/DockTaskEvent.srv`，
  注释副本 `docs/srv/dock_task_event.srv`）
- 默认服务名：`/dock_task/event`（参数 `dock_task_event_service` 可改）
- QoS：ROS 2 service 语义（请求-响应，可靠）

**Request**（船 → 上层）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `event` | `string` | 事件名（必填） |
| `mission_id` | `string` | 任务标识（可空，原样回填） |
| `command_id` | `string` | 指令标识（可空，原样回填） |
| `detail` | `string` | UTF-8 JSON 对象；无 detail 时空串（等价 `{}`） |
| `stamp_sec` | `float64` | 船端事件时间戳（epoch 秒） |

**Response**（上层 → 船，ACK）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `success` | `bool` | `true`=上层已受理（ACK）；`false`=拒绝/未识别 |
| `message` | `string` | 结果说明 / 失败原因 |
| `ack_id` | `string` | 上层回执唯一 id（幂等/去重；可空） |
| `ack_stamp_sec` | `float64` | 上层确认时间戳（epoch 秒；0=未提供） |

**事件清单**：

| event | detail | 触发时机 |
|-------|--------|----------|
| `DOCK_TASK_ACCEPTED` | `{mode}` | 归港/仅精靠泊命令受理（`mode=one_click`/`dock_only`） |
| `UNDOCK_TASK_ACCEPTED` | `{mode:"undock"}` | 出泊命令受理 |
| `DOCK_STAGING_STARTED` | — | Nav2 预泊点已成功下发（**每次重试各一条**；`dock_only` 不发） |
| `DOCK_HANDOFF` | — | 已发布 `/dock/start`，进入精靠泊 |
| `UNDOCK_HANDOFF` | — | 已发布 `/dock/undock`，进入出泊 |
| `DOCK_SUCCEEDED` | `{elapsed_sec, mode}` | 精靠泊完成（2 s 收尾后），会话随后关闭 |
| `UNDOCK_SUCCEEDED` | `{elapsed_sec, mode}` | 出泊完成 |
| `DOCK_FAILED` | `{reason, retry_count, needs_manual_takeover, needs_reapproach}` | 失败终态；**出泊失败也走这个事件** |
| `DOCK_CANCELLED` | — | 已取消（会话存在或非 IDLE 时） |
| `MANUAL_TAKEOVER_REQUESTED` | `{reason, retry_count}` | 重试耗尽/夹爪半抓/驶出未确认，请求人工接管（先于 `DOCK_FAILED`） |

补充说明：

- **成功只以 `DOCK_SUCCEEDED`/`UNDOCK_SUCCEEDED` 为准**，不要解析 `/dock/status` 的 `success` 字段
  （那是船内联调字段）。
- `DOCK_FAILED` 的 `needs_reapproach` 表示“船端认为还可以重接近”；`needs_manual_takeover=true`
  表示“不要自动重试”。两者可能同时为 true（夹爪半抓、驶出未确认等）。
- **出泊失败不会发 `UNDOCK_FAILED`**：统一发 `DOCK_FAILED`，`reason` 形如
  `UNDOCK_TIMEOUT`、`UNDOCK_NO_VISION`、`UNDOCK_EXIT_UNCONFIRMED`（仅盲开开启）、
  `DOCK_RELEASE_FAILED`、`DOCK_RELEASE_TIMEOUT`、
  `SAFETY:*` 等；当前实现出泊失败通常 `needs_manual_takeover=false`（上层按出泊会话映射 2106）。
- `MANUAL_TAKEOVER_REQUESTED` 只在其后紧跟 `DOCK_FAILED` 才有意义；它是告警，不是第二终态。
- `DOCK_CANCELLED` 在“本来就已经 IDLE”时不发（幂等成功）；从 `FAILED` 取消会发。
- 事件 request 的 `command_id` 是**会话级** `command_id`（上层下发值），不是 `retryN`；
  重试次数看 status 的 `retry_count`。`/dock/home`、Trigger 触发的会话 `command_id` 为空。
- 船端对每个事件发起 service 调用，`event_ack_ok`/`event_ack_failures`（见 §3.1）指示上层是否确认收到。
  默认超时 `event_ack_timeout=3 s`；**上层不可达不阻塞船侧 FSM**，只告警/累计失败。
- 上层应将 `success=true` 表示已记录/已处理；重复事件按幂等返回 `true`。
  建议用 `event + command_id + stamp_sec` 作为幂等键；`ack_id` 可回显该键。
- 船侧另向可选观察话题 `/dock_task/event_log` 发布同 JSON（参数 `dock_task_event_log_topic`，
  置空关闭），供日志/联调；**它不保证送达，不能替代 service**。

**上层事件处理建议**（与 Decision 的实现一致）：

| 收到 | 上层动作 |
|---|---|
| `*_TASK_ACCEPTED` | 标记受理；启动执行超时（建议 600 s） |
| `DOCK_STAGING_STARTED` / `DOCK_HANDOFF` / `UNDOCK_HANDOFF` | 仅进度展示，不改变终态 |
| `DOCK_SUCCEEDED` | 按需 WaitIO 验证夹爪锁定（失败/验不出 → 2103）；等 status 回 `dock_active=false && IDLE` 后判完成 |
| `UNDOCK_SUCCEEDED` | 判出泊完成；等 status 回 IDLE 后再派航线 |
| `MANUAL_TAKEOVER_REQUESTED` | 告警/上报告警；继续等 `DOCK_FAILED` |
| `DOCK_FAILED` | 按 §5 映射 21xx；发 `cancel`；等 `DOCK_CANCELLED` + status IDLE；上报失败 |
| `DOCK_CANCELLED` | 取消确认；status 随后 IDLE |

## 4. 完整状态机与流程

### 4.1 dock_mission 编排 FSM

```text
IDLE
  │ /gcs_dock/command(one_click|dock_only|undock) 或 /dock/home / Trigger
  ▼
ARMED（已回 *_TASK_ACCEPTED）
  ├─ one_click ──► NAV_TO_STAGING ──TASK_COMPLETED──► SETTLE ──停稳──► DOCK_HANDOFF
  ├─ dock_only ─────────────────────────────────────────────────────► DOCK_HANDOFF
  └─ undock ────────────────────────────────────────────────────────► UNDOCK_HANDOFF
                                                                        │
DOCK_HANDOFF ──► MONITOR_DOCK ──success──► COMPLETE_SETTLE ──2s──► SUCCEEDED ──► IDLE
                     │                                              ▲
                     ├─ needs_manual_takeover ──► FAILED（保持）     │
                     └─ needs_reapproach ──► 重试（< retry_max）────┘
UNDOCK_HANDOFF ──► MONITOR_UNDOCK ──undock_success──► COMPLETE_SETTLE ──2s──► SUCCEEDED ──► IDLE
                     └─ DOCK_ABORT ──► FAILED（保持）
```

关键行为：

| 项 | 当前实现 |
|---|---|
| 预泊下发 | `mission_bridge/send_waypoints`（异步）；响应超时 **12 s** 判失败并重试 |
| 到点判定 | 订阅 `/task_event`，只认 `mission_id` 匹配且 `command_id=retryN` 的 `TASK_COMPLETED`/`TASK_FAILED`；外任务/上一轮残留事件丢弃 |
| SETTLE 停稳门 | `settle_require_still=true`（默认）：线速度 ≤0.15 m/s、\|角速度\| ≤0.1 rad/s，连续有效观测累计 ≥0.5 s 且 ≥3 帧、帧间隔 ≤1 s，且总等待 ≥2.5 s，才交接；超 15 s 未停稳走预泊重试（`SETTLE_TIMEOUT: ...`） |
| SETTLE 速度源 | `odom_speed_topic` 默认 `/mavros/gps_input/local`；必须与 `usv_docking` 用同一话题 |
| dock_only | 不走 SETTLE；失败重试直接回 `DOCK_HANDOFF`（重新交接，不重新 Nav） |
| 重试上限 | `staging_retry_max` 默认 **5**；每次预泊/交接失败 +1；重试期间 `dock_active` 保持 true，GCS 预泊点覆盖保留 |
| 重试耗尽 | `MANUAL_TAKEOVER_REQUESTED` → `DOCK_FAILED`，`needs_manual_takeover=true` |
| 精靠泊失败 | `MONITOR_DOCK` 先看 `needs_manual_takeover`（夹爪半抓等，直接终局），再看 `needs_reapproach`（重试）；顺序不能反 |
| 完成收尾 | `COMPLETE_SETTLE` 固定 2 s，成功后发 `*_SUCCEEDED` 并回 IDLE |
| 取消 | 释放会话（取消 Nav、发 `/dock/cancel`、恢复巡航 GoalChecker、让权），回 CANCELLED 再 IDLE；幂等 |
| 会话结束 | 速度权 `RELEASE`（取消/成功）或 `FAILED`（失败）；`/dock/cancel` 同时回收 usv_docking |

### 4.2 usv_docking 精靠泊 FSM（内部状态）

> 上层不直接消费这些状态，但排障和“为什么还在动/为什么失败”需要看。状态名可从
> `/docking/state`（内部）或 `/dock/status.v2_state` 观察。

```text
IDLE → [WAIT_DOCK_OPEN*] → ACQUIRE_TAG → APPROACH_ENTRY → ALIGN_ENTRY
     → BACK_IN → FINAL_DOCK → DOCKED
异常：REACQUIRE_TAG（入口外丢 Tag）/ ABORT_EXIT（坞内失败驶出）/ FAILED
出泊：[WAIT_DOCK_RELEASE*] → UNDOCK_EXIT → UNDOCK_SETTLE
* 夹爪动作，仅 dock_claw_enabled=true 且对应方向开关为 true 时启用
```

| 状态 | 行为（target_mode） | 结束条件 / 超时 |
|---|---|---|
| `WAIT_DOCK_OPEN` | HOLD；请求船坞打开夹爪（ControlDO action） | 成功 → ACQUIRE_TAG；失败/超时 15 s → IDLE + needs_reapproach（兴飞 `dock_claw_open_on_start=false`，不走此状态） |
| `ACQUIRE_TAG` | 无锚点：SEARCH 原地旋转；见 Tag：HOLD 集帧（连续 5 帧 VISION） | 锚定 → APPROACH_ENTRY；60 s → IDLE + needs_reapproach |
| `APPROACH_ENTRY` | APPROACH 双向就位：坞外倒退入位，坞内前进倒出；锥形漏斗内直接边倒边收敛，锥外先上轴 | 到预备点（x≈-2.0，\|y\|≤0.15，\|e_yaw\|≤25°，实测速度≤0.15 并保持 0.5 s）→ ALIGN_ENTRY；120 s → needs_reapproach |
| `ALIGN_ENTRY` | ALIGN 小倒速弧线消艏向（0.08 m/s，x≥-1.5 退回 v=0 纯转）；\|e_y\|>0.45 退回 APPROACH | \|e_y\|≤0.15、\|e_yaw\|≤7° 保持 2 s → BACK_IN；45 s → needs_reapproach；y 卡死 6 s 回 APPROACH |
| `BACK_IN` | 沿轴线倒入（正常 0.25 / 慢 0.15 m/s，门控 2 超限停车修艏向）；夹爪模式：WaitIO 抓住即 DOCKED | 距目标 <0.8 m 且 \|y\|≤0.15 → FINAL_DOCK；90 s → ABORT_EXIT；位移停滞 15 s → ABORT_EXIT |
| `FINAL_DOCK` | 低速倒向充电位（0.15 m/s）；到达死位置后压紧段 0.18 m/s 继续倒 | WaitIO 夹爪抓住 → DOCKED；压紧 15 s 未抓住 → ABORT_EXIT；60 s → ABORT_EXIT |
| `DOCKED` | DOCKED_HOLD 零速；`success=true` | `/dock/undock` → UNDOCK_EXIT；`/dock/cancel` → IDLE |
| `REACQUIRE_TAG` | 入口外丢 Tag：预测位姿可用且近（\|x\|≤5 m）且会话预算 ≤10 s → APPROACH 朝虚拟坞位（**可能倒车**）；否则 HOLD/SEARCH | 重捕获 5 帧 → 按位姿路由回 APPROACH/ALIGN；30 s → needs_reapproach |
| `ABORT_EXIT` | EXIT_FORWARD 前进驶出；默认 `blind_exit_enabled=false`：**只有 VISION 才前进**，ODOM_PREDICTION/INVALID 都零速等待 | 到 x≤-4.0 → IDLE + needs_reapproach；45 s 或无视觉超 15 s → 见 §4.5.2 |
| `WAIT_DOCK_RELEASE` | HOLD；请求船坞抬爪（ControlDO） | 成功 → UNDOCK_EXIT；失败/超时 15 s → FAILED（禁止盲动） |
| `UNDOCK_EXIT` | UNDOCK_FORWARD 前进驶出；默认 `blind_exit_enabled=false`：只有 VISION 才动，无视觉零速等待 | 到 x≤-3.0 → UNDOCK_SETTLE；无 VISION 超 10 s → `UNDOCK_NO_VISION` FAILED；60 s → UNDOCK_TIMEOUT（见 §4.5.2） |
| `UNDOCK_SETTLE` | HOLD 1 s | → IDLE，`undock_success=true` |
| `FAILED` | HOLD 零速；`needs_manual_takeover=true` | 等 `/dock/cancel` 或 `/dock/start` 重新开始 |

> `usv_docking` 内部**不自动重试**：入泊失败回 IDLE/FAILED 并上报 `needs_reapproach`/
> `needs_manual_takeover`，重 Nav/重交接由 `dock_mission` 决定。
>
> **成功判据的现状**：自 2026-10-05 压紧段设计 / 2026-10-08 删除充电判据后，归港成功
> **统一以 WaitIO 夹爪抓住为准**，位置到位不再判 DOCKED。因此 `dock_claw_enabled=false`
> （无夹爪船坞）当前没有成功路径，FINAL_DOCK 会超时失败；兴飞船（带夹爪）按默认
> `dock_claw_enabled=true` 工作。换无夹爪船坞前必须补代码/改判据。

### 4.3 正常时序

**一键归港成功**：

```text
上层 → /gcs_dock/command {action:"one_click_dock", mission_id, command_id}
船   → /dock_task/event DOCK_TASK_ACCEPTED {mode:"one_click"}      （上层回 ACK）
       status: run_state=RUNNING, phase=STAGING, dock_active=true
船   → /dock_task/event DOCK_STAGING_STARTED                         （每次重试各一条）
       （Nav2 到点；SETTLE 实测停稳）
船   → /dock_task/event DOCK_HANDOFF
       status: phase=DOCKING
船   → /dock_task/event DOCK_SUCCEEDED {elapsed_sec, mode:"one_click"}
       status: run_state=IDLE, dock_active=false, mode=null
上层 ← 判定成功闭环（如需要，先 WaitIO 验证夹爪 → 2103）
```

**仅精靠泊成功**：

```text
上层 → /gcs_dock/command {action:"dock_only", ...}
船   → DOCK_TASK_ACCEPTED {mode:"dock_only"} → DOCK_HANDOFF → DOCK_SUCCEEDED
       （无 DOCK_STAGING_STARTED，无 SETTLE）
```

**出泊成功**：

```text
上层 → /gcs_dock/command {action:"undock", ...}
船   → UNDOCK_TASK_ACCEPTED {mode:"undock"} → UNDOCK_HANDOFF → UNDOCK_SUCCEEDED {elapsed_sec, mode}
       status: phase=UNDOCKING → IDLE
```

**出泊失败**：

```text
船   → DOCK_FAILED {reason:"UNDOCK_TIMEOUT"/"UNDOCK_NO_VISION"/"DOCK_RELEASE_FAILED"/...,
                    retry_count:0, needs_manual_takeover:(通常 false), needs_reapproach:false}
上层 → cancel（可选但建议）→ DOCK_CANCELLED → status IDLE
上层 → 按出泊会话映射 2106
```

### 4.4 失败、重试与人工接管

- **预泊失败**（`send_waypoints` 失败/超时、`TASK_FAILED`、`SETTLE_TIMEOUT`）：
  - `retry_count += 1`；`< staging_retry_max` → 重发预泊（`DOCK_STAGING_STARTED` 再发一条）；
  - `dock_only` → 直接回 `DOCK_HANDOFF` 重交接；
  - 达到上限 → `MANUAL_TAKEOVER_REQUESTED` → `DOCK_FAILED`。
- **精靠泊要求重接近**（`needs_reapproach`）：`one_click` 回预泊流程重试；`dock_only`
  直接重交接（`DOCK_HANDOFF`）；status `needs_reapproach=true`。
- **精靠泊要求人工接管**（`needs_manual_takeover`，如夹爪半抓、安全硬停、驶出未确认）：
  **不重试**，直接 `MANUAL_TAKEOVER_REQUESTED` → `DOCK_FAILED`。
- **人工接管后复位**：
  - 发 `cancel`：FAILED → CANCELLED → IDLE（幂等，会发 `DOCK_CANCELLED`）；
  - 或直接下新的 `/gcs_dock/command`（FAILED 也受理，新会话重置标志）。
- **失败终态**：`DOCK_FAILED` 是唯一失败事件；`status.run_state` 保持 `FAILED`，
  直到新命令/cancel。上层拿到事件后应主动发 `cancel` 收尾（Decision 的做法），
  避免船端停在 FAILED 状态。

### 4.5 盲倒/盲开：丢 Tag 后的推算驾驶边界（重点）

> 现场把“没有新鲜视觉、靠里程计推算继续倒船/驶出”统称为“盲倒/盲开”。当前四节点实现
> **没有无限制的盲倒**：倒船方向只有在 `pose_source=ODOM_PREDICTION` 时才允许继续，且有
> 明确的时间/距离门；一旦 `pose_source=INVALID`，所有倒船运动态立即零速。
>
> **2026-10-20 起默认取消出港盲开**：`docking.yaml: blind_exit_enabled=false`。
> 出泊只有 `pose_source=VISION`（后视相机能检测到二维码）才允许运动；无视觉原地
> 等待 `undock_vision_timeout_sec`（默认 10 s）后 FAILED（`UNDOCK_NO_VISION`），
> 不盲开、不报假成功。只有显式置 `blind_exit_enabled=true` 才恢复旧的
> `exit_blind_timeout_sec` 开环直行/`undock_unconfirmed_as_success` 行为。

#### 4.5.1 位姿来源的含义

| `pose_source` | 含义 | 能否继续倒船 |
|---|---|---|
| `VISION` | 当前有 Tag 测量，锚点新鲜 | 可以 |
| `ODOM_PREDICTION` | 最近看过 Tag，锚点仍活着；用 `odom→base_link` 推算船在坞系位姿 | **有界允许**（下表） |
| `INVALID` | 锚点丢失/超时（推算硬上限 70 s）或上游异常 | **不允许**：倒船运动态零速 |

#### 4.5.2 各状态的“丢 Tag/推算”边界

| 状态 | `ODOM_PREDICTION` 时 | `INVALID` 时 | 边界参数 |
|---|---|---|---|
| `APPROACH_ENTRY` | 继续按推算位姿倒退/对准 | 立即 `REACQUIRE_TAG`；控制器倒车零速 | 宽限 3 s（`approach_tag_loss_grace_sec`） |
| `ALIGN_ENTRY` | 继续小倒速弧线 | 立即 `REACQUIRE_TAG`；控制器零速 | 宽限 5 s（`align_tag_loss_grace_sec`） |
| `REACQUIRE_TAG` | 若 \|dock_x\|≤5 m 且会话预算 ≤10 s → `APPROACH` 朝虚拟坞位（**可能倒车/转向**）；否则 HOLD | HOLD（有 VISION 但 Tag 闪）或 SEARCH（纯旋转、不平移） | 距离门 5 m，预算 10 s（`reacquire_drive_max_dist_m`/`reacquire_drive_max_sec`），会话内累计不重置 |
| `BACK_IN` | HOLD 0~0.5 s → SEARCH_LIMITED（v=0，±8°）0.5~2 s → ABORT_EXIT | 同样按丢失时长分级；`measurement_age` 通常已 >2 s，下一次判定即 ABORT_EXIT | 0.5 s / 2 s（`back_in_tag_loss_hold_sec`/`back_in_tag_loss_search_sec`） |
| `FINAL_DOCK` | HOLD 等待，最多 2 s → ABORT_EXIT | 同样最多等 2 s；INVALID 时通常 `measurement_age` 已 >2 s，直接 ABORT_EXIT | 2 s（`final_dock_tag_loss_timeout_sec`） |
| `ABORT_EXIT` | 默认 `blind_exit_enabled=false`：**只有 `VISION` 才前进**；`ODOM_PREDICTION`/`INVALID` 都零速等待 `exit_blind_timeout_sec` → `ABORT_EXIT_UNCONFIRMED`。`blind_exit_enabled=true` 才开环恒速前进 | 同左（不盲开）；`true` 时开环 cap 15 s → `ABORT_EXIT_UNCONFIRMED` | 15 s（`exit_blind_timeout_sec`）、完整 45 s |
| `UNDOCK_EXIT` | **默认不动**：只有 `VISION` 才前进；`ODOM_PREDICTION` 也零速等待视觉 | 零速等待 `undock_vision_timeout_sec`（10 s）→ `UNDOCK_NO_VISION` FAILED；`blind_exit_enabled=true` 才开环前进（cap 15 s） | 10 s（`undock_vision_timeout_sec`）、完整 60 s |

补充：

- **REACQUIRE 的“盲倒”是受控的**：只在锚点仍活着（`ODOM_PREDICTION`）、船距坞 ≤5 m、
  本会话累计推算驾驶 ≤10 s 时，才会朝“虚拟坞位”做 APPROACH（可能倒车/转向）。
  超出任一条件立即退回 HOLD/SEARCH，不会一路把船带走。
  远场锚点噪声大（实测重定位 dp 0.77~1.21 m），所以不允许拿远场预测位姿驾驶。
- **BACK_IN/FINAL_DOCK 不会盲倒**：预测态只 HOLD/小角度搜索，2 s 内不恢复视觉就驶出重试。
  这是为了防“坞内盲倒顶错位置/撞坞”。
- **出坞/撤离默认不再“盲开”**：`blind_exit_enabled=false`（默认）时，UNDOCK_EXIT
  与 ABORT_EXIT 都必须 `VISION` 才动；`ODOM_PREDICTION`/`INVALID` 一律零速等待，
  超时失败/转人工。只有显式置 `true` 才恢复旧的开环直行（15 s 上限约 6.8 m 出泊 /
  4.5 m 撤离）。
- `ABORT_EXIT_UNCONFIRMED`：`needs_reapproach=false`、`needs_manual_takeover=true`——
  船位不明，**上层不要自动重试/派航线**，交人工确认。
- `UNDOCK_NO_VISION`：默认不盲开时等待 VISION 超时 → FAILED，`undock_success=false`；
  出泊会话以 `DOCK_FAILED` 报给上层（2106）。**没出去就是失败，不报假成功**。
- `UNDOCK_EXIT_UNCONFIRMED`（仅 `blind_exit_enabled=true` 时可能出现）：
  `usv_docking` 内部 `_fail` → `FAILED`、内部 `needs_manual_takeover=true`；
  出泊会话最终以 `DOCK_FAILED` 报给上层（2106）。注意 `dock_mission` 的
  `MONITOR_UNDOCK` 当前**不转发**该标志，事件里的 `needs_manual_takeover` 可能仍是
  `false`——上层应按“出泊失败”一律人工确认/报 2106。
- **临时旁路 `undock_unconfirmed_as_success`**（默认 `false`，仅
  `blind_exit_enabled=true` 时生效）：置 `true` 时，出泊盲开 15 s 位姿仍无效会按
  “人工确认驶出成功”处理，上报 `UNDOCK_SUCCEEDED`；status 里 `pose_source` 仍是
  `INVALID`。默认取消盲开后本参数不再参与正常流程。

#### 4.5.3 禁止盲动：夹爪半抓住保护

- `usv_docking` 在 `BACK_IN/FINAL_DOCK` 发 WaitIO 等夹爪抓住；feedback 的 `digital_input`
  的 bit0/bit1 任一置位，即记 `_claw_partial_mask`（爪子已扣住船体）。
- 此后坞内一切驶出路径（停滞/压紧超时/走廊违规/丢 Tag/安全请求/全局超时）**一律不驶出**，
  就地停车 `FAILED` + `needs_manual_takeover=true`；WaitIO 继续监视，两个夹爪都抓住仍判 DOCKED。
- 出泊 `WAIT_DOCK_RELEASE` 抬爪失败/超时 → `FAILED`（`DOCK_RELEASE_FAILED/TIMEOUT`），
  **禁止盲动**，需人工处置。
- 上层看到 `needs_manual_takeover=true` 时不要自动重试或派航线；先人工确认夹爪/船位。

#### 4.5.4 背光与检测通道（与盲倒相关）

- **归港**：`usv_docking` 在 `/dock/start` 用 SetDO 点亮船坞背光（DO bit1），
  **整个归港会话保持**并按 20 s 保活；失败/重试不关灯，DOCKED、`/dock/cancel` 才关。
- **出港**：进入 `UNDOCK_EXIT` 时用 **ControlDO start=true 按位控制**：
  - 有夹爪且 `dock_claw_release_on_undock=true`（兴飞）→ `mask=0x0003`
    （夹爪 bit0 + 背光 bit1，**开闸 + 开灯**）；`WAIT_DOCK_RELEASE` 抬爪后
    FSM 再发一次，保持到驶出；
  - 无夹爪/不抬爪 → `mask=2`（只开灯）。
  进入 `UNDOCK_SETTLE` 写 DO 0 关灯；驱动 60 s 后也会自动全清。
- `dock_mission` 在进入 SETTLE / DOCK_HANDOFF / UNDOCK_HANDOFF 时打开 apriltag 检测通道，
  成功收尾关闭；`dock_only` 在 DOCK_HANDOFF 补开。
- `/dock/in_dock` 查询在无会话且位姿无效时，会用 **ControlDO mask=2** 点背光 + 开通道
  （见 §2.4），查完用 SetDO 0 关灯。
- 这些动作都是船端自动行为，上层不需要、也不应该直接控制 DO/通道。

## 5. 特殊情况码（21xx）映射

`/dock_task/event`、`/dock_task/status` 不直接携带 21xx（`error_code` 恒 0）。
上层按 `reason` 归类。**当前 Decision 的实际映射**如下（以
`decision_core/include/decision/actuator/dock_failure_code.hpp` 为准，优先级从上到下）：

| 条件 | 码 |
|---|---|
| `DOCK_FAILED.detail.task_code` 存在且在 `2101..2107` / `2010` / `2019` | 直接采信（船端当前不发） |
| `reason` 含 `safety`（`SAFETY:*`，含出泊期） | `2010` |
| **出泊会话**中的任何 `DOCK_FAILED`（不再往下归类） | `2106 UNDOCK_FAILED` |
| `reason` 含 `rtk_offline` / `rtk_blockout` | `2019` |
| `reason` 含 `undock`（如 `UNDOCK_TIMEOUT`） | `2106 UNDOCK_FAILED` |
| `reason` 含 `staging` / `reapproach`（预泊导航重试耗尽） | `2104 DOCK_STAGING_NAV_FAILED` |
| `reason` 含 `charge`（充电确认超时） | `2107` |
| `reason` 含 `tag_lost`（`TAG_LOST_IN_BACK_IN`/`TAG_LOST_IN_FINAL_DOCK`） | `2102 DOCK_APPROACH_FAILED` |
| `reason` 含 `tag` / `pose_unavailable` / `acquire` | `2101 DOCK_NOT_FOUND` |
| `needs_manual_takeover=true`（以上都归不了类） | `2105 DOCK_MANUAL_TAKEOVER_REQUIRED` |
| 其他（含各种 `*_TIMEOUT`、`CORRIDOR_VIOLATION`、`FINAL_DOCK` 判稳失败） | `2102 DOCK_APPROACH_FAILED` |

补充：

- **2103 `DOCK_LOCK_FAILED` 不从 `DOCK_FAILED.reason` 映射**。它的信号源是
  上层在收到 `DOCK_SUCCEEDED` 后对 `/wait_io` 的夹爪锁定确认：
  - 抓夹合上 → 采信成功；
  - 抓夹未合上 / 探不出（`wait_io` 不在线）→ 2103；
  - `dock_presence_required=false` 时允许“探不出也采信成功”（现场无 IO 时的放行开关，
    不改变 2103 的正常语义）。
- 2104 只在**重试耗尽**时才上报；重试期间保持 `RUNNING`。
  **注意当前映射口径**：上层只按 `reason` 是否含 `staging`/`reapproach` 判 2104；
  而船端预泊重试耗尽的 `reason` 可能是 `SETTLE_TIMEOUT: ...`、`send_waypoints ...`、
  `nav task failed` 等不含上述关键字的串，此时会落到 2102/2105。
  若需要稳定的“预泊导航重试耗尽 → 2104”，建议船端在 `DOCK_FAILED.detail` 里补
  `task_code: 2104`（上层已支持该字段），或上层结合 `mode/retry_count/retry_max/
  needs_reapproach` 自行归类。
- 上层自身的受理/状态/执行超时（`dock_accept_timeout_s=5`、`dock_status_timeout_s=3`、
  `dock_execution_timeout_s=600`）→ `2011`（等待取消确认）。
- `DOCK_CANCELLED` → `2005`（任务取消）。
- `/dock_task/status` 的 `run_state`、`phase` 只用于进度展示，**不要**用它们替代事件做终态。
- 码的语义/阻断策略以船端仓 `docs/特殊情况码V0.2.md` 为准；本仓 `docs/特殊情况码汇总.md`
  只到 2103，已过期。

## 6. 互斥与前置条件（上层须知）

1. **与主导航任务互斥**：归港预泊通过 `mission_bridge/send_waypoints` 下发，会**抢占**正在
   执行的航线任务（老通道抢占语义）。上层应保证：主导航任务结束/取消后再下归港；
   归港会话期间不要再下发新航线。
2. **在坞先出泊**：船在坞内时派航线/单点任务，先调 `/dock/in_dock` 确认，再发 `undock`，
   等 `UNDOCK_SUCCEEDED` + status IDLE 后再派航线（§2.5.3）。
3. **速度互斥由船内保证**：精靠泊阶段 `/cmd_vel_nav` 由 `usv_docking` 接管；停稳静默后交还；
   速度桥（`usv_ardupilot_velocity_bridge`）有 1 s 看门狗兜底清零。
4. **触发幂等**：`cancel` 任何时刻可发；重复 `one_click_dock` 在忙时静默拒绝，
   以 `*_TASK_ACCEPTED` 为受理凭据。
5. **无心跳即失效**：`/dock_task/status` 5 Hz；超过 3 s 无新帧视为归港栈离线（上层兜底告警）。
6. **事件服务必须先起**：上层是实现 `/dock_task/event` server 的一方；若未实现/未起，
   船端会累计 `event_ack_failures` 但继续归港。正式对接必须起 server 并回 ACK。
7. **触发前确认泊位已标定**：`bay_id` 指向的泊位已在船端 `config/dock_database.yaml`
   用 RTK 标定；上层不指定预泊点时省略 `dock_lat`/`dock_lon` 或填 65536 哨兵均可（§2.1.1）。
8. **相机/视觉链**：精靠泊与 `/dock/in_dock` 都依赖后视相机 + AprilTag；相机故障时
   精靠泊会按 §4.5 的边界失败，出泊默认**不再盲开**（`blind_exit_enabled=false`），
   原地报失败。相机故障由上层状态机通过 `/sensor_health` 自己检测；`/dock/in_dock`
   只返回 `INVALID`/`NONE`，不额外上报相机故障。上层收到相机故障告警应拒绝归港/
   出泊任务（船端上层已有 FRONT_CAMERA/REAR_CAMERA 阻断）。

```bash
# 触发（推荐，带 id）
ros2 topic pub --once /gcs_dock/command std_msgs/msg/String \
  "{data: '{\"action\": \"one_click_dock\", \"mission_id\": \"m001\", \"command_id\": \"c1\"}'}"

# 取消
ros2 topic pub --once /gcs_dock/command std_msgs/msg/String "{data: '{\"action\": \"cancel\"}'}"
ros2 service call /dock/mission/cancel std_srvs/srv/Trigger "{}"

# 观察（上层对接依据）
ros2 topic echo /dock_task/status
ros2 topic echo /dock_task/event_log     # 可选观察流（事件 JSON，不保证送达）

# 在坞查询（出泊/派航线前）
ros2 service call /dock/in_dock m_common/srv/QueryInDock "{wait_vision: true}"

# 背光/出港 DO（ControlDO 新接口带 uint16 mask）
ros2 action send_goal /control_do usv_rs485_driver/action/ControlDO \
  "{start: true, mask: 2}"        # 只开灯（在坞查询）
ros2 action send_goal /control_do usv_rs485_driver/action/ControlDO \
  "{start: true, mask: 3}"        # 夹爪+背光（出港）

# 船内联调（不要作为上层接口）
ros2 topic echo /dock/status             # usv_docking 原始 JSON（success/pose_source/abort_reason...）
ros2 topic echo /docking/state           # ACQUIRE_TAG/BACK_IN/...
ros2 topic echo /dock/mission_status     # dock_mission 内部状态

# 事件上报 service（上层实现 server 前，可用 mock 顶替）
python3 scripts/dock_test/mock_event_server.py   # 回 ACK，打印收到的事件
ros2 service call /dock_task/event m_common/srv/DockTaskEvent \
  "{event: 'DOCK_SUCCEEDED', mission_id: 'm001', command_id: 'c1', detail: '{\"elapsed_sec\": 142.5, \"mode\": \"one_click\"}', stamp_sec: 0.0}"
```

> 船端 ROS CLI 偶发卡死（服务调用全超时）；优先用 `rclpy` 小脚本查话题/服务，
> 确需 CLI 时套 `timeout`。

| `settle_max_speed` | 0.15 m/s | 停稳线速度门 |
| `settle_max_yaw_rate` | 0.1 rad/s | 停稳角速度门 |
| `settle_still_hold_sec` | 0.5 s | 连续停稳保持时间 |
| `settle_min_still_frames` | 3 | 最少有效速度帧 |
| `settle_timeout_sec` | 15 s | 停不稳 → 预泊重试 |
| `complete_settle_sec` | 2.0 s | 成功后收尾 |
| `event_ack_timeout` | 3.0 s | 事件 ACK 超时（不阻塞 FSM） |
| `send_waypoints` 响应超时 | 12 s（代码硬编码） | 预泊下发失败 → 重试 |
| `cruise_xy_goal_tolerance` | 2.0 | 巡航到点容差（与 Nav2 general_goal_checker 一致） |

| `docking_yaw_goal_tolerance` | 0.4 | 预泊到点艏向容差（rad） |
| `in_dock_x_min` / `in_dock_x_max` | -1.5 / 1.0 | 在坞区域（dock 系） |
| `in_dock_y_max` | 0.6 | 在坞横向范围 |
| `in_dock_pose_max_age_sec` | 1.5 | 位姿缓存龄期 |
| `in_dock_prediction_max_age_sec` | 3.0 | ODOM_PREDICTION 最大推算龄期 |
| `in_dock_vision_timeout_sec` | 6.0 | `wait_vision=true` 等视觉上限 |
| `in_dock_restore_channel` | true | 查询后恢复通道/背光 |
| `control_do_action` | `control_do` | 点背光用 ControlDO（mask=2 只开灯不松闸） |
| `set_do_service` | `set_do` | 关背光用 SetDO 写 0 |
| `in_dock_backlight_mask` | 2 | 背光 DO bit1 |
