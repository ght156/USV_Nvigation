## 三、证据

### 3.1 mission_bridge 逐点下发（`python3_68486...log`）

24 航点任务的片段（时间已换算）：

```
16:56:31  Sending waypoint  1/24 x=247.42, y=147.97, yaw=30.727   → 17:57:17 到点（46 s）
16:57:29  Sending waypoint  2/24 x=247.51, y=147.97, yaw=0.000    → 33 s（腿长 0.09 m）
16:57:33  Sending waypoint  3/24 x=247.70, y=147.97, yaw=0.000    →  3 s（腿长 0.19 m）
16:57:35  Sending waypoint  4/24 x=247.42, y=147.86, yaw=-158.654 → 16:59:24 到点（109 s，腿长 0.30 m）
16:59:45  Sending waypoint 11/24 ...                              → 134 s
17:03:47  Sending waypoint 14/24 x=225.96, y=137.95, yaw=-26.221  → 295 s
17:07:02  Sending waypoint 22/24 x=242.39, y=151.76, yaw=143.268  → 313 s
```

**要点 1：到点 yaw 用的是"行进方向"，不是平台的 0。**
`-158.654` = 上一航点 (247.70, 147.97) → 本航点 (247.42, 147.86) 的方位角；`-26.221` 同理。所以"每个航点都要朝东"的情况本次**没有发生**。

**要点 2：短腿的"行进方向"是噪声。**
2/3/4 号航点腿长只有 0.09 / 0.19 / 0.30 m —— 用 `atan2` 算 0.3 m 线段的方向毫无物理意义，算出来是 `-158.654°`（几乎掉头）。船当时大致朝东，于是被迫原地转约 158°。

### 3.2 控制器：反复判"没进展"（`component_container_isolated_68484...log`）

```
16:35:35 ERROR controller_server: Failed to make progress
16:36:05 ERROR controller_server: Failed to make progress     ← 恰好 30 s 一次
16:38:15 / 16:38:45 / 16:39:43 / 16:40:13 ...
16:58:05 / 16:58:35 / 16:59:06  （对应上面 4 号航点的 109 s）
```

本会话共 **29 次 `Failed to make progress`**、32 次 `Reached the goal`、4 次 `RegulatedPurePursuitController detected collision ahead!`、**51 次清代价地图**（local 31 / global 20）。每次进度检查失败都会：中止 FollowPath → BT 内层清局部代价地图重试一次 → 再失败 → 外层 `NavigateRecovery`（`number_of_retries=6`）跑 RoundRobin 恢复（清图 → Spin 90° → Wait 5 s → BackUp 0.3 m）。

判据来自 `SimpleProgressChecker`：**只统计平移**，`required_movement_radius: 2.0` / `movement_time_allowance: 30.0`（`nav2_params_real_mavros.yaml`）。而 goal checker 的 `xy_goal_tolerance` 也是 **2.0** —— 两者相等，任何短于 2 m 的腿都无法"走出进展"，只能靠 goal checker 先判到达。

### 3.3 恢复行为全部在 1 s 内自我中止（同一份日志）

```
[INFO]  [behavior_server]: Running spin
[INFO]  [behavior_server]: Turning 1.57 for spin behavior.
[ERROR] [behavior_server]: Pose Goes Off Grid.
[WARN]  [behavior_server]: Collision Ahead - Exiting Spin

[INFO]  [behavior_server]: Running backup
[ERROR] [behavior_server]: Pose Goes Off Grid.
[WARN]  [behavior_server]: Collision Ahead - Exiting DriveOnHeading
```

统计：`Running spin` 13 次、`Running backup` 12 次、`Running wait` 13 次，而 `Pose Goes Off Grid` / `Collision Ahead - Exiting` 各 **25 次** —— **每一次恢复动作都被判越界中止**。

原因在配置：`behavior_server.global_frame: map`，而它做碰撞检查用的 `costmap_topic: local_costmap/costmap_raw` 是 **odom** 系。拿 map 坐标（如 x≈225）去查一个 20×20 m 的 odom 滚动窗口必然出界。`nav2_costmap_2d::CostmapTopicCollisionChecker::scorePose()` 里 `worldToMap` 失败即抛 `Pose Goes Off Grid.`，行为随即判 `FAILED`。

### 3.4 状态聚合与速度桥的旁证

```
[ERROR] [nav_status_aggregator]: controller STUCK | no_progress=12.0s last_move=0.14m
[ERROR] [nav_status_aggregator]: controller STUCK | no_progress=12.0s last_move=0.21m
```

12 s 只挪 14~26 cm，说明那几段船基本没有平移。速度桥侧则是每次中止/到达后 1 s 看门狗清零：

```
[WARN] [ardupilot_velocity_bridge]: Velocity command timeout 1.00s exceeded, publishing zero command
```

另外该会话多次出现 `Control loop missed its desired rate of 20.0000Hz` / `Planner loop missed its desired rate of 2.0000 Hz`，Jetson 负载偏高会拖慢控制环（次要因素）。

## 四、根因

| # | 根因 | 状态 |
|---|---|---|
| A | **短腿航点用自身行进方向补 yaw**：0.1~0.3 m 的示教碎点算出噪声航向（如 -158.7°），船被迫原地对朝向；而进度检查只认平移、30 s 判一次 → 必然失败重试 | 已确证 |
| B | **mission_bridge 的跳过阈值与 Nav2 到达判定不同源**：`waypoint_tolerance_m=1.5` < `xy_goal_tolerance=2.0`，这些碎点既跳不掉、又被 Nav2 判到达 | 已确证 |
| C | **`behavior_server.global_frame` 与它订阅的代价地图坐标系不一致**（map vs local_costmap=odom），恢复行为 25/25 全部 1 s 内中止，等于没有恢复 | 已确证 |
| D | 卡顿集中在 (x≈225~232, y≈134~142) 一小片区域（mission A 的 4/5 号点、mission B 的 14 号点、以及 `planner could not reach target` 的点都在这里），疑有持续障碍 / 未知格 / 水花假障碍导致代价缩放把速度压到近 0 | **待验证**（缺 bag） |
