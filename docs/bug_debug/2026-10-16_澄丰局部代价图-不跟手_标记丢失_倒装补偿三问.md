## 二、现象与结论（三条，按出现顺序）

### 2.1 局部代价图"不跟船" —— 是工具的节流，不是代价图

船端各路实测都新鲜：

| 通道 | 实测 |
|---|---|
| `/local_costmap/costmap` | `update_frequency`/`publish_frequency` 5.0，header age ≈ 2 ms |
| `/mavros/gps_input/local`（定位源） | 9.9–10.0 Hz |
| `odom→base_link` TF | 9.5–10 Hz |
| 滚动窗口中心 | 与船在 odom 的位置一致（差 5 cm），即**窗口在跟着船** |

原因：网页 `resubscribeRosTopics()` 把**局部代价图节流到 1000 ms**、TF 节流 200 ms。
局部代价图是 odom 系 20×20 m 滚动窗口，1 Hz 时窗口中心最多落后船 1 秒（遥控开船 ≈1 m），
肉眼就是"方框不跟船"。**已改**：代价图 `throttle_rate: 1000 → 250`、`/tf: 200 → 100`。

### 2.2 "Sensor origin ... out of map bounds" + 代价图整窗被清空/标记丢失

nav 窗口刷：

```
[local_costmap]: Sensor origin at (1.65, -0.01 0.36) is out of map bounds (-23.50, -25.10, -0.20)
  to (-3.55, -5.15, 0.95). The costmap cannot raytrace for it.
```

(1.65, -0.01, 0.36) 正是「船在 odom 原点附近」时才成立的杆臂偏移，而窗口中心在 (-13.5, -15.0)。
出现时间点与**船用遥控开动、odom 位姿发生大跳**（EKF 本地原点重设）重合，属跳变瞬间的短暂状态；
之后窗口正常居中、警告停止。期间实测 `/tf` 上 `odom→base_link` 只有一族取值（-11.79, -16.15, +15.2°），
`map→odom` 恒定（见 2.4），没有第二个发布者。

**教训**：出现"传感器原点不在窗口内"时，先看 `odom→base_link` 是否刚发生过跳变，别急着改参数。

### 2.3 代价图致命格归零 —— 来自一次驱动外参实验（已回滚）

排查"岸边左右反"时试过：把 `livox_ros_driver2` 的 `pub_handler.cpp:132`
`packet.extrinsic_enable = false → true`（= 不再对每个点乘外参旋转），重编后重启雷达。
结果是**局部代价图从此一个致命格都没有**（`致命格=0`），而按同一套规则复算应有 700~1100 格；
`mark_threshold=0`、`clearing=false` 两个在线实验都无效；体素层有数据但 2D 不标。
把驱动改回原样（备份 `pub_handler.cpp.bak-20261016-175446`）重编重启后**立即恢复**：
`致命格=5175`，且复算的"应标"格命中 778/788。

→ **保持驱动原样**：`extrinsic_enable = false`（驱动照旧对点云做外参旋转）。

### 2.4 岸边"左右反" —— 现场看是对的，未改

排查过程中把三处 180° 都数了一遍（**结论：当前组合是对的，别按"重复纠正"去删任何一处**）：

| 位置 | 内容 | 证据 |
|---|---|---|
| 雷达驱动（config 推给雷达） | `MID360_config.json` `extrinsic_parameter.roll = 180`（src + install 两份）经 `call_back/livox_lidar_callback.cpp:92-102` 用 `SetLivoxLidarInstallAttitude()` 推给雷达 | 日志 `successfully set lidar attitude` |
| 雷达驱动（对每个点） | 同一组外参经 `lds_lidar.cpp:160-180` → `pub_handler.cpp` 的 `extrinsic_.rotation` 逐点应用（`extrinsic_enable=false` 走 else 分支） | `pub_handler.cpp:370/398/432` |
| TF | `base_link → livox_frame` = (1.60, 0, 0.36) + **quat(x,y,z,w)=(1,0,0,0) → roll = +180°** | `ros2 run tf2_ros tf2_echo base_link livox_frame` |

TF 那份来自 `usv.xacro` 的 `livox_rpy = ${pi} 0 0`（注释明确"Mid360 当前为倒装"），
由 `usv_localization/launch/usv_map_odom_tf.launch.py` 起 `robot_state_publisher` 加载，
`robot_description_file` 默认 `~/usv/src/usv_transforms/urdf/usv.xacro`（全仓无覆盖）。
**`/livox/imu` 实测 z ≈ -1.0 g（负）→ IMU 数据也在倒装系**，与 TF 的 roll=π 语义一致。

现场以静态地图岸线为基准做左右对照时，代价图标记与地图岸线**同侧**；
去掉驱动那次旋转后代价图直接空掉（2.3），所以**维持现状**：
驱动旋转 + TF roll=π 一起构成"能标记且朝向正确"的组合。

## 五、顺带发现 / 待办

1. **`map→odom` 是常数**（本场次一直是 x=222.19, y=153.03, yaw=140.0°）→ 船在 map 里的位置
   完全由 odom（mavros INSPVAA/GNSS 局部位置）死推，GNSS 不再修正 map↔odom。长期漂移会直接
   变成地图漂移，值得单独查 `usv_map_odom_tf` 的设计意图。
2. **雷达正前方近场遮挡**：约 82% 回波落在雷达 0.2 m 以内、90% 集中在正前方 ±15°，
   导致 2~10 m 中距几乎无回波。建议现场确认雷达前方是否有挡板/线缆/罩子（或镜头脏污）。
3. `inflation_radius: 5.0` 会让每个障碍糊出 5 m 光晕，视觉上"代价图一大片"；
   若只想要"看得见的障碍"，可评估降到 1.5~2.5（需配合 RPP `cost_scaling_dist` 一起看）。
4. 本次未改任何 yaml 参数；如需把 `mark_threshold` 或 `inflation_radius` 调优，改 yaml + 重启 nav 栈
   （观测源类参数在线改是 phantom，实测 `clearing=false` 在线改无效）。
