# 2026-10-14 Mid-360S 雷达钟超前 UTC（GI320 NMEA 小数秒历元 × Livox 同步算法）

## 一、基本信息

| 项 | 值 |
|---|---|
| 日期 | 2026-10-14（hkzl 船端，4G 链路 + SDK2/UDP/gpsd 只读测量 + 现场示波器） |
| 影响面 | 点云时间戳、点云落图、bag 对齐、与 TF/INSPVAA 时基对比 |
| 状态 | **根因定案**：GI320 的 NMEA（GPRMC/GNGGA）时间字段带非零小数秒（历元不对齐 UTC 整秒），Mid-360S 的 GPS 同步算法把 RMC 小数秒一并采用，雷达钟继承该相位。待办：现场确认串口 RMC、找北微问历元对齐配置。**2026-10-16 澄丰复测见 §九**：雷达转 NoSync（驱动回退主机钟）、GI320 又回到 .15 相位 |

## 二、现象

雷达（192.168.2.191，SN ARMCP8B0031562，固件 35.01.01.08）点云时间戳
超前主机时钟，且**每次上电数值不同**：10-10 测得 0.47~0.57 s，
10-14 上午 +0.19 s，10-14 下午整机重启后 +0.44 s，雷达单独软重启
（Livox Viewer Reboot）后仍为 +0.44 s。

**澄丰船复测（2026-10-14 傍晚，ssh nx）**：同样存在。雷达 UDP 裸包
time_type=2，时间戳超前主机 **+0.242 s**（15 秒稳定，抖动 <1 ms）；
ROS `/livox/lidar` header age -0.14 s（= 超前 0.24 s 减去 100 ms 帧首
口径，一致）。同船 GI320 健康：GGA 小数秒 `.00`、INSPVAA 与主机差
-5 ms。即：两条船、两台雷达、两台 GI320，同构问题复现。

## 三、根因（2026-10-14 下午定案）

**证据链：**

1. 主机钟：chrony 锁阿里云 NTP，±3.5 ms，可信基准。
2. 雷达 UDP 原始包头时间戳超前主机（ROS 未开，排除驱动加工）。
3. SDK2 内部状态：sync_type=2（GPS 同步），`time_offset` ≈ -5 µs
   （雷达跟 PPS 跟得很紧，雷达自身无故障），`last_sync_time` 小数部分
   恒为 `.450000`（上午为 `.200000`）。
4. 示波器（现场）：TTL 侧 PPS 为正常 1 Hz 方波，无问题。
5. 雷达软重启后偏移不变（+0.44 → +0.44）→ 偏移由输入信号确定性产生，
   不是坏时刻锁存。
6. **GI320 网口 GNGGA 实测（决定性）**：

   ```
   GNGGA 时间字段 = 090107.45   到达相位 = 整秒后 0.524 s
   ```

   **GI320 的 NMEA 时间字段带小数秒 .45**——GNSS 解算历元在整秒后
   0.45 s，报文内容时间准确（到达即发，仅 ~75 ms 传输延迟），
   只是历元相位不在整秒上。同源的 INSPVAA（INS 解算）历元严格对齐
   20 ms 整数网格（x.900/x.920/...），与主机钟差 -6.5 ms——
   **同一台 GI320，INS 口与 GNSS NMEA 口的历元相位不同**。

**机制：** Mid-360S 的 GPS 同步在 PPS 沿把 GPRMC 时间字段（**含小数秒**）
写入时钟。PPS 沿在真 UTC 整秒，RMC 字段是 `hhmmss.45` → 雷达钟被写成
整秒 +0.45 s → 超前 0.45 s。偏移量 = GI320 NMEA 的小数秒，逐次开机
不同（.20/.45/0.5x）是因为 GI320 的 NMEA 历元相位随解算状态变化。

**补充（10-14 傍晚进一步实验）：** GI320 断电重启后其**网口** GGA 小数秒
归正为 `.00`，但兴飞雷达偏移变成 `.70` 且对雷达做 Viewer 软重启也不变。
说明**喂雷达的串口 GPRMC 的历元相位与网口 GGA 相互独立**的可能性存在，
最终以现场 USB-TTL 抓串口 GPRMC 原文为准。

**澄丰船决定性验证（10-14 傍晚）**：GI320 断电重启 → GGA 从首次定位起
小数秒即为 `.00`（DGPS→RTK 浮点全程），到达相位整秒后 44 ms（教科书形态）。
**雷达（未重启）偏移随之从 +0.242 s 自动收敛到 +0.008 s**——雷达钟实时
跟随 GI320 串口 GPRMC 的小数秒相位，铁证闭环。澄丰船恢复后：
雷达 +6~8 ms、INSPVAA +6 ms、GGA `.00`，三路时基一致。

**串口 GPRMC 原文证据（10-12 现场 USB-TTL 抓包，4.5 小时）**：
报文格式本身正常（`$GNRMC,hhmmss.ss,A,...` 状态位 A、校验正确），
但**时间字段小数秒是 50 ms 的整数倍且随会话跳变**，实测序列：
`.05 → .25 → .50 → .10 → .15 → .00 → .35 → .55 → .70 → .65`。
即 GI320 内部按 20 Hz（50 ms 量子）解算，NMEA 历元相位停在哪一格
是随机的、每次上电/会话不同。抓包数值与雷达偏移一一对应：
`.25` ≈ 澄丰 +0.242 s、`.70` = 兴飞 +0.694 s、`.20`/`.45` = 兴飞
上午/下午偏移。报文传输延迟正常（历元后 50~260 ms 发出）。

**操作规程（治本前的临时措施）**：整机/设备上电顺序应为
**先 GI320 定位正常（RTK 固定/浮点），后雷达上电**；若雷达已有亚秒级
偏移，重启 GI320 并待其定位正常后，雷达偏移会自动收敛（澄丰验证），
如不收敛再断电重启雷达。

所有历史观测（0.19 / 0.44 / 0.47~0.57、示波器正常、重启不变、
time_offset 微秒级）全部自洽。

## 八、2026-10-15 现场拔线验证（兴飞 hkzl，闭环"授时线到底喂了谁"）

**现场操作**：现场把雷达的授时线拔掉，随后对雷达整机断电重启。全程船端
只读测量（被动 UDP 监听 + `/livox/lidar` 订阅），唯一一次写操作是
`/tmp/livox_timesync/tsync_query` 用**驱动自身配置**
（`MID360s_config.json`）握手（把目的端写回 host 192.168.2.101:56301 /
imu 56401，等同驱动重启时的常规行为）。

### 8.1 拔线但**不**重启雷达：与"还连着"几乎不可区分

| 判据 | 实测 |
|---|---|
| 报文同步类型 | `time_type=2`（仍自报 GPS 同步） |
| 雷达超前主机 | **+0.5169 s**（6 分钟逐秒均值；即时采样 +0.5096 s） |
| 6 分钟漂移率 | **+0.013 ms/min（0.22 ppm）**，残差 0.6 ms |
| 主机钟基准 | chrony 锁阿里云 NTP，system time 差 5 ns、RMS 1.3 ms |
| GI320 网口 GGA 相位 | 小数秒 `.00`（同驱动的 INSPVAA 报 `.030`，非截断） |

**判读**：相位冻结在旧值（`.50` 那一格）、速率保持——因为数字锁相环的
频率修正量在失去输入后会保留，晶振短时间内仍跑在 ±1 ppm 内。所以
"拔线不重启"时，雷达的**相位不跳、速率不变**，与"仍在被外部纠正"
在几分钟尺度上无法区分（这正是 10-14 只能靠相位量级做判据的原因）。

### 8.2 断电重启后（SDK2 直读内部状态）：授时彻底没了

```
[q28] ret_code:32 param_num:31 sync_type=0
  time_offset    = 0 ns
  local_time_now   00:18:06.864238600 UTC     # 开机以来约 18 分钟
  lidar_minus_host = -1792029834.96 s         # ≈ 1970 纪元 → 计时自开机
  last_sync_time   00:00:00.000000000 UTC     # 重启后一次都没同步过
  last_sync_age    = 1086.9 s
  key 0x0006 host_ip:192.168.2.101 host_port:56301 lidar_port:56300
  key 0x0007 host_ip:192.168.2.101 host_port:56401 lidar_port:56400
```

`sync_type` 由 2（GPS）变 0（无同步）、`last_sync_time` 归零、内部钟只是
开机计时 → **拔掉的那根线确实是雷达的授时输入**；10-14 及 10-15 上午测到的
`+0.5x s` 是"拔线前最后一次同步锁存下来的相位"。

### 8.3 点云恢复正常（时间戳回到主机基准）

SDK 会话把目的端按驱动配置写回后，`/livox/lidar` 立即恢复：
20064 点/帧 @ 10 Hz，header `age` 恒 **+0.104 s**（10 Hz 帧首口径），
**超前偏差消失**。即：拔掉授时线后，时间戳由驱动侧对齐主机，短时可用，
但雷达内部是自由振荡晶振（无绝对 UTC），长时间会有 ppm 级漂移，
每次重启需重新对齐。

### 8.4 两个复现到的坑（与 §六 注意事项①一致，已实测复现）

1. **雷达断电重启前，驱动"发现不到雷达"**：08:57 和 09:30 两次启动的
   驱动只打印到 `Init lds lidar success!`，`/livox/lidar` 发布者数 0；
   `ss` 显示只有 56000 探测 socket，从未建命令/数据通道；独立 SDK 会话
   亦报 `no lidar found`（已排除端口占用）。同时雷达侧一切正常：点云
   2083 包/秒送 56301、430 B 心跳送 56201、48 B 握手广播送
   255.255.255.255:56000。**雷达断电重启后驱动即恢复**（10:04 那次启动
   日志出现 `livox/lidar publish use PointCloud2 format`）。
2. **SDK/Viewer 会话结束后雷达会回到"等主机"状态**：不再往本机发点云与
   心跳，只剩 1 Hz 握手广播（56000）；此时必须重启驱动/栈，驱动才重新

### 8.5 本次结论与待办

## 九、2026-10-16 澄丰 NX 复测（雷达转 NoSync；驱动回退主机钟；GI320 又回到 .15 相位）

**背景**：接着 10-15 的结论，在澄丰船（`ssh nx`，栈用 `start_nx_stack.sh` 那一套：rtk 10:04 /
mavros 10:04 / 定位 10:05 / nav2 10:05 / livox 驱动 10:10）复测「雷达时间还会超前吗」。

| 项 | 实测（2026-10-16 10:05–10:15） | 判读 |
|---|---|---|
| 雷达 UDP 裸包（10:05、10:09，驱动还没起） | `time_type=0`（**NoSync**），点云 ~2065 包/s、握手包 0；雷达时间戳 = 上电计时 2268 s → 2498 s（与 09:27 上电吻合，1:1 走动） | 雷达当前**没在跟 GPS**，钟自由振荡；不存在"超前 0.2~0.5 s"那种形态 |
| `/livox/lidar` header age（10:13，驱动 10:10 起） | med **+0.1398 s**（min +0.1352 / max +0.1436，spread 8.4 ms），10 Hz | **不超前**：0.10 s 帧窗口 + ~40 ms 处理/传输。对照 10-14（雷达钟 +0.24 s 时 age 会变负） |
| `/usv_map_pose` header age | +0.0013 s | 定位/里程计侧正常 |
| `/gi320/gngga`（1 Hz） | NMEA 时间字段小数秒**恒为 .15**（`stamp.nanosec = 150000000`，仍是 50 ms 量子）；到达相位 +0.0498 s；**RTK 固定(4)、40 星、hdop 0.40** | GI320 定位健康，但 NMEA 历元**又停在小数秒 .15 这一格**（10-12/10-14 记录的同一类形态） |

**为什么"不超前"——驱动代码级证据**（船端 `~/ws_livox/src/livox_ros_driver2`）：

- `src/comm/pub_handler.cpp:265-275` `GetEthPacketTimestamp()`：只有 `time_type` 为
  PTP/GPTP 或 GPS 时才采用雷达自己的时间戳，**否则 `return std::chrono::high_resolution_clock::now()`
  —— 直接退回主机墙钟**；
- `src/comm/pub_handler.cpp:388/416/451`：`point.offset_time = pkt.time_stamp + i * pkt.point_interval`，
  再经 `src/lddc.cpp:404/408` 成为 `cloud.header.stamp`。

即：雷达一旦 NoSync，**ROS 侧整条时间戳退到主机钟**（帧头 = 收包时刻，逐点是帧头 + 帧内偏移），
`is_timestamp_sync_` 也随之为 false（`pub_handler.cpp:105`），`CheckTimer` 的整秒对齐分帧逻辑不走。
所以"当前不超前"是**回退兜底**的结果，不代表授时正常 —— 代价是点云时间轴完全跟着主机收包抖动走
（跨机对齐、bag 事后对齐要留这个心眼）。

**结论与现场待办**：

1. 澄丰雷达现在是 **NoSync**（≈ §8 兴飞"拔线"后的状态），不是 10-14 的"超前"；ROS 有主机钟兜底，
   表面看不出异常，但**没有绝对时基**。
2. GI320 健康（RTK 固定、40 星）而雷达仍不同步 → **先查雷达那根授时线**（GI320 的 GPRMC/PPS
   到雷达的接线/插头，或 GI320 串口输出是否被关）。按 10-14 的机制雷达是实时跟随 GPRMC 的，
   线通 + GI320 健康就该看到 `time_type=2`。
3. 雷达一旦重新锁上同步，按 10-14 机制它会继承当前 GI320 的 **.15 相位 → 雷达钟超前约 0.15 s**，
   也就是"超前"会以 +0.15 s 回归。**治本仍是问北微把 GPRMC/GGA 历元对齐整秒**（或给雷达单独配
   PTP / 独立授时 GNSS）。
4. 复测命令（澄丰）：`python3 /tmp/livox_udp_probe.py -s 8`（**必须先停 livox 驱动**，否则点云 UDP
   被驱动占着 56301，探针只剩 56000 握手，现象是 `point_pkts=0 handshake=N`）；
   `python3 /tmp/ros_probe.py lidar 8 | pose 5 | gngga 6`（只订阅不发布）。
   两个探针本机副本已入库：`scripts/livox/livox_udp_probe.py`、`scripts/nav_diag/ros_probe.py`。
