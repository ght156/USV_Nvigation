# 导航侧与 Decision(嵌软) 对接问题清单与约定

- 日期：2026-09-04
- 发送方：导航侧（`USV_NAV` / `workspace_nav`）
- 接收方：嵌软（`decision` / `decision_core`）
- 范围：仅**导航对接**；电子围栏配置、归港/ReturnDock 不在本文档讨论范围。

---

## 一、总体结论

导航侧对外的接口（名称、消息类型、字段、主语义）与嵌软侧的 `decision` / `decision_core` **能对上**，这部分是通的：

- 主任务：`/mission_bridge/navigate`（`m_common/action/NavigateTask`），单点 1 个航点、无动作航线 ≥2 个；终态只看 Action Result。
- 暂停/恢复：`/mission_bridge/set_pause`（`m_common/srv/SetPause`）。
- 急停：`/mission_bridge/emergency_stop`（`m_common/srv/EmergencyStop`）。
- 退出急停：`/mission_bridge/cancel_mission`（`m_common/srv/CancelMission`）。
- 电子围栏：`/mission_bridge/set_geofence` / `get_geofence`（`zone_manager` 提供）。
- 航点字段 `latitude/longitude/yaw/seq`、`seq` 原样透传、QoS（`/nav_status` = RELIABLE + TRANSIENT_LOCAL, depth=1）都与对齐文档一致。

但嵌软侧在**几处导航对接逻辑**上存在需要修正的问题，具体见下文。其中第 2、5 项与本次约定强相关，请在联调前同步。

## 二、问题清单

### 问题 1：急停解除走了 Action Cancel，没有走 `cancel_mission` 服务（严重，会导致导航卡死在 EMERGENCY）

- **现象**：硬件急停松开、`/boat_control/emergency` 变 `false` 后，Decision 从 `EmergencyStop` 退出时调的是 `navActuator()->missionControl("cancel")`。
- **根因**：`missionControl("cancel")` 在 `NavActuator` 里是 **Action 标准 Cancel**（`async_cancel_goal`）。但急停发生时，导航已经把活动的 `NavigateTask` goal 以 `RESULT_EMERGENCY_STOP` abort 掉了，`NavActuator::active_` 已为 `false`，所以这一步**直接返回 `kStateNotAllowed`，什么都不发**。`NavActuator` 里其实创建过 `cancel_mission_service_` / `cancel_mission_client_`（`/mission_bridge/cancel_mission`），但全工程一次都没调用过。
- **影响**：导航侧 `EMERGENCY` 不会自动回 `IDLE`，**只有 `cancel_mission` 服务能退出**。Decision 不调它，导航一直停在 `EMERGENCY`，之后任何新的 `/mission_bridge/navigate` Goal 都会被拒（§3.2 处于 `EMERGENCY` 直接 reject），船动不了。
- **建议（嵌软侧改）**：在 `DecisionNode` 退出 `EmergencyStop` 时，调用 `/mission_bridge/cancel_mission` 服务（复用已创建的 `cancel_mission_client_`），而不是 `missionControl("cancel")`。导航侧无需改动。

### 问题 2：越界 Result 无法区分“闯入禁航区(2001)”与“驶出作业区(2002)”——**导航侧已修，请嵌软确认**

- **现象**：`taskCodeFromNavigationResult()` 里按 `error_code.find("INCLUSION")` 区分 2001/2002，但此前导航侧无论 `exclusion` 还是 `inclusion` 越界，`error_code` 恒为 `"GEOFENCE_VIOLATION"`，不含 `INCLUSION`，所以永远映射成 2001。
- **导航侧已做修改**（`mission_bridge.py`）：越界终止任务时，`error_code` 现在带围栏类型与进出方向：

  | 场景 | error_code |
  |---|---|
  | 闯入禁航区 | `GEOFENCE_VIOLATION:EXCLUSION:ENTER` |
  | 驶出作业区 | `GEOFENCE_VIOLATION:INCLUSION:EXIT` |

  `_emergency_stop()`（越界与急停竞速）和 `/mission_bridge/safety_event`（无任务越界时若有活动 goal）两条路径都已带上。
- **嵌软侧建议**：保持既有 `find("INCLUSION")` 映射即可（`INCLUSION` → 2002，`EXCLUSION` → 2001）；请确认不再硬编码“恒等于 `GEOFENCE_VIOLATION`”。同时请把 `safety_event` 的 `fence_type` + `transition` 字段也纳入文档约定。

### 问题 3：`NavData` 没有订阅 `/nav_status`、`/task_event`（状态通道是断的）

- **现象**：`NavData` 构造仅打印“consumes mission_bridge /nav_status and /task_event”，但**没有任何 `create_subscription`**；`updateState()` 从未被调用。
- **影响**：`NavData::state() / stateStale()` 永远为空/恒 `true`；`agent_status` 的导航块（`state` / `current_seq` / `state_age_ms`）永远不出现；嵌软也读不到 `/nav_status` 里的 `localization_overall`、`alerts_*`、`planner_status` / `controller_status` 等持续状态。任务主流程依赖 Action feedback/result 不受影响，但“导航运行健康状态”对上位是盲的。
- **导航侧已按契约发布**：`/nav_status`（`m_common/msg/NavStatus`，2 Hz，RELIABLE + TRANSIENT_LOCAL，depth=1）；`/task_event`（`std_msgs/String` JSON，RELIABLE，depth=50）。
- **建议（嵌软侧改）**：在 `NavData` 构造 `rclcpp::Subscription` 订阅 `/nav_status`（QoS 必须 RELIABLE + TRANSIENT_LOCAL，depth=1）；订阅 `/task_event` 并解析（或由 `NavActuator` 维护）。任务终态仍以 Action Result 为准。

### 问题 4：新任务“覆盖”旧任务存在竞态（潜在）

- **现象**：`PointNavigatingState` / `ReturnNavigatingState` / `MissionExecutingState` 在检测到新任务时调 `nav_act->missionControl("cancel")` 后立即回 `Idle`，下一 tick 重新派发新目标；但 `NavActuator::active_` 要等旧 goal 的 cancel `result_callback` 触发 `clearOperation()` 才变 `false`。
- **影响**：若新派发先于旧 Result 到达，`dispatchNavigate` / `executeMission` 会因 `if (active_) return kStateNotAllowed` 失败；单点导航还会 `clearGotoPoint()` 把新目标丢掉。
- **根因**：头注释写“待旧 Result 后再派发”，实现未等待。
- **建议（嵌软侧改）**：在“取消旧 goal 后、派发新任务前”显式等待 `NavActuator::isPaused()/isActive()` 回到空闲，或引入一次性的“cancel→dispatch”状态机。

## 三、航向 yaw 约定（重要，需嵌软配合）

### 3.1 现状与问题

- 云平台航点协议**不含 yaw**，`mqtt_bridgev2` / 嵌软 `decision` / 示教采点**恒填 0**。
- 导航侧 [mission_bridge.py `yaw_is_specified()`](/home/ght/USV_NAV/src/USV_NAV/workspace_nav/workspace_nav/mission_bridge.py:74) 判定 `[-2π, 2π]` 内的值为合法航向；**`0` 在范围内 → 被当成“朝东”**，不是“不指定朝向”。
- 因此：嵌软下发 `yaw=0` 时，导航会按“到点朝东”处理，而不会按“沿行进方向”。这与《decision_nav对接文档》§9.1 / §12 约定的“不指定朝向 → yaw 填超范围值（如 **65536**）”不一致。

### 3.2 约定（定稿）

| 语义 | 下发值 |
|---|---|
| 指定到点航向 | 合法弧度值，`[-2π, 2π]`（`0` = 朝东，是合法航向） |
| **不指定朝向** | **`65536.0`（或任意超出 `[-2π, 2π]` 的值）** |

规则：

1. 嵌软在把云航点转给导航前，**若云端未提供朝向（默认 0）且语义是“不指定”**，请把 `yaw` 填 **`65536.0`**。
2. 导航侧保持 `0 = 朝东` 不变（这是合法航向，不归为“不指定”）。
3. 导航收到超范围值后，到点朝向取该段航线的行进方向（见 `mission_bridge.py`，非 `yaw_is_specified` 时用 `atan2` 计算）。
4. 请嵌软侧在 `Waypoint` 转换成 `MissionWaypoint` 时执行上述规则：`yaw = (yaw 是否显式指定) ? yaw : 65536.0`。

> 说明：本项目导航暂不要求到点锁航向，按行进方向是更合理的行为；`0=朝东` 保留为合法的“精确朝东”朝向。
