### 2.6 Livox Mid360s（避障点云，**必须手动起**）

**两份驱动都能用，且都已编译**（2026-10-09 逐项核对）：

| 源码 | 编译产物 | 说明 |
| --- | --- | --- |
| `~/usv-main/src/drivers/lidar/livox_ros_driver2` | `~/usv-main/install/arm/livox_ros_driver2` | 主工程自带那份，**推荐用这个**（少 source 一个工作区） |
| `~/ws_livox/src/livox_ros_driver2` | `~/ws_livox/install/livox_ros_driver2` | 原厂工作区那份 |

两边**兴飞实际在用的** `launch_ROS2/msg_MID360s_launch.py` **逐字节相同**：
`xfer_format=0`（发 `sensor_msgs/PointCloud2`）、`frame_id=livox_frame`、`publish_freq=10 Hz`、
话题 `/livox/lidar`；配置 `config/MID360s_config.json` 也一致：
雷达 `192.168.2.191`、本机 `192.168.2.101`（**eth1**，与 CycloneDDS 同一张网卡）。
（两份 `CMakeLists.txt` 不同：ws_livox 是原厂 ROS1/ROS2 双用版、usv-main 裁成 ROS2-only，
两边都编译通过；`launch_ROS2/msg_MID360_launch.py` 的 `xfer_format` 两边不一样（0 / 1），
但兴飞不用这个文件。）

```bash
# 推荐：用 usv-main 那份（与主工程同工作区）
source /opt/ros/humble/setup.bash
source ~/usv-main/install/arm/setup.bash
source ~/logs/xingfei_stack/.cyclone_env      # DDS 限定 eth1；交互终端 .bashrc 已在 eth1 UP 时设过同样内容，脚本/非交互环境必须显式 source
ros2 pkg prefix livox_ros_driver2             # 期望：/home/hkzl/usv-main/install/arm/livox_ros_driver2
ros2 launch ~/usv-main/install/arm/livox_ros_driver2/share/livox_ros_driver2/launch_ROS2/msg_MID360s_launch.py

# 或：用 ws_livox 那份（源码树/安装树都行 —— 配置是相对 launch 文件找的，两边内容相同）
source ~/ws_livox/install/setup.bash
ros2 launch ~/ws_livox/src/livox_ros_driver2/launch_ROS2/msg_MID360s_launch.py
```

⚠️ **`source <工作区>/setup.bash` 不能省** —— 只 source `/opt/ros/humble` 会直接报（2026-10-09 现场踩到）：

```text
[ERROR] [launch]: Caught exception in launch: "package 'livox_ros_driver2' not found, searching: ['/opt/ros/humble']"
```

这句 = **工作区没 source**（不是驱动没编好）。补上后 `ros2 pkg prefix livox_ros_driver2` 应打印
`…/install/arm/livox_ros_driver2`，再起就正常。
另外注意域/RMW：交互终端里 `.bashrc` 已给 `ROS_DOMAIN_ID=5` + `rmw_cyclonedds_cpp`
（并在 eth1 UP 时自动限定 `CYCLONEDDS_URI=eth1`），**但 `.bashrc` 不 source 任何工作区**；
写脚本/非交互起时，域与 RMW 要自己 export —— 漏了会起在 domain 0，驱动看着"起成功了"，
导航侧却永远收不到点云。

⚠️ **要按文件路径起，短名会找不到文件**：两条 install 树里只有
`share/livox_ros_driver2/launch_ROS2/`，**没有 `launch/` 目录**，所以
`ros2 launch livox_ros_driver2 msg_MID360s_launch.py` 这种写法会报找不到文件
（2026-10-09 核对；本文早先写的短名命令已按实测改正）。

⚠️ **两个工作区别同时 source、别同时起** —— 否则 `/livox/lidar` 会有两个发布者，代价图来回跳。

注意文件名：`msg_MID360s_launch.py`（带 s，兴飞在用）≠ `msg_MID360_launch.py`（旧款）；
`start_odom.sh` 前置里写的是不带 s 的旧文件名，用脚本起前置 Livox 时要留意。

**它不在 `~/start_xingfei_stack.sh` 的 11 项里**（§2.9），感知 launch 也不带它
（2026-10-09 核对：感知日志里 0 处 livox），所以每次重启后要自己起。
不起的后果：Nav2 的 local/global costmap 都订阅了 `livox_cloud`（日志里可见
`Subscribed to Topics: livox_cloud`）却收不到点云 = **没有任何障碍物输入**，纯靠静态地图跑。

**验证（3 条）**：

```bash
ping -c2 192.168.2.191                                  # 雷达在网：1~2 ms
ros2 topic hz /livox/lidar                              # 应 ≈10 Hz
ros2 topic echo --once /livox/lidar --field header      # frame_id 应为 livox_frame
```

`livox_frame → base_link` 的静态 TF 由 `usv_transforms` 发（2026-09-28 标定：斜向后上方、
-43.9° yaw），**雷达驱动本身不发 TF**。

⚠️ 已知未修项：点云时间戳与 TF/里程计不同源（差 0.85 s，见
`docs/bug_debug/2026-09-17_TF与雷达时基偏差.md`），起了雷达后点云落图仍会整体错位
（直航 ≈0.42 m、转向时 20 m 处横向 ≈2.2 m）。

改雷达 IP 用 `~/ws_livox/src/livox_ros_driver2/tools/` 下的 `set_lidar_ip` / `set_lidar_ip_arm`
（主机侧对应 `scripts/livox/flash_lidar_ip.sh`）。

- 归港参数与 2026-10-07 的改动（纠偏外边界、虚拟坞位距离门、廊道门槛等）见

### 2.10 改完 usv_localization 后必须重编（2026-10-05 实测）

船端是**拷贝安装**（aarch64 → `install/arm`，不是 `--symlink-install`），所以改了
`~/usv-main/src/USV_NAV/usv_localization/` 里的 launch / config 后**必须重编**，
否则 `ros2 launch` 读到的仍是 `install/arm` 里的旧文件。

先确认运行时用的到底是哪一份：

```bash
source /opt/ros/humble/setup.bash && source ~/usv-main/install/arm/setup.bash
ros2 pkg prefix usv_localization
# 期望：/home/hkzl/usv-main/install/arm/usv_localization
# 注意：~/usv-main/install/usv_localization 是另一个 install base，不在运行路径上，别去改它
```

重编（只编这一个包，约 30 s）：

```bash
cd ~/usv-main
source /opt/ros/humble/setup.bash && source install/arm/setup.bash
colcon build --log-base log/arm --build-base build/arm --install-base install/arm \
  --base-paths src tools --packages-select usv_localization \
  --cmake-args -DCMAKE_BUILD_TYPE=Release -DROS_EDITION=ROS2 -DDISTRO_ROS=humble \
  -DCMAKE_TOOLCHAIN_FILE=/opt/vcpkg/scripts/buildsystems/vcpkg.cmake
```

校验（安装件应与 src 一致，diff 无输出即一致）：

```bash
S=~/usv-main/src/USV_NAV/usv_localization
D=~/usv-main/install/arm/usv_localization/share/usv_localization
diff -q $S/launch/usv_map_odom_tf.launch.py $D/launch/usv_map_odom_tf.launch.py
diff -q $S/config/usv_map_odom_tf.yaml   $D/config/usv_map_odom_tf.yaml
xacro ~/usv-main/src/usv_transforms/urdf/cleaning_boat_xingfei.xacro >/dev/null && echo XACRO_OK
```

- 编完**换新终端**（或重新 source `~/usv-main/install/arm/setup.bash`）再 launch。
- `usv_map_odom_tf.launch.py` 的 `publish_robot_tf` 默认 `true`，会额外起
  `robot_state_publisher` 发 `base_link→传感器` TF；若 `jzw_ws` 的
  `publish_tf.launch.py` 在跑，两处会抢同一段 TF，只留一个（另一处加 `publish_robot_tf:=false`）。
- **踩过的坑（2026-10-05）**：旧默认 xacro 路径 `~/usv/src/usv_transforms/urdf/usv.xacro` 在船上
  **不存在**——`~/usv` 是纯部署目录（只有 `install/`，没有 `src/`），而且 `usv.xacro` 早已改名成
  `cleaning_boat.xacro`（澄丰）/ `cleaning_boat_xingfei.xacro`（兴飞）。报错里跟着的
  `AttributeError: module 'xml' has no attribute 'parsers'` 是 xacro 打开文件失败后的次生报错，
  不是环境坏了。现默认已改为 `~/usv-main/src/usv_transforms/urdf/cleaning_boat_xingfei.xacro`。
- 主机留档 `/home/ght/usv/src/USV_NAV/usv_localization/launch/usv_map_odom_tf.launch.py`
  仍是旧的 `~/usv/src/...` 默认值，两边同步时留意。

### 2.11 换地图（2026-10-12 实做）

**判据：先比几何，再决定动不动 yaml。** 同一场地**同范围重绘**时，新 pgm 的
`尺寸 / 分辨率 / origin` 与旧图一致（2026-10-12 那次：1795×1455 @ 0.2 m、origin `[0,0,0]`，
逐像素差异仅 0.13%、障碍质心一致）→ **只换 pgm，yaml 不动**：yaml 里的 `ref_gnss_*` 锚点继续有效，
且锚点自洽（359 m ↔ 经度 0.00378°、291 m ↔ 纬度 0.00261°）。

一次要换齐的位置（**app/map 的 yaml 规则不同，见下**）：

| 位置 | 文件 | 为什么 |
|---|---|---|

## 3. RS485 驱动包（夹爪 / 背光板）

包路径：`~/usv-main/src/usv_rs485_driver`

统一管理 RS485 总线上的设备：水质传感器、BMS、IO 控制器、无线充电器等。
夹爪和背光板都挂在 **IO 控制器**（Modbus RTU，从站地址 64）的 DO 输出上。

当前通信方式（`config/usv_rs485_config.yaml`）：TCP → `192.168.2.111:18223`（串口服务器），非直连串口。

注意：整船启动时该节点可能由 `usv_app/launch/cleaning_boat.launch.py` 拉起；
`mqtt_bridgev2.launch.py` 若带 `start_rs485_driver:=true` 会在 `/mqtt` 命名空间下再起一份
（服务/话题带 `/mqtt` 前缀），两处同时起会抢总线，调试时确认只有一份在跑。

### DO 通道映射（2026-09-30 实物验证）

**2026-10-08 起控制归属改了**（归港侧判定，见下）：

| 位（掩码） | 硬件 | 控制逻辑 |
| --- | --- | --- |
| bit0（`0x0001`） | 夹爪电机线圈 | **只有出港**用 ControlDO 抬爪（电机动作 ~3s）。归港不用：船体靠机械结构自己把爪子撞开，`dock_claw_open_on_start=false` |
| bit1（`0x0002`） | 背光板 | **归港**由 `docking_fsm` 在找 Tag 阶段（ACQUIRE/APPROACH/ALIGN/REACQUIRE）经 `/set_do` 主动点亮 + 周期保活，DOCKED/FAILED/IDLE 关闭；BACK_IN/FINAL_DOCK 由驱动 WaitIO 自己开关。不依赖驱动的 ControlDO（驱动日志里叫 "DO2"，1 基命名） |
| bit2（`0x0004`） | 无线充电启停 | 2026-10-08 版驱动**已改走 TCP**（`wireless_charger_tcp.host=192.168.2.101:8236`），源码里不再使用此 DO 位 |
注意：`set_do` 写的是 **16 位全掩码**，不是单 bit 操作——`{digital_output: 2}` 会把
bit1 置位、其余全部清零。想保留其他通道状态时，先读当前 DO 再按位或：

```bash
ros2 topic echo /io_state    # digital_output 字段即当前 DO 掩码，按位或后再写回
```

2026-09-30 起驱动行为（船端已打补丁，见
`bug_debug/2026-09-30_RS485驱动DO定时关闭误伤背光与无线充电.md`）：
归港途中夹爪+背光保持不断电；WaitIO 结束（抓住/取消/失败）才一并断电；
10 分钟兜底仅断 DO0/DO1，无线充电全程不被定时器误关。

⚠️ **2026-10-08 回归**：当天 14:49 驱动整树被重刷后，上面那版补丁丢了——
`kDOOnMask` 回到 `0x0001`（不含背光位）、兜底回到 60s 且仍是 `writeDO(0x0000)`
全通道清零。已提单
`bug_debug/2026-10-08_RS485驱动ControlDO漏点背光板与60s全清回归.md`。
归港侧同时做了方向拆分 + 自己管背光（见下节），不再依赖驱动 ControlDO 点灯。

### 3.1 归港/出港的夹爪方向拆分（2026-10-08）

硬件事实：**归港时夹爪不用电机打开**（船体撞开机爪），**出港必须主动抬爪**
（爪子被船体扣住）。原来 `dock_claw_enabled` 一个开关管两个方向，表达不了，
已拆成两个参数（`usv_docking/config/docking.yaml`）：

| 参数 | 兴飞值 | 作用 |
| --- | --- | --- |
| `dock_claw_enabled` | `true` | 总开关：坞内是否用 WaitIO 判"抓住 → DOCKED" |
| `dock_claw_open_on_start` | **`false`** | 归港是否先 `WAIT_DOCK_OPEN` 开爪。`false` 直接从 `ACQUIRE_TAG` 起，因此**不会再出现 `DOCK_OPEN_FAILED/TIMEOUT` 这类归港失败**（10-06/10-07 共 11 次） |
| `dock_claw_release_on_undock` | `true` | 出港是否先 `WAIT_DOCK_RELEASE` 抬爪，失败 → `FAILED` 停车 |

> 其他船坞（坞爪需电机主动打开才能进船的，如澄丰）把
> `dock_claw_open_on_start` 置 `true` 即可回到原行为。

### 3.1.1 夹爪半抓住保护（2026-10-09）

现场事实（同事确认）：**一个夹爪抓住即爪子已扣住船体**，此时驶出重试会
拉拽船坞，危险。驱动 WaitIO 的成功判据是两个夹爪（DI bit0+bit1，掩码
`0x0003`）**同时**置位；单个夹爪的信息只在 WaitIO **feedback** 的
`digital_input` 里（驱动每次 goal 默认 3000 次 × 200ms = 10 分钟才超时，
实际先到的都是 FSM 侧超时）。

FSM 行为（`docking_fsm.py`）：

- WaitIO feedback 任一夹爪位置位 → 累计进 `_claw_partial_mask`（新会话清零；
  goal 不在途的迟到 feedback 帧直接丢弃）
- 此后坞内**一切驶出路径全部拦截**：停滞超时、压紧超时、BACK_IN/FINAL_DOCK
  超时、走廊违规、坞内丢 Tag、安全退出请求、全局超时，一律就地停车
  `FAILED`（`needs_manual_takeover=true`）
- **dock_mission 同步拦截**（2026-10-09 下午实船回归后补）：FAILED 的状态
  JSON 里 `needs_reapproach` 被历史契约强制 true，dock_mission 原先只认它，
  会把"就地停车"误判成 staging retry 把船开出去；现 `_dock_status_cb`
  优先认 `needs_manual_takeover` → 直接终局 FAILED + `MANUAL_TAKEOVER_REQUESTED`，
  不再自动重试
- WaitIO 继续重发监视（纯轮询无危险）：第二个夹爪抓住仍正常判 `DOCKED`
- 一个夹爪都没抓住过时，原行为不变（`ABORT_EXIT` 驶出由 dock_mission 重试）
- ⚠️ 代价：DI 信号若**误触发**（爪子实际没扣住），任务也会直接终局失败等
  人工接管，不再自动重试——DI 可靠性需与嵌软确认（必要时驱动侧加去抖）

### 3.2 船坞背光板由归港 FSM 管（2026-10-08）

归港不再发 ControlDO，驱动的"顺带点灯"没了，改由 FSM 自己点：

| 参数 | 兴飞值 | 说明 |
| --- | --- | --- |
| `backlight_enabled` | `true` | 无背光船坞置 `false` |
| `backlight_mask` | `2` | `/set_do` 是**全掩码**写：`2`=只 bit1 背光，`3`=夹爪+背光 |
| `backlight_keepalive_sec` | `20.0` | 找 Tag 阶段重发周期（须 < 驱动 60s 全清间隔） |
| `set_do_service` | `"set_do"` | `usv_rs485_driver/srv/SetDO` |

- 点灯：`/dock/start` 起，**整个归港会话保持**；**失败/重试不关灯**
  （重试期间相机还要看 Tag，灯一灭就要重新等一个 60s 级超时）
- 关灯：`DOCKED`（归港成功）、`/dock/cancel`、`/dock/undock` 三个会话真正结束的点
- **`WAIT_DOCK_OPEN/RELEASE` 与 `BACK_IN/FINAL_DOCK` 不干预**：那几段 bit1 由驱动
  自己驱动（ControlDO 写 `0x0001` / WaitIO 开关），两边同写会互抢
- 必须保活的原因：驱动 ControlDO 成功后 60s 会 `writeDO(0x0000)` 全清 DO，
  出港紧接归港时会把刚点亮的灯抹掉
- 现场手工验证：`ros2 service call /set_do usv_rs485_driver/srv/SetDO "{digital_output: 2}"`
- 现场判断：`ros2 topic echo --once /dock/status` 里看
  `backlight_session_active`（true=灯应亮）与 `docking_fsm` 日志的
  `船坞背光: 写 DO 0x0002/0x0000`

### 4.5 相机曝光（夜间/逆光检测 tag；2026-10-07 更新）

**现象**：夜间开背光板后，后视相机自动曝光把整个面板拉成均匀白块，二维码图案被洗掉，
`objects: []` 检测不到（白天同位置双 tag 稳定）。**位置/角度没问题，是过曝**。

**✅ 当前推荐方法：`~/bridge_calib/cam_backlight_mode.sh`**（仓库 `scripts/bridge_calib/`）

```bash

~/bridge_calib/cam_backlight_mode.sh on 50    # 切手动 + 短曝光（背光板点亮时用；值可省，默认 50）
~/bridge_calib/cam_backlight_mode.sh on 100   # 白天/弱背光：留环境光余量
~/bridge_calib/cam_backlight_mode.sh off      # 恢复自动曝光（默认安全态）
```

**为什么不用旧方法**（本节曾写 `python3 ~/v4l2_ctrl.py set exposure_auto 1` 那套）：

| 旧方法的问题 | 说明 |
|---|---|
| **设备号写死** | `~/v4l2_ctrl.py` 内 `DEV = "/dev/video0"`，而后视相机现在已漂到 **/dev/video8**（Orbbec 深度相机占 video0~7）。写死 = 改到**别的相机**上或直接失败，后视相机根本没人管 |
| 必须先切手动 | `exposure_auto=3(自动)` 时直接写 `exposure_absolute` 报 EACCES —— 这点新旧脚本都一样 |

`cam_backlight_mode.sh` 按 `/sys/class/video4linux/video*/name` 里的 **"USB Camera"** 自动找设备
（2026-10-06 起），重启后设备号漂移也不怕。

**按光照选值**（2026-10-07 实测补充）：

| 场景 | 设置 | 说明 |
|---|---|---|
| 白天、背光关 | `off`（自动）或 `on 80`~`on 100` | 自动足够；要稳可手动留余量 |
| 逆光 / 傍晚 / **夜间且背光板点亮** | **`on 50`** | 黑底亮 tag、抗过曝，实测检出 100% |
| **夜间、背光没开** | ⚠️ **手动短曝光 = 全黑** | 2026-10-07 18:19 实测：夜里不开背光时 `on 50` / `on 100` 抓帧只剩几个灯点（36 KB 帧），`off`（自动）才有 122 KB 的环境轮廓。**夜间要检测 tag 必须先点亮船坞背光板**，单靠调曝光救不回来 |

**验证**：`python3 ~/grab_frame.py` 抓一帧肉眼确认；或 `ros2 topic echo --once /docking/tag_visible`。

**背光亮度**：RS485 驱动侧 DO 只有开关（Modbus 线圈，无 PWM/调光接口），
亮度调节只能看硬件侧（灯箱驱动是否有调光旋钮），软件无法调。

注意：

- v4l2 设置是**临时的**：相机/节点重启或重新插拔后恢复自动曝光，夜间测试前需重设。
- 白天用手动曝光 50 会全黑，**白天务必 `off` 恢复自动**。
- 长期方案：给 video_camera 节点加曝光参数支持，或在 perception launch 里固化
  v4l2 设置（最好按白天/夜间分两档）。

## 5. 与归港算法（usv_docking）的接口对应

已核对（2026-09-30）：本地与船端 `docking_fsm.py`、`docking.yaml` 完全一致，接口匹配，无需改代码。

**⑥ 点云 vs 局部代价图：为什么 RViz 里"障碍物不全"（2026-10-09 实测 + 源码核对）**

工具：`python3 $B --compare 5`（逐格对比点云与局部代价图，只读；`--voxelcheck` 看 voxel 层内部网格，
注意 `/local_costmap/voxel_grid` 是 `nav2_msgs/VoxelGrid` 不是点云）。

一帧 20064 点（10 Hz）的实测流水：

```text
点云 20064 点/帧
 → 观测源窗口（3D 距离 1.4~15 m、z∈[-0.35,1.0]）     剩 ~1500 点/帧
 → voxel 层 z 窗口（min_obstacle_height=0.0 ~ max=0.6）剩 ~650 点/帧
 → 每帧满足 mark_threshold=2 的格子只有 139~150 个（8 帧并集 323）
 → 代价图实际致命格：281 个，集中在"船头前 ~8.6 m、左舷 ~4.9 m"一簇
```

**`mark_threshold` 不是"点数"，是"该格被标过的 z 体素个数"，且比较是【严格大于】**：源码
`nav2_voxel_grid/voxel_grid.hpp::markVoxelInMap()` 取列的 16 位 z 掩码
（`marked_bits = *col >> 16`），条件是 **popcount > mark_threshold**
（`bitsBelowThreshold` 用 `>`，2026-10-10 更正：不是 ≥）→ **0=单层即标、1=需≥2层、2=需≥3层**。
voxel 位跨帧累积（射线清了才消失），所以平面目标靠船体微晃几帧内能攒出第 2 层（阈值 1 能标），
但远岸掠射角每列最多 1~2 层 → **阈值 2 时连较高的岸也标不上**（2026-10-10 实测复现）。

- 同一格里的点**全在同一个 10 cm 高度层**（水面、平岸、单一高度的船体/码头面）→ 只置 1 位
  → **永远达不到 2 → 永远不标**；
- 只有**有垂直结构**的格子（码头边缘、桩、坡面，点在 ≥2 个高度层里）才会被标成障碍
  → 这就是 RViz 里"点云有、代价图不成片"的直接原因，也解释了为什么清完代价图后**同一簇 281 格
  立刻原样回来**（那是唯一满足"跨 2 个高度层"的地方，不是残留）。

**机械证据**（`$B --voxelmap` 解码 `/local_costmap/voxel_grid`，就是层内部那个网格）：


**真正的三个闸门**（实测）：

| 参数 | 作用 |
|---|---|
| `voxel_layer.mark_threshold` | **主闸门**：只留"跨 ≥2 个 z 体素"的格子 → 平面目标几乎全不标 |
| `voxel_layer.livox_cloud.obstacle_max_range: 15.0` | 15~30 m 的岸（实测 1198 点/帧进不来）；24 m 窗口半对角 ≈17 m，取 18 才覆盖全窗 |
| `voxel_layer.max_obstacle_height: 0.6` | 高于此的点不入体素（岸的上部）；观测源上限已是 1.0，此处才是卡点 |

⚠️ 更正（2026-10-09 实测）：`voxel_layer.min_obstacle_height` **在 voxel 标记路径里不生效**
（A/B 把它改 -0.35，致命格 281→281 完全不变；`--voxelmap` 也显示被标体的 z 低到 -0.37，
说明下界只由**观测源**的 `min_obstacle_height: -0.35` 决定）。别改这个参数去调下界。

**2026-10-09 已落地的参数改动**（`nav2_params_xingfei.yaml`，船端已同步 + 备份
`nav2_params_xingfei.yaml.bak_20261009_183739`）：

| 位置 | 参数 | 改前 → 改后 |
|---|---|---|
| local voxel_layer | `mark_threshold` | 2 → **1** |

**岸"贴到船边还是不进图"时按这个顺序排（2026-10-09 补充实测）**：

1. **先确认看的是哪张图**：全局代价图（`/global_costmap/costmap`）的 voxel 层实测 `enabled: false`
   → 全局图上**没有任何雷达障碍**，只有静态图的黑边（静态图的岸线本身比实际靠水域，
   所以看着就是"岸没显示"）。要看雷达障碍请订 `/local_costmap/costmap`。
2. **不是高度带**：把 `voxel_layer.max_obstacle_height` 0.6→1.5、观测源 1.0→2.0 在线试，
   致命格只从 1230 变 1267（+37）→ 岸不是被上限切掉的（已还原 0.6/1.0）。
3. **不是 TF 冲突**：`$N tfcheck` 实测 `base_link → livox_frame` 全程只有一个取值
   （= xacro 的 2.05/0/0.28、-0.02°/-43.87°/180°），`/tf_static` 发布者只有
   mavros + robot_state_publisher（正常）。
4. **真正的两个"贴边禁区"**（船紧贴岸时最容易中招）：
   - `obstacle_min_range: 1.4`：以**雷达光心**为球心的 1.4 m 盲区（雷达在 base_link 前 2.05 m）
     → 岸若在雷达 1.4 m 内直接丢；
   - `footprint_clearing_enabled: true`：每周期把**船体 footprint + padding**（前 2.7 m、
     后 0.5 m、半宽 0.84 m + 0.2 m）范围内的标记清掉 → 岸落在 footprint 里就永远不显示。
   现场可按需试 `obstacle_min_range: 0.5` / `footprint_clearing_enabled: false`
   （代价：船头自反射/自身结构会入图，配合高度带压）。
5. **底噪**：一帧 19968 点里 **16550 点（83%）是 0~0.2 m 的贴窗回波**，1.4~15 m 只有 ~2000 点
   → 可用点太少，岸只能标成稀疏带。擦净雷达窗口后复检 `--diag` 的"雷达 1.4m 内"应从 1.6 万降到几百。

| 改动 | 致命格 | 膨胀代价格 |
|---|---|---|

## 8. 注意事项

- 所有 RS485 设备共享同一条半双工总线，由 `RS485Manager` 串行化访问，不要绕过节点直接操作串口。
- WaitIO / ControlDO 运行期间会覆盖手动设置的 DO2 / DO0+DO1 状态，手动调试时先确认没有归港任务在跑。
- 完整协议与消息定义见船端 `~/usv-main/src/usv_rs485_driver/README.md`。
