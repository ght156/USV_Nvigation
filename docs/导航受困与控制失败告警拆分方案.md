## 1. 文档目的

当前导航把“导航控制失败”和“船体受困”合并成一个
`CONTROLLER_OR_STUCK=2007` 终态。实际作业中两者恢复方式完全不同：

- 控制器故障：控制链本身不可用，人工把船拖出来也不能恢复原任务。
- 船体受困：控制器和定位可能都正常，只是船被障碍、水草或其他外力困住；
  人工脱困后可以继续原任务。

同时，规划失败也存在两类不同情况：

1. 起点被代价图障碍覆盖、局部通道被堵。人工移出障碍后可能恢复。
2. 目标航点非法、在地图外、位于不可达障碍内。移动船通常不能解决问题。

本文只讨论导航侧以下问题：

- 路径规划失败；
- 控制器故障；
- 船体受困/无进展；
- 定位丢失；
- 导航未就绪；
- 任务执行超时。

**电子围栏逻辑不在本次调整范围内，保持现有设计。**

## 2. 建议业务先确认的结论

### 2.1 推荐采用“三类故障”而不是“一码兜底”

| 故障 | 本质 | 是否可人工恢复 | 推荐上层动作 |
|---|---|---:|---|
| 控制器故障 | 控制器没有输出、输出非法或控制 Action 异常 | 否，通常需修复/重启控制链 | 取消底层 Action，任务 `FAILED` |
| 船体受困 | 定位有效、控制器有输出，但船持续没有位移 | 是，可人工脱困 | `PAUSED`，保留任务断点 |
| 规划受阻 | 起点在障碍中，或合法起终点之间持续无路 | 多数可人工移出/清障 | `PAUSED`，保留任务断点 |
| 规划目标非法 | 目标地图外、障碍内、禁航区或数据非法 | 否，移动船通常无效 | `FAILED` |

### 2.2 “取消”和“失败”的术语要统一

自动故障不应上报 `CANCELLED/2005`。推荐口径：

1. 上层可以 cancel/abort 底层 NavigateTask Action，保证导航停车；
2. 对平台的任务结果仍上报 `FAILED`，并带具体故障码；
3. `CANCELLED` 保留给人工取消、新任务替代等明确取消动作。

否则云平台容易把“控制器故障”理解成“操作员主动取消，可随时恢复”。

## 3. 当前代码事实

### 3.1 导航侧

- [nav_status_aggregator.py](../src/USV_NAV/workspace_nav/workspace_nav/nav_status_aggregator.py)
  当前把“控制器命令流中断”和“船体无进展”都归为 `CTRL_STUCK`。
- 当前 `controller_status` 只有 `OK/STUCK`，没有独立的控制器故障状态。
- [mission_bridge.py](../src/USV_NAV/workspace_nav/workspace_nav/mission_bridge.py)
  的 `CTRL_STUCK` 看门狗持续超时后，会取消 Nav2 任务并返回
  `RESULT_CONTROLLER_FAILED`。
- `RESULT_STUCK=7` 已在
  [NavigateTask.action](/home/ght/usv/src/m_common/action/NavigateTask.action)
  中定义，但当前没有生产路径。
- Humble 的 `FollowWaypoints.Result` 不能直接给出“起点在障碍中”或
  “目标非法”的细粒度原因，只能看到航点被标记为 missed。
- 规划器内部的单次 `PLAN_FAILED` 只是告警，不代表任务已终止；任务是否终止取决于
  Nav2 最终是否产生 missed waypoint。

### 3.2 上层决策侧

- [mission_executing_state.cpp](/home/ght/usv/src/decision/src/state/mission_executing_state.cpp)
  当前只把 `2009 定位丢失` 和 `2002 驶出作业区` 视为可恢复暂停。
- `RESULT_PLANNING_FAILED` 映射为 `2006/FAILED`。
- `RESULT_CONTROLLER_FAILED` 和 `RESULT_STUCK` 都映射为 `2007/FAILED`。
- 上层已经支持“导航 Action 结束后，从当前已完成航点的下一个点重新派发”，
  所以可恢复阻断不需要重新设计整套任务恢复机制。

### 3.3 当前主要问题

1. `CTRL_STUCK` 同时包含控制链故障和船体受困，无法选择暂停或失败。
2. `RESULT_STUCK=7` 没有使用，船体受困只能落到 `RESULT_CONTROLLER_FAILED`。
3. 规划失败没有原因分类，目标非法和起点被困走同一条终态。
4. `/nav_status` 告警适合展示，但当前缺少明确、持续、可由上层执行动作的
   “可恢复阻断”字段。
5. 单帧告警、自动恢复成功和持续故障没有形成清晰的三级语义：
   告警、自动恢复、任务阻断。

## 4. 导航侧目标设计

### 4.1 将控制器故障与船体受困拆开

在 `nav_status_aggregator.py` 中建议拆成两个独立状态：

```python
_controller_output_failed = False
_vessel_no_progress = False
```

#### `CONTROLLER_OUTPUT_FAILED`

满足以下条件时判定：

- `controller_server` 正在执行 FollowPath；
- `/cmd_vel_nav` 超过阈值时间无更新，或出现 NaN/Inf；
- 或控制器 Action 异常退出；
- 自动代价图重膨胀恢复一次后仍无有效控制输出。

建议状态字段：

```text
controller_status = FAILED
controller_last_error = CONTROLLER_OUTPUT_FAILED
last_error = CONTROLLER_OUTPUT_FAILED
block_recoverable = false
```

上层动作：

```text
abort/cancel 当前 NavigateTask Action
任务报告 FAILED/2007
```

#### `VESSEL_NO_PROGRESS`

满足以下条件时判定：

- 定位状态为 `GOOD`；
- 控制器 Action 正在执行；
- 最近存在有效的非零线速度/角速度输出；
- 船的实际平面位移持续小于阈值；
- 持续时间超过配置门槛。

建议状态字段：

```text
controller_status = STUCK
controller_last_error = VESSEL_NO_PROGRESS
last_error = VESSEL_NO_PROGRESS
block_recoverable = true
nav_phase = STUCK
```

上层动作：

```text
停止任务推进
上报 PAUSED
要求人工脱困
保留航点和断点
人工确认后再恢复或取消
```

#### 自动恢复顺序

建议先保留现有自动自愈：

```text
控制输出静默
  → 触发一次代价图重膨胀
  → 控制输出恢复：清除告警，继续任务
  → 仍无输出：CONTROLLER_OUTPUT_FAILED，失败

有控制输出但无位移
  → VESSEL_NO_PROGRESS 告警
  → 持续超过门槛：可恢复阻断，暂停
```

### 4.2 规划失败分类

Humble 本身没有足够细的规划错误码，建议导航侧增加一个分类器。

#### `PLANNER_START_BLOCKED`

条件：

- planner 返回 missed/失败；
- 当前船位位于全局代价图的致命或不可通行区域；
- 或起点附近找不到可通行的最近替代格。

建议：

```text
recoverable = true
上层动作 = PAUSED
```

#### `PLANNER_TARGET_INVALID`

条件：

- 目标点在地图外；
- 目标点位于致命障碍格；
- 目标点违反硬边界或任务校验；
- 航点字段非法。

建议：

```text
recoverable = false
上层动作 = FAILED/2006
```

#### `PLANNER_NO_PATH`

条件：

- 起点和目标都合法；
- planner 连续重试后仍无法生成路径；
- 场景可能由动态障碍、地图变化、通行走廊被堵造成。

建议：

- 首次失败只告警并允许 Nav2 自身恢复；
- 连续失败达到配置门槛后判可恢复阻断；
- 上层动作 = `PAUSED`，人工移船、清障或更新地图后恢复。

#### 代价图检查建议

在 [mission_bridge.py](../src/USV_NAV/workspace_nav/workspace_nav/mission_bridge.py)
收到 missed waypoint 后，可调用全局代价图服务检查起点和目标：

```text
起点格致命/不可通行         → PLANNER_START_BLOCKED
目标格非法/地图外           → PLANNER_TARGET_INVALID
起点和目标合法但无路         → PLANNER_NO_PATH
```

可使用 Nav2 的 `/global_costmap/get_costmap` 服务进行只读检查。
如果服务不可用，建议保守回退为 `PLANNER_NO_PATH`，并在日志中明确记录
“代价图分类不可用”，不要根据 planner 日志字符串做正式协议判断。

### 4.3 首轮自动恢复

建议规划失败后先做一次可观测的自动恢复尝试：

1. 清一次全局代价图或执行现有重膨胀；
2. 重新规划；
3. 成功：清除 `PLANNER_*` 告警，任务继续；
4. 失败：按上述三类原因进入暂停或终态。

自动恢复次数建议配置化，不写死在代码中。

### 5.1 扩展 `NavStatus.msg`

当前

建议追加以下字段，保留原有字段以兼容旧订阅者：

```text
# 导航可恢复阻断状态

```

建议取值：

```text

PLANNER_NO_PATH
PLANNER_TARGET_INVALID
VESSEL_NO_PROGRESS

```

建议的可恢复性：

| block_type | 可恢复 | 上层动作 |
|---|---:|---|
| `PLANNER_START_BLOCKED` | 是 | `PAUSED` |
| `PLANNER_NO_PATH` | 是，达到重试门槛后 | `PAUSED` |
| `VESSEL_NO_PROGRESS` | 是 | `PAUSED` |
| `LOCALIZATION_LOST` | 是 | `PAUSED` |
| `PLANNER_TARGET_INVALID` | 否 | `FAILED/2006` |
| `CONTROLLER_OUTPUT_FAILED` | 否 | `FAILED/2007` |

`block_type=NONE` 表示阻断解除。

### 5.2 保持现有告警通道兼容

建议现有 `/task_event` 继续发布：

```text
PLAN_FAILED
CTRL_STUCK
LOC_LOST
LOC_DEGRADED
MISSION_FAILED
```

新增细分信息优先放在：

```text
/nav_status.planner_last_error
/nav_status.controller_last_error
/nav_status.block_type
```

重要约定：

- `ALARM_RAISED/CLEARED` 只用于平台展示和日志；
- 上层任务状态不能只依赖瞬时告警事件；
- 暂停/失败动作应以持续状态或 Action Result 为准，避免漏消息和竞态。

## 7. 上层决策对接行为

### 7.1 收到可恢复阻断

当满足以下任一条件：

- `NavStatus.block_type` 为可恢复类型且 `task_id` 匹配当前任务；
- 或 NavigateTask 返回 `RESULT_STUCK=7`；

上层应：

1. 向导航发送暂停；
2. 保持当前任务、航点、断点和电子围栏；
3. 上报 `PAUSED`；
4. `VESSEL_NO_PROGRESS` 报 `2032`；
5. `PLANNER_START_BLOCKED/NO_PATH` 报 `2033`；
6. 平台显示“人工脱困/移出障碍后恢复或取消”；
7. 不自动恢复，必须由操作员确认。

### 7.2 收到不可恢复故障

`CONTROLLER_OUTPUT_FAILED`：

1. abort/cancel 当前导航 Action；
2. 任务上报 `FAILED/2007`；
3. 不保留可恢复断点；
4. 修复控制器后重新下发任务。

`PLANNER_TARGET_INVALID`：

1. 终止任务；
2. 上报 `FAILED/2006`；
3. 提示操作员修改航点或任务数据。

### 7.3 恢复任务

建议支持两种恢复路径：

1. **同一目标恢复**

   人工只把船移出障碍，原目标仍有效。恢复后从当前任务断点重新规划。

2. **指定航点恢复**

   人工移动期间已经越过原目标，平台允许下发 `start_seq`，从指定航点继续，
   避免恢复后倒回去寻找旧目标。

上层现有逻辑会从 `reached_seq+1` 重新派发剩余航点。业务需要确认：

- 默认恢复是否继续原目标；
- 是否需要平台提供“从当前位置之后的最近航点继续”；
- 是否需要人工选择恢复航点。

### 7.4 再次受阻

恢复后如果导航再次产生相同可恢复阻断：

1. 再次暂停；
2. 不自动反复恢复；
3. 记录本轮任务已恢复次数；
4. 达到业务设定上限后提示人工取消或重新规划。

## 8. 建议的导航修改点

### 8.1 `nav_status_aggregator.py`

- 拆分 `_controller_output_failed` 与 `_vessel_no_progress`；
- `controller_status` 扩展为 `OK/FAILED/STUCK`；
- 增加 `block_type/block_recoverable/block_duration_sec` 更新；

- 自动恢复成功必须清除阻断状态；
- 不能在 aggregator 内直接 cancel 任务，继续遵守“纯观测节点”边界。

### 8.2 `mission_bridge.py`

- 收到 `CONTROLLER_OUTPUT_FAILED`：返回 `RESULT_CONTROLLER_FAILED`；
- 收到 `VESSEL_NO_PROGRESS`：优先让上层暂停；未能及时暂停时返回
  `RESULT_STUCK + VESSEL_NO_PROGRESS` 作为兜底；
- missed waypoint 时执行规划原因分类；
- 起点受阻或持续无路：`RESULT_STUCK`；
- 目标非法：`RESULT_PLANNING_FAILED`；
- 不要把 Humble 的空 `error_msg` 作为分类依据。

### 8.3 `m_common`

- `NavStatus.msg` 增加可恢复阻断字段；
- `MissionState.msg` 增加 `VESSEL_BLOCKED=2032`、
  `PLANNER_BLOCKED=2033`；
- `NavigateTask.action` 仅补充注释，说明 `RESULT_STUCK=7` 表示“可恢复阻断”；
- `m_common` 修改后，导航仓和船端主仓必须同步并重新编译接口包。

### 8.4 上层 `decision` / `decision_core`

- `RESULT_STUCK=7` 映射到暂停，不再映射到 `2007`；
- `CONTROLLER_OR_STUCK=2007` 建议只保留“控制器失败”语义；
- 新增 `2032/2033` 的中文原因文案；
- `isPausingNavigationCode()` 增加新暂停码；
- 恢复时保留任务、航点和围栏断点；
- 平台取消时仍按原有取消流程丢弃断点。

```yaml
vessel_no_progress_timeout_sec: 15.0
```

- 低速作业时可能过晚；
- 到点原地转向可能误报；
- 应结合当前有效速度、船速和任务类型设置。

## 10. 验收用例

### 10.1 控制器故障

- 人为停止 controller_server；
- 确认 `/nav_status.block_type=CONTROLLER_OUTPUT_FAILED`；
- NavigateTask 返回 `RESULT_CONTROLLER_FAILED=6`；
- 上层最终上报 `FAILED/2007`；
- 人工移动船后不自动恢复任务。

### 10.2 船体受困

- 模拟障碍卡住船体；
- 定位持续 GOOD，控制器持续输出非零速度；
- 超过阈值后 `block_type=VESSEL_NO_PROGRESS`；
- 上层进入 `PAUSED/2032`；
- 人工移出后 resume，从断点继续；
- 若平台指定 `start_seq`，按指定航点继续。

### 10.3 规划起点受阻

- 将船位姿放到全局代价图致命区域；
- planner 返回 missed；
- 分类为 `PLANNER_START_BLOCKED`；
- 导航返回 `RESULT_STUCK=7`；
- 上层进入 `PAUSED/2033`；
- 人工移出后重新规划成功并恢复。

### 10.4 规划目标非法

- 将目标设置在地图外或不可达障碍格；
- 分类为 `PLANNER_TARGET_INVALID`；
- 导航返回 `RESULT_PLANNING_FAILED=5`；
- 上层上报 `FAILED/2006`；
- 不进入暂停等待。

### 10.5 瞬时规划失败

- planner 第一次失败，下一次重规划成功；
- 只发布短暂告警并清除；
- 不改变任务状态；
- 不产生 NavigateTask 终态。

### 10.6 定位丢失

- 保持现有 `RESULT_LOCALIZATION_LOST=8 -> PAUSED/2009`；
- 定位恢复后由人工确认恢复；
- 不自动恢复航行。

### 10.7 重复恢复失败

- 同一任务连续触发可恢复阻断；
- 每次均暂停，不自动恢复；
- 达到业务设定上限后提示人工取消或重新规划。

## 11. 需要业务/平台确认的问题

1. 是否同意新增 `2032 VESSEL_BLOCKED`、`2033 PLANNER_BLOCKED`。
2. `PAUSED` 状态下，平台是否支持显示具体 `block_type` 和处理建议。
3. 人工脱困后，默认从原目标恢复，还是从当前位置之后的最近航点恢复。
4. 是否支持平台下发 `start_seq` 指定恢复航点。
5. 同一任务允许人工恢复几次；超过上限后是否自动取消。
6. 船体受困阈值采用固定值，还是根据当前命令速度动态计算。
7. 规划失败第一次只告警、第几次开始暂停。
8. 定位丢失超过多长时间后由暂停升级为失败/人工接管。
9. 控制器输出失败前是否保留一次自动代价图重膨胀。
10. `HISTORY`/`CLEARED` 告警如何展示，避免平台告警列表一直保留已恢复项。
