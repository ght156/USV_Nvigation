### 2. 顺带发现、请你确认的一个历史问题

yaml 里原有的 `publish_period_ms: 5000` 这个键，在节点源码里**没有对应的 `declare_parameter`**（节点声明的是 `wireless_charger_period_ms`，默认 5000）。也就是说 `publish_period_ms` 很可能是个不生效的孤儿键，无线充电器此前一直以代码默认 5s 轮询。请确认它是历史遗留还是应该映射到某个参数。

### 3. 使用方式的变化（调用方，不是你的代码）

- **监测开关开始被真正使用**：`/wireless_charger_monitor` service 此前从未被调用（充电器状态一直没在轮询）。现在 `docking_fsm` 会在进入归港 BACK_IN 时自动 `enable: true`，归港会话结束（回 IDLE/FAILED）时 `enable: false`，对接成功（DOCKED）后保持开启以便观察充电。
- **新增话题消费方**：`docking_fsm` 订阅 `/wireless_charger_state`，判据为 `charging_status ∈ {1(充电中), 5(已充满)}` 且 `error_code == 0` 连续稳定 2 秒 → 判定对接到位。
- 这些调用遵循你代码里既有的"懒加载 + 接口缺失降级"约定：service/话题不可用时归港侧只 warn，不阻塞，自动退化到原 WaitIO/超时逻辑。

### 4. 今天实测验证（信号链端到端正常）

- 开监测后 `/wireless_charger_state` 1s 一帧稳定发布；
- 船在坞内真实充电：**53.8V / 15.1A（约 800W），`charging_status=0x01`，`error_code=0`**，发射端 42°C / 接收端 41°C；
- 早前船停对接位但 BMS 接近满电（95.3%）时电流为 0A 但 status 仍为 1，说明 `charging_status=1` 反映"耦合成功/充电链路建立"，适合做到位判据。

## 二、9/30 前后的改动（按文件修改时间与调用方行为推断，请你核对）

> usv-main 不是 git 仓库、9/30 的源码备份未包含本包，无法给出精确 diff。以下为文件 mtime（2026-09-29~10-01 被修改：`src/usv_rs485_node.cpp`、`include/usv_rs485_node.hpp`、`include/modbus_master.hpp`）结合当前代码与调用方行为整理的接口面，如有出入以你的记录为准。

9/30 为配合归港栈（兴飞船坞夹爪对接）上线，驱动侧增加了以下接口（均沿用至今、今天验证均正常）：

| 接口 | 类型 | 用途 | 备注 |
|---|---|---|---|
| `ControlDO.action` | action | 请求船坞夹爪开/合（DO0/DO1） | FSM 每次归港开始调用；曾有"goal 被拒（在途 goal 竞态）"告警，FSM 已做下周期重试兜底 |
| `WaitIO.action` | action | 轮询等待夹爪抓住/停泊到位 DI | 成功掩码 `io_wait_input_mask=0x0003`（DI0+DI1 同时置位）；执行期间强制保持 DO2 ON；成功/取消时关 DO0/DO1 |
| `wireless_charger_monitor` service | srv | 无线充电状态轮询门控（默认关） | 今天起由归港 FSM 自动开关（见上） |
| `/kvmsbms_state` 话题 | msg | KVMS BMS 电池状态 | 含电流符号约定：负值为充电 |
| BMS RSOC → DO3 自动充电控制 | 内部逻辑 | RSOC<95% 开、>99% 关 | 仅在 WaitIO 成功过之后才允许执行（防止未对接就充电） |

调用方（`usv_docking/docking_fsm.py`）对这些接口的使用方式：全部懒加载、`usv_rs485_driver` 包不可导入时降级（夹爪交互不可用但归港流程继续），WaitIO 仅在坞内状态（BACK_IN/FINAL_DOCK）存活。

## 三、注意事项 / 建议

0. **（2026-10-06 新发现）共享总线挤占**：WaitIO 期间 IO 以 5Hz 轮询，叠加 BMS×2、水质、充电器 1s 后，网关串口排队会让充电器读取错过 500ms 响应窗口（TCP poll timeout）。已用配置缓解（WaitIO 2.5Hz + 充电超时 1s）。**治本建议：如果 IO 控制器支持 DI 变化主动上报/中断模式，WaitIO 就不用轮询了**；另外 `wireless_charger_period_ms` 保持 1000 是归港充电判据的硬需求，请勿回退。
1. **轮询负载**：充电器改为 1s 一帧后，总线上同时有 BMS×2、水质、充电器、IO（WaitIO 期间）在跑，今天实船观察未见丢帧/超时告警；如果日后总线紧张，`wireless_charger_period_ms` 是第一可调项。
2. **兼容约束**：归港侧现在依赖 `WirelessChargerState.msg` 的 `charging_status` 取值约定（0=待机，1=充电中，2=耦合度检测，5=已充满，0xFF=故障/禁止）。若充电器固件升级改了状态语义，归港到位判据会失效，请同步告知。
3. **`charging_status` 与电流解耦**：接近满电时电流可为 0 但 status 仍为 1（耦合建立）。如果你们更倾向用"电流 > 阈值"做判据，也可以，归港侧改动很小，但浮动坞场景下 status 判据更直接。
4. **孤儿键 `publish_period_ms`**：见上文一.2，建议清理或映射。
5. 今天归港链路其它改动（速度桥位置保持/旋转刹车、nav2 限速、归港压紧段状态机等）与 rs485 无接口关系，不展开；需要了解可找我要完整变更记录。
